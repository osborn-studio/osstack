# Refactoring

Use when structure changes while the observable behavior contract stays the same. State that contract before editing. New behavior belongs to [feature](feature.md); correcting a defect belongs to [bug fix](bug-fix.md). Separate those changes from the structural diff and apply their own checks within existing authorization. Do not disguise a behavior change as cleanup.

1. Read the implementation, consumers and current verification. Record the baseline revision/build and the behavior to preserve: outputs, errors, ordering and side effects relevant to this surface. Capture a characterization test, snapshot or old-versus-new comparison before moving structure. If coverage is missing, add the smallest useful pin first. A typecheck or lint result alone is not a behavior pin. When the baseline cannot be exercised, record the blocker and keep equivalence unproved.
2. Name the concrete structural problem and target shape. Explain where it reduces reader effort: fewer competing representations, fewer invalid states or a clearer ownership boundary. Keep already clear local code. For a cross-module move, inspect the call graph and compare viable boundaries before changing callers.
3. Remove demonstrably unused or redundant layers before adding abstractions. Check exports and external consumers before calling an API dead. Move in small steps and keep the same baseline checks green. Revert speculative reshaping that does not improve the stated problem.
4. For a rename or API reshape, inventory every affected caller, configuration key, string reference and relevant documentation link. Use symbol references and text searches; account for generated or dynamic references and known external consumers. Migrate in-scope consumers and check their actual surfaces. Remove an old API only when the scope and compatibility contract permit it. If external consumers require a transition, name that obligation and use an explicitly scoped compatibility plan; do not silently break them or invent a permanent dual path. When all in-scope callers are migrated and no external compatibility obligation remains, remove the old path in the same unit. Any temporary compatibility path needs an owner, known consumers and an explicit removal condition. Escalate cross-owner writes to the coordinator while continuing disjoint work.
5. Compare baseline and candidate under the same inputs and environment on the real artifact. Preserve the selected outputs, errors and side effects. Normalize only declared nondeterminism; never discard a meaningful difference to force equality. Keep any unexplained difference as failed or unknown equivalence. For a larger reshape, retain a replay or differential harness. If the driver itself needs repair, use [maintain verification](maintain-verification.md) and preserve the old result before rerunning.
6. Review whether the result is simpler to understand. State a concrete improvement rather than only a line-count reduction. Keep ordered, behavior-preserving units independently checkable. PR preparation authority does not imply approval or merge authority; preserve any user-reserved merge step. Follow the existing task's commit/publication scope and [evidence/cleanup rules](evidence.md).

When a refactor exposes a real defect, record it separately. Do not change the behavior pin to absorb the fix. Split the fix and its regression evidence into an authorized follow-up, or revise the task scope explicitly if it must be resolved first. A broad redesign should start with a bounded design and migration plan; do not begin a sweeping rewrite under a local cleanup request.

Report the structure changed, pinned contract, baseline/candidate comparison, migrated callers, reader-effort improvement, and any discarded changes. Example: extracting a CLI formatter should preserve text, ordering and exit behavior on the same fixtures; compilation and a new helper snapshot alone do not prove the command stayed equivalent.
