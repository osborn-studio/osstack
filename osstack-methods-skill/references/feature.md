# Feature

Use when the requested outcome adds or deliberately changes observable behavior. Identify an existing promise from the specification, tests, documentation or observed contract; investigate ambiguity that changes the scope. A correction to that promise uses [bug fix](bug-fix.md). A structural change that preserves that promise uses [refactoring](refactoring.md). An explanation-only request uses [investigation](investigation.md).

1. Read the affected entry point, callers, domain types and current tests. State the user-visible outcome, existing behavior to preserve and explicit non-goals. Identify a success case and an important rejected or failure case before implementing. Capture an applicable baseline for behavior that must stay unchanged. Name affected consumers and compatibility obligations before changing their contract. If a material requirement is unknown, resolve it from source or ask only for that missing decision; continue independent work.
2. Choose a small design that fits the domain. Name the inputs, outputs and ownership of state. For stateful behavior, list valid transitions and rejected transitions rather than adding unrelated flags. Compare alternatives when they change compatibility, cost or correctness; a local change does not need a design ceremony. If structural preparation is needed, apply the refactoring method under its behavior pin before adding the new behavior.
3. Record a short work checkpoint: prerequisites before parallel work; independent slices with exclusive files/resources; shared state and its owner; and the smallest useful implementation unit. Split independent artifacts before serializing shared writes. Keep coupled code under one integration owner. For a small task, this checkpoint can be one sentence; mark irrelevant dimensions as not applicable with a reason. If one worker is sufficient, record why. Use real delegation only when authorized and available; do not require a particular model, a particular multi-model review system, or recursive spawning.
4. Implement the smallest usable slice through its actual entry point. Add meaningful checks for the new result, rejected inputs and affected existing behavior. When work is delegated, supply the chosen data shape, write boundary and acceptance checks; review the resulting diff against those checks. Update all affected consumers of a shared primitive. Recheck the checkpoint if the next slice changes ownership or dependencies.
5. Verify the candidate on the surface named in step 1. A helper test can support the change but cannot prove an unexercised CLI, UI or provider path. Preserve the original failure or absent behavior when useful; label new-feature baseline absence separately from a product defect. If no suitable driver exists, use [create verification](create-verification.md). If its instructions are stale, use [maintain verification](maintain-verification.md). Missing access or builds stay blocked; wrong-surface results stay limited.
6. Review the changes for scope and compatibility. Keep small dependency-ordered units verifiable before moving to the next. Use the existing task's commit or publication authority; method selection itself does not authorize shipping. PR preparation authority does not imply approval or merge authority; preserve any user-reserved merge step. Clean up owned resources and retain evidence under [the shared rules](evidence.md).

Report the behavior delivered, important design choice, checkpoint and actual checks. Include the source/build identity, missing coverage and open decisions. For example, adding a CLI filter needs evidence that the real command filters output and still handles an empty result; a passing parser test alone does not establish either command outcome.

Adapted in OSStack wording from the pinned upstream [feature playbook](sources.md). This method adds reusable instructions, not a runtime dispatcher or a formal gate.
