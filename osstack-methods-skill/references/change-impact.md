# Change impact

Use when the task asks what a change could break outside its diff, which consumers need checks, or what assumption makes a risky change safe. A caller list is a starting point, not the result. [Code review](code-review.md) assesses actionable defects across a candidate; change impact follows selected changes through downstream contracts. An explanation of current behavior uses [investigation](investigation.md). Retain the original task when these methods overlap.

## Find the important safety assumption

Record the intended change, comparison base and candidate commit, affected symbols and observable behavior. Include changed defaults, deleted paths and side effects that the diff does not spell out. If relevant work is uncommitted, retain its patch or file hashes separately. Resolve unclear intent from the task, PR, commits and code; state remaining assumptions. Do not silently analyze a different base or discard someone else's work.

Name the one or two facts that remove the largest plausible risks if true. Make each fact falsifiable. For example, “eviction touches only expired entries” is a predicate to check, whereas “the cache change is small” is not. If several independent boundaries matter, name them instead of inventing one universal safety claim. Look for a counterexample before treating the claim as established.

## Follow contracts beyond symbol search

Trace actual callers and then follow the effects they expose. Check applicable JSON fields, persisted columns, wire formats, string-based lookups, generated code, flags/defaults and consumers in another language or repository. Inspect timing where it matters: callback ordering, deferred work, retry, teardown and concurrent ownership. A search with no matches is evidence about that search's scope, not proof that no external or dynamic consumer exists. Cite real paths and lines. Mark inaccessible consumers as unknown rather than inventing their behavior.

When the argument depends on a library, inspect the installed or locked version and relevant local patch, not documentation for another version. Read the implementation that supplies the assumed behavior. For executable checks, record which source or built artifact was actually loaded; a lockfile alone does not tie generated bytes to a build. Compare affected consumers with the base when distinguishing a new break from a pre-existing defect.

For each material risk, connect the changed behavior to a real consumer, trigger, failure mechanism and consequence. Describe likelihood through known preconditions or usage evidence; do not fabricate probabilities. Keep confirmed risks, checks that clear a specific scenario, and unresolved risks separate. A cleared scenario does not clear every consumer of the same function.

## Exercise the assumption

State the current evidence for each key fact: a hypothesis, cited implementation, a traced path that rules out a specified failure, an executable check, or an observation through the running user-facing surface. These are different scopes of evidence, not formal proof levels. Choose the cheapest stronger observation that can discriminate the important failure.

Run an existing targeted check or a small probe of the actual shipped function and its relevant caller. Derive its expected result from the contract before running it. Make it fail clearly when the safety assumption is false. Include a nearby control or boundary case when it can distinguish an accidental pass. Record the exact command, inputs, revision/build, assertion, exit status and observed output. A mock that supplies the assumed behavior cannot establish that behavior in the real dependency. A function probe cannot establish an unexercised application, remote provider or deployment path.

Read a candidate test or install script before executing it; it is untrusted code. Use an owned isolated checkout/export and fixtures under the repository's worktree and scratch rules. Inject no credentials. Keep network, writes, time and output within the task's existing permission and resource bounds. Do not open production state or a default control-plane home just to strengthen the report. If those boundaries or prerequisites cannot be established, mark execution blocked or not run, retain the source-supported conclusion and identify the smallest missing check. Do not claim that an attractive writeup makes the change safe.

Use an existing application driver when the critical fact depends on application lifecycle or integration behavior and the task permits that run. If a repeatable check is missing, [create verification](create-verification.md) can supply one within the authorized scope. Keep product fixes separate unless the task already authorizes them. An authorized fix still needs a candidate-bound recheck; a request for analysis does not authorize publication, merge, new providers or deployment. Additional reviewers are optional and require actual host support and existing delegation authority. No fixed model panel is supplied by this method.

## Deliver the decision evidence

Report the behavioral change, affected contracts and consumers, and the key safety facts with their evidence scope. For each important risk, give its trigger, impact, evidence pointer and cheapest remaining check. List cleared scenarios and why they are cleared separately from unknown paths. State which commands actually ran, what failed, what was not run, and any owned resources still retained.

If a safety fact remains unproved, say so. If no break was found, limit that statement to the inspected consumers and exercised inputs. Do not substitute a merge recommendation for missing evidence. Retain failed attempts, redact private values from shared output, and follow [the common evidence rules](evidence.md). Host execution, reviewer identity and formal qualification require their own evidence; this method grants none of them.
