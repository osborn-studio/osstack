# 改写后的题目

**将 OSStack 升级为单一工程 Agent：以机器可读行为注册表和“等待决策”闭环为首个试点，完成 Firstmate 24 项能力的原生融合、自动调度与证据化验收设计。**

## 可直接使用的任务说明

请基于 OSStack 最新 main 和固定版本的 Firstmate 原始源码，设计 OSStack 的下一代工程 Agent 架构。

用户只需要向 OSStack 描述工程目标、回答必要的产品问题，并批准超出既有权限的具体操作。OSStack 应负责拆解目标、选择并调度工作者、决定使用 Loop、合格 Graph 或调查工具、持续监督、恢复故障、验证结果和交付。用户不应承担 Agent 管理和执行器选择。

不要把“增加命令”“存在相似代码”或“测试数量增加”当作能力融合完成。每项能力必须接入默认用户旅程，并有独立可复查的行为证据。

### 输入和事实要求

1. 读取 OSStack 最新 main，记录完整 commit。区分已发布实现、main 实现、未合并修改和设计提案。
2. 固定 Firstmate 参考 commit。优先读取原始运行契约、源码、测试、issue、修复 PR、协议和实际故障材料。README 和既有报告只作为线索。
3. 对关键结论给出固定提交的来源链接和证据。未核验的内容明确标为假设或待验证。
4. 对每个复制的代码/测试片段记录来源和许可。保持 OSStack 的授权和数据边界。

### 必须交付的设计

1. 说明当前架构缺口。区分底层原语、默认行为、用户体验和真实环境资格。
2. 给出统一工程 Agent 架构。定义 Mission、Task、Run、Session、Decision、WaitObligation、Evidence 的责任和唯一权威。
3. 定义模型与确定性控制器的分工。说明事件恢复、预算、并行写冲突、权限、取消、清理、版本迁移和可观测性。
4. 给出 Loop/Graph/Scout 的自动路由规则。先检查实际能力范围、策略和证据，再比较成本和质量。能力不足时明确失败或调查。
5. 将原来的 24 项账本变成有严格 Schema 的机器可读注册表。每项包含来源、现有实现、默认触发、责任组件、依赖、不变量、缺口、验收和资格证据。
6. 设计开发时的自动移植流程：原始变更 → 行为契约 → 场景 → 适配实现 → 测试 → 独立挑战 → 证据包 → PR → 分阶段启用。不能将上游代码或模型输出自动提升为可信权限。
7. 先设计并实施一个可验证的“等待决策”纵向试点。先采纳已有 Session，覆盖发现问题、持续保留、低打扰展示、精确回答、幂等发送、未知投递、恢复执行和完成验证。初始自动派发与 Loop/Graph 选择属于下一里程碑；不得将采纳试点完成写成最终目标完成。
8. 对试点给出状态机、接口、字段、事务、故障窗口、取消竞态、宿主要求、回退和测试场景。明确区分回答已记录、已应用与任务已继续。
9. 给出可逐项执行的开发计划。每个工作包列出依赖、文件落点、验收命令、证据和交付边界。契约冻结后按不冲突的职责分工并行开发。
10. 给出专家应主动补充的工作：威胁模型、独立状态模型、属性/变异/故障测试、隐藏场景、对照实验、用户改口、长时恢复、成本与延迟、可升级性和数据保留。

### 验收与独立性

“完整融合”只对声明的版本和支持矩阵成立。24 项都必须有可追溯来源、默认工作流和验收证据。安全关键负例必须通过。未决问题不能丢失；未知投递不能自动重发；旧授权不能复用到新对象；完成证明必须对应同一候选。

请说明除作者和需求方意见之外的证据：上游行为回放、独立黑盒测试、有限状态模型、真实宿主回执、CI、变异测试、独立审查和用户对照实验。模型审计只是一项挑战输入，不能替代这些证据。

若使用 Claude Code CLI，先核验登录和请求模型的实际可用性。保存真实模型标识与原始报告。不得把不可用型号的审计标成通过。

真实环境无法验证的项目单独列出环境、责任、所缺证据和阻断范围。其他可做的开发与检查继续完成。不得把设计文档、模拟器通过或本地单元测试通过写成生产可部署。

### 输出格式与本轮边界

先交付详细设计、注册表、试点规格、实施计划、原始材料索引和验收矩阵。本轮设计包完成后，明确列出已实际执行的检查和后续运行时实现工作。后续实施依计划交付可审查 PR。

正文使用清晰中文，并为接口、稳定术语和核心说明提供英文对应。采用 OSStack 的 ASD-STE100-inspired 写作原则：短句、固定术语、先条件后操作、明确结果与未知处理。不宣称完整标准合规。
