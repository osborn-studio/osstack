## 3. 剩余问题

### P2-D（条件性，文档/运维）被拒绝的托管升级留下的持久 fence，与永久 hold 叠加

- **事实依据**
  - `resolveAuthority` 在任何停服动作之前发布 `upgrade-operation.json`（port:74）。
  - 协调器失败路径不清除它。`close()` 的注释和测试 :194 都表明 fence 在任何失败后保留。
  - 存在 operation 而无匹配 permit 时，托管启动抛 `upgrade_start_blocked`（native.test:107-108）。
- **反例**
  1. v47 home 有 committed-unknown hold，操作员发起托管升级。
  2. `doDrain` 在 stop 前以 `upgrade_unknown_actions` 拒绝。journal 进入 `recovery_required`，fence 保留，daemon 仍运行。
  3. 操作员按指南用 `daemon.resume` 恢复，一切看似正常。
  4. 之后该 daemon 崩溃或主机重启。launchd 拉起时被 fence 阻断。
  5. 唯一的受支持恢复是 `reconcileForward`。服务为 absent 时它走 `holdStoppedHome → lockHomeDatabase`，hold 仍在，再次抛 `upgrade_unknown_actions`。
  6. 结果：该 home 在托管路径下无法启动，也无法被 reconcile。
- **性质**
  - 这是可用性问题，不是安全问题。没有重发，也没有伪造证据。
  - fence 持久化是既有协调器行为，graph hold 同样适用。区别是 graph hold 会自行消失，而 committed-unknown hold 可能永久存在。
  - 指南的"放弃升级"恢复步骤没有提到 fence 和 `recovery_required`。
- **最小修复（文档即可）**
  - 在中英文指南 §"Upgrade, rollback…" 增加一段，说明：
    - 被拒绝或中止的托管升级会遗留 operation fence 和 `recovery_required` journal。
    - 在 fence 清除前，该 home 的托管重启可能被阻断。
    - 对存在永久 hold 的 home，不要发起托管升级。
    - 写明实际可用的 fence 处置方式，若没有就明说没有。
- **可选加固（不要求）**：在发布 fence 之前，用只读连接预检 `engineeringUpgradeHolds`，让这类拒绝不留下 fence。
- **降级条件**：若 `complete()` 或等价命令是受支持的操作员入口，且 `publishPrivate` 允许后续计划覆盖旧 fence，则降为 P3（仅补文档）。这两点不在我看到的文件里。

# 采纳 Session，处理等待决策

[English](engineering-session-adoption.en.md)

`osstack engineering` 用同一个入口采纳已有 Session、显示等待、提交明确回答并观察回复回合。它是显式启用的本地试点。它不启动初始 Agent，不选择 Loop 或 Graph，也不提供通用聊天界面。

完成级别固定为 `observed_turn`：OSStack 确认本 Mission 的回答所触发的回复回合已完成并落库。这个结果不是代码交付、测试通过或部署成功的证明。

当前每个精确决定只能被一个 Mission 采纳一次。即使尚未回答就取消或结束观察，这个决定也不能再采纳；系统返回 `authority_already_adopted`。已有回答取消后也不能换键重答。继续用原 Session 的正式入口处理，或由来源产生具有新身份的新决定。不要伪造 decision ID 来绕过这个限制。

## 1. 启用条件

使用已经准入、处于 `awaiting_decision` 的精确 Task、Run 和 Session。Session 必须具有非空原生会话 ID。试点仅接受默认租户、普通产品选择或允许文本输入的问题。风险批准、任务授权仍使用原来的正式批准入口。

宿主同时设置 `OSSTACK_ATTENTION=1` 和 `OSSTACK_ENGINEERING=1`。使用独立、明确的 `OSSTACK_HOME`。不要用开发 checkout 打开 `~/.osstack` 或保留的生产 home。CLI 不自动启动 daemon。

先通过已有 attention 服务建立精确仓库范围：

```sh
osstack attention watch --task TASK_ID --repo /absolute/repository --default-tenant
```

保存返回的 `scope_id`，并核对 Session 的 Task、Run 和仓库绑定。由宿主管理者准备权限文件，然后按现有运维流程重启该 home 的 daemon。试点没有自动生成宿主权限的命令。

### 宿主身份配置

`OSSTACK_ENGINEERING_AUTH_FILE` 是绝对路径。文件必须由当前宿主用户拥有，权限为 `0600`，是普通文件且不是符号链接。将它放在受信私有 home 内，且位于所有被采纳仓库之外。不要提交它。

文件结构如下。替换全部占位值。摘要和 scope 都是 64 位小写十六进制字符串。

```json
{
  "version": 1,
  "principals": [
    {
      "credential_sha256": "<SHA256 of owner credential>",
      "principal_id": "local-owner",
      "client_session_id": "owner-cli",
      "read_scopes": ["<scope_id>"],
      "write_scopes": ["<scope_id>"],
      "stop_scopes": ["<scope_id>"],
      "operator_scopes": []
    },
    {
      "credential_sha256": "<SHA256 of separate operator credential>",
      "principal_id": "local-stop-operator",
      "client_session_id": "operator-cli",
      "read_scopes": ["<scope_id>"],
      "write_scopes": [],
      "stop_scopes": ["<scope_id>"],
      "operator_scopes": ["<scope_id>"]
    }
  ]
}
```

使用密码学随机的独立凭据。通过受信、仓库外的渠道将原始凭据传给客户端环境变量 `OSSTACK_ENGINEERING_CREDENTIAL`。CLI 只读这个环境变量；它不从权限文件挑选账号。不要把凭据放到命令参数、请求 JSON、日志、报告或仓库里。宿主文件只存 SHA-256 摘要。宿主在每次请求及首次派发前重新读取权限，撤销不会依赖旧缓存。

仅轮换 `credential_sha256`，同时保留相同 principal/client 及权限，不会撤销这个主体已经接受、仍待首次派发的回答。要阻止派发，撤销对应 write grant 或删除该 principal/client 授权行。宿主在派发前重读主体授权，不把凭据哈希变化等同于撤权。保留独立的 read + stop operator 恢复通道。

这是受信进程 profile。权限文件不能隔离同一 UID 下的恶意 Worker。旧的本地 socket 接口（例如 `session.send`、`attention.answer`、`attention.abandon-receipt`、`task.cancel`）仍可按其原有权限规则操作同一 Session；engineering 凭据不覆盖这些入口的授权。所有本地调用者必须可信。试点未因此获得生产隔离资格。

## 2. 完成一次回复观察

以下命令在同一个私有 home、同一个客户端身份下执行。每个 `--request` 或 `--action` 都是调用者保存的幂等键。发生超时后，重试原请求与原键；不要换键猜测结果。

`action_id` 使用同一 home 的 attention 全局命名空间，多个主体和旧命令共享它。每次新回答生成并保存一个全局唯一 UUID，或使用真实 Mission UUID 加后缀（如 `真实MissionUUID:answer-001`）。不能让不同 Mission 都使用裸 `answer-001`。`request_id` 则在 principal/client 范围内唯一。

```sh
osstack engineering adopt \
  --scope SCOPE_ID --task TASK_ID --run RUN_ID --session SESSION_ID \
  --goal "确认本次兼容性选择的回复回合" --request adopt-001 --json

osstack engineering observe --mission MISSION_ID --json > "$OSSTACK_HOME/mission-view.json"
```

读取这个观察文件中的问题、明确选项 ID、Mission revision、Wait ID 和状态。文件保存了短期交互 token。保护这个文件，不要提交它。随后回答明确选项。下列 UUID 只生成一次，重试和查询必须复用保存的 `ANSWER_ID`：

```sh
ANSWER_ID="$(node -p 'require("node:crypto").randomUUID()')"
osstack engineering decide --observation "$OSSTACK_HOME/mission-view.json" \
  --wait WAIT_ID --action "$ANSWER_ID" --choice CHOICE_ID --json

osstack engineering observe --mission MISSION_ID --json
```

对于允许原文输入的问题，用 `--text "原始回答"` 代替 `--choice`。两者不能同时提供。系统不把“继续”自动猜成某个选项；文本也不能批准风险动作。

`--observation` 使用文件中原封不动的 Mission revision、问题引用和 token。CLI 不会在提交前偷偷刷新版本。宿主重新核对来源、身份、权限和过期时间。

状态必须按证据理解：

| 状态或事实 | 含义 |
|---|---|
| 回答已记录 / reserved | 已持久预留回答；尚未证明 Worker 执行 |
| dispatch_committed | 已承诺这一次派发；结果不明时不能自动再发 |
| applied | 整个回复回合已完成并落库；不只是传输接收 |
| delivery_unknown / needs_reconciliation | 证据不足；保留原回执与责任 |
| Mission completed + ObservationProof | 本次回答的精确回合已确认，当前没有新决定、未清义务、未决副作用或取消意图 |

若回复又提出决定，重新 `observe` 并处理新 Wait。较早的 Run 终态、普通 `done` 文本或 Session 空闲不能单独使 Mission 成功。

若原回答回合已完成，但用户在下一次观察归约前又推进了一个人工 turn，最新 turn 就不再是原回答回合；原 Mission 可能保持 `observing`。先查询原 action 回执并核对原 Session 的回合记录。确认不再需要本 Mission 的观察后，可以明确 `end-observation`。不要因此重发原回答或伪造完成状态。

## 3. 暂缓、取消与结束观察

暂缓只改变重查安排。它不提供回答或执行权限。

```sh
osstack engineering defer --observation "$OSSTACK_HOME/mission-view.json" \
  --wait WAIT_ID --request defer-001 \
  --revisit-at 2026-10-26T12:00:00Z --reason "等待产品输入"

osstack engineering cancel --mission MISSION_ID --revision REVISION \
  --request cancel-001 --reason "停止本次工作"

osstack engineering end-observation --mission MISSION_ID --revision REVISION \
  --request end-001 --reason "不再观察此回复"
```

`cancel` 持久记录停止意图，并通过独立停止通道请求中止。未知回答不会阻塞它。`stop_requested` 或 `stop_unknown` 都不是停止证明。在途动作可能仍然完成。

`end-observation` 结束本 Mission 的观察，阻止其后续首次派发。它不停止 Worker，不声称成功，也不抹去 committed/unknown 回执。原 attention 对账责任和会话发送守卫仍然有效。 若原回答仍在等待仓库 writer 准入，且持久证明确认它已是 `cancelled_before_dispatch`，宿主会释放这条尚未开始的排队工作。此处理不向已 committed 的 Worker 发送中止。

对已证明未派发的取消，原回答的同键、同正文重放返回 `cancelled_before_dispatch`；改变原正文返回 `action_conflict`。Mission 终结后，换新 action_id 再回答返回 `mission_terminal`。旧 `session.send` 重放这条已取消消息时使用错误码 `cancelled_original_answer`。这些结果都不允许恢复或替换原回答。

| 操作 | 当前权限要求 |
|---|---|
| adopt | scope read + write；记录不可变 owner |
| decide / defer / dispose_wait | 同一 owner + 当前 read + write |
| cancel | 当前 scope read + 独立 stop，且是 owner 或显式 scope-stop operator |
| end-observation | owner + read；或 operator + read + stop |

其他 writer 不能接管 owner。write 不隐含 stop。owner 写权被撤销后，只要 read 与独立 stop 权仍有效，就可取消。read 权被撤销时不能读取或操作这个 Mission；另行认证的 operator 负责恢复处置。凭据整体撤销后由另行认证的 scope-stop operator 恢复处置。

## 4. 对账

查询原动作。查询不会重新发送：

```sh
osstack engineering reconcile --kind query_action \
  --mission MISSION_ID --action "$ANSWER_ID" --json
```

如果用户已在原会话处理问题，且旧 Wait 没有关联回答 action、没有未知在途副作用，可以明确撤出旧观察义务。先读取新快照，再提交：

```sh
osstack engineering observe --mission MISSION_ID --json > "$OSSTACK_HOME/mission-view.json"
osstack engineering reconcile --kind dispose_wait \
  --observation "$OSSTACK_HOME/mission-view.json" --wait WAIT_ID --request dispose-001 \
  --disposition human_answered_out_of_band --reason "已在原会话明确处理"
```

另一个处置值是 `no_longer_relevant`。处置绑定精确旧 Wait 和当前观测摘要，是用户授权的观察目标调整。它不产生 applied、停止证明或新的执行权限。有关联回答的 Wait 必须查询原 action 或取消，不能用人工声明清除未知副作用。

## 5. 接口与限制

所有命令都接受 `--input FILE`，用严格请求 JSON 代替其余业务参数；可同时使用 `--json`。文件上限为 1 MiB，必须是普通文件且不是符号链接。未知字段、重复参数和 `actor`/权限声明会被拒绝。协议 Zod 源码和已生成 JSON Schema 位于 `packages/protocol/src/engineering.ts` 与 `packages/protocol/schemas/engineering-*.schema.json`。

以 `--` 开头的文本值（例如 `--help`）必须放入 `--input FILE` 的完整请求 JSON；把 `answer` 写为 `{"kind":"text","text":"--help"}`。不要把这段 JSON 当作完整请求。普通 `--text -h` 可用，但 `--text --help` 会被识别为缺失参数。

`observe` 的 `--cursor` 是事件序号，`--limit` 为 1–100。检查返回的 cursor、has_more 与未决 Wait；增量事件不是完整等待视图的替代。保存含 token 的 JSON 后应限制文件权限。

| 错误 | 下一步 |
|---|---|
| permission_denied | 让宿主管理者核对当前身份与精确 scope 权限；不要在 JSON 中伪造 actor |
| draining | 宿主暂停新工作；读取、查询和已授权停止仍可用。若升级已中止，按下文核对后恢复接收，不能换键绕过 |
| dispatch_gate_required | 原回答须由统一派发门执行；保留原 action，通过工程入口查询，不经旧 session.send 绕过 |
| dispatch_inconsistent | 派发阶段、消息或取消证明不一致；停止新增写入，保留证据交由宿主操作员调查，不手改账本 |
| stale_decision / source_changed | 重新观察；先查询原 action，确认没有已接受副作用后再提交新决定 |
| action_conflict / action_id_conflict | 保留原键和原正文；不同意图使用独立新请求 |
| delivery_unknown | 查询原 action；不要换键重发 |
| signed_approval_required | 使用该风险/任务的正式批准入口 |
| executor_not_qualified | 检查默认租户、Session 状态、原生 ID 与支持的 Adapter profile |
| not_dispatched_use_cancel | 取消严格未派发预留；不要把它伪装成未知已发送 |
| cancelled_original_answer | 原消息已明确取消且未派发；查询原回执，不换键重发 |
| authority_already_adopted | 该精确决定已被采纳；包括无回答就取消/结束观察的情况。使用原 Mission/Session 入口 |
| budget_exhausted | 宿主或 Mission 的持久上限已达到；检查账本，不改库重置。当前 home 累计最多 1000 个 Mission，包含终态记录 |
| engineering_busy | 待派发槽已满；稍后重试未改变的原请求，读取和停止仍可用 |
| mission_terminal | Mission 已终结；读取现有结果，不把重试变成新的目标或回答 |
| interaction_expired | 先查询原 action；未接受的回答需重新 observe 获取当前 token，再提交明确的新请求 |
| interaction_mismatch | 核对 principal/client 和原观察文件；不得手工拼接 token、Wait 或问题引用 |
| durability_required | 实际 daemon 写连接没有验证为 synchronous=FULL；修正宿主配置，不绕过持久性检查 |
| stop_attempt_budget_exhausted | 本 Mission 已接受 8 次停止尝试；原停止意图仍保留。查询原回执，交由宿主操作员处理，不能换键绕过上限 |

宿主同时最多运行 16 个内存中的派发尝试，每页 watchdog 最多检查 16 个 reserved action 和 16 个活跃 Mission。回复有 5 分钟宿主 deadline；到期请求中止，不代表进程已停止。每次暂缓最多产生一个提醒事件，可通过 `observe` 读取；试点不发送外部通知。

每个 home 最多存储 1,000 条 Mission，每个 Mission 最多 64 个 Wait。每个 Mission 最多 256 个一般控制请求。取消和结束观察独立于此计数；取消另有每个 Mission 最多 8 次的停止尝试上限，包含第一次。每次尝试保留原停止意图，只面向本 Mission 尚未解决的原 committed 消息。相同请求重放不增加计数。结束观察是单次终结操作。交互令牌五分钟到期，每个 Mission 最多保留 32 个活跃令牌。遇到 `budget_exhausted` 或 `stop_attempt_budget_exhausted` 时，不得删除未解决的证据来绕过限制。查询既有回执，并由主机操作员核对额度。

`completed` 和 `failed` 是不可逆的终态。新的 cancel 或 end-observation 请求返回 `mission_terminal`，不会改写结果或中止同 Session 后续的手工指令。已接受的相同请求仍可只读重放。结束观察后若仍有本 Mission 的 committed 未决消息，独立停止通道可在上述停止额度内请求中止。

`cost_evidence` 明确返回 `status: unknown` 和 `hard_cap_enforced: false`。试点不核销 Provider 用量，不把缺失计量当作零。5 分钟宿主 deadline 不是 token 或费用硬上限。真实编程回复可能超过这个期限；到期中止可能留下不确定回执和部分工作区改动。此 profile 尚不适合不设时长边界的长回合任务。

### 关闭功能后的处理

关闭 `OSSTACK_ENGINEERING` 不会删除派发阶段或释放 Session 守卫。已有 `reserved` 行仍会阻止新的手工指令；旧 `abandon-receipt` 会要求先取消。工程入口关闭时不能通过它取消，因此须在相同 home 重新启用 `OSSTACK_ENGINEERING=1` 与 `OSSTACK_ATTENTION=1`，使用有效凭据查询并处理原 action，然后再关闭。不要改写或删除数据库回执来解锁。已 committed/unknown 的动作仍需原有对账，不能因重新启用而重发。

### 升级、回退与恢复服务

schema 47 是数据库迁移边界。迁移完成后，只支持旧 schema 的 binary 不能打开这个 home。不能只退回旧 npm 版本或替换 binary；本试点没有受支持的数据库降级/自动回退通道。备份也不等于已获得回退许可：还须保留迁移后的动作和外部副作用证据。

升级前会检查 `attention_dispatch_holds`。只有原 committed 消息已经 `applied`，或完整证明确认 `cancelled_before_dispatch`，才能清除相应 hold。committed 但未 applied 的消息持续阻止升级；failed、unknown、`abandoned_unknown` 回执、结束观察和关闭功能均不能清除它。对于没有原 applied 证明的失败或未知动作，这个限制可能无限期保留。当前试点没有自动解除它的受支持流程。保留原 home、原账本和可用副作用证据，等待单独设计并审核的离线处置方案；不要手工修改 phase、消息、回执或 schema version，也不要删除数据库来强制升级。

托管升级在 `resolveAuthority` 阶段就写入持久的 `upgrade-operation.json`，早于 drain 和安装。已有 hold 时不要发起托管升级。若它随后因未决 hold 失败，operation fence 和升级 journal 会保留，状态需要恢复处置（`recovery_required`）。`daemon.resume` 只恢复仍存活进程的接收状态，不删除该 fence；今后的托管重启可能被 `upgrade_start_blocked` 拒绝。对 committed 未知动作的持续 hold，现有 upgrade reconcile 也不能自动解决。本试点没有针对这种失败的受支持 fence 清除或操作员放行流程。保留 fence、journal 和原 home，等待单独审核并实现的恢复方案；不要手改或删除这些文件，不要调用不存在的 complete/force-clear 命令。

`daemon.drain` 即使返回 `drained: false`，daemon 仍处于 draining 状态。新的任务和会话写入会被拒绝；升级中止不会自动恢复接收工作。先确认没有安装、重启或其他维护仍在进行，再查询 hold。仍是严格未派发 reserved 的回答可在 draining 状态下显式取消；已经 committed 的未知动作不能据此释放。

如果决定放弃本次升级并继续运行当前版本，由受信宿主管理者调用 `daemon.resume` RPC，然后核对 `osstack health` 的 `result.draining` 为 `false`。本版没有 `osstack daemon resume` 或通用 `osstack rpc` 子命令。下面的 Node 命令使用现有本地 socket RPC；它不打开数据库。必须先把 `OSSTACK_SOCKET` 换成启动日志中该 home 的精确绝对 socket 路径，并保持 `OSSTACK_HOME` 指向该 home：

```sh
export OSSTACK_SOCKET=/absolute/path/from-daemon-startup.sock
node --input-type=module <<'NODE'
import { connect } from 'node:net';
import { isAbsolute } from 'node:path';
const path = process.env.OSSTACK_SOCKET;
if (!path || !isAbsolute(path)) throw Error('Set OSSTACK_SOCKET to the exact absolute daemon socket path');
const socket = connect(path);
let bytes = Buffer.alloc(0), done = false;
const fail = message => { if (done) return; done = true; clearTimeout(timer); socket.destroy(); console.error(message); process.exitCode = 1; };
const timer = setTimeout(() => fail('daemon.resume timed out'), 5000);
socket.on('error', error => fail(error.message));
socket.on('end', () => { if (!done) fail('Incomplete RPC response'); });
socket.on('connect', () => {
  const body = Buffer.from(JSON.stringify({ id: 1, method: 'daemon.resume' }));
  const header = Buffer.alloc(4); header.writeUInt32BE(body.length);
  socket.write(Buffer.concat([header, body]));
});
socket.on('data', chunk => {
  bytes = Buffer.concat([bytes, chunk]);
  if (bytes.length < 4) return;
  const size = bytes.readUInt32BE(0);
  if (size > 1048576) return fail('RPC response exceeds 1 MiB');
  if (bytes.length < size + 4) return;
  try {
    const response = JSON.parse(bytes.subarray(4, size + 4).toString('utf8'));
    if (response.id !== 1 || response.ok !== true || response.result?.draining !== false) throw Error('Resume was not confirmed');
    done = true; clearTimeout(timer); socket.end(); console.log(JSON.stringify(response));
  } catch (error) { fail(error.message); }
});
NODE
osstack health
```

恢复接收工作会让符合条件的队列继续调度，必须先处理不希望执行的 reserved 回答。`daemon.resume` 不解除 upgrade hold，不证明未知动作已停止，也不是数据库回退。若磁盘等健康条件仍不满足，健康检查可能再次进入 draining。以上 RPC 属于现有受信本地宿主接口，并非 engineering 凭据授权接口。

尚需独立验证：真实 Provider 回答、物理断电与文件系统持久性、跨重启的进程域停止证明、恶意同 UID Worker 隔离、非默认租户、远程宿主。单元测试、完整测试和模型审计不能替代这些资格。

完整规格见[修订后的运行时契约](../design/2026-10-25-engineering-agent/runtime-contract-v2.md)与[试点场景](../design/2026-10-25-engineering-agent/pilot-scenarios.json)。

# Adopt a Session and handle a waiting decision

[中文](engineering-session-adoption.md)

`osstack engineering` provides one entry to adopt an existing Session, inspect waits, send an explicit answer, and observe its reply turn. This local pilot requires explicit enablement. It does not start an initial Agent, select Loop or Graph, or provide a general chat interface.

The completion level is `observed_turn`. OSStack confirms that the reply turn caused by this Mission's answer completed and was stored. This result does not prove code delivery, passing checks, or successful deployment.

An exact decision can currently be adopted by only one Mission, once. This remains true if observation ends or is cancelled before any answer. A later adoption returns `authority_already_adopted`. A cancelled answer cannot be replaced with a new key. Continue through the original Session endpoint, or handle a new decision with a new source-issued identity. Do not fabricate a decision ID to bypass this limit.

## 1. Enable the pilot

Use an exact, admitted Task, Run, and Session. The Session must be `awaiting_decision` and have a nonempty native session ID. The pilot accepts only the default tenant and ordinary product choices or questions that allow text input. Risk and task authorization still use their existing approval endpoints.

The host sets both `OSSTACK_ATTENTION=1` and `OSSTACK_ENGINEERING=1`. Set an explicit, isolated `OSSTACK_HOME`. Do not open `~/.osstack` or a reserved production home from a development checkout. This command does not start a daemon.

Use the existing attention service to establish the exact repository scope:

```sh
osstack attention watch --task TASK_ID --repo /absolute/repository --default-tenant
```

Save the returned `scope_id`. Check the Session's Task, Run, and repository binding. The host operator prepares the authority file, then restarts that home's daemon with the existing operations procedure. The pilot has no command that automatically grants host authority.

### Host identity configuration

`OSSTACK_ENGINEERING_AUTH_FILE` is an absolute path. Its file must belong to the current host user, have mode `0600`, and be a regular file, not a symbolic link. Keep it in a trusted private home and outside every adopted repository. Do not commit it.

The file has this structure. Replace all placeholders. Digests and scopes are 64 lowercase hexadecimal characters.

```json
{
  "version": 1,
  "principals": [
    {
      "credential_sha256": "<SHA256 of owner credential>",
      "principal_id": "local-owner",
      "client_session_id": "owner-cli",
      "read_scopes": ["<scope_id>"],
      "write_scopes": ["<scope_id>"],
      "stop_scopes": ["<scope_id>"],
      "operator_scopes": []
    },
    {
      "credential_sha256": "<SHA256 of separate operator credential>",
      "principal_id": "local-stop-operator",
      "client_session_id": "operator-cli",
      "read_scopes": ["<scope_id>"],
      "write_scopes": [],
      "stop_scopes": ["<scope_id>"],
      "operator_scopes": ["<scope_id>"]
    }
  ]
}
```

Use separate, cryptographically random credentials. Provision each raw credential through a trusted channel outside the repository into the client environment variable `OSSTACK_ENGINEERING_CREDENTIAL`. The CLI reads that variable only. It does not select a principal from the authority file. Do not place credentials in command arguments, request JSON, logs, reports, or the repository. The authority file stores SHA-256 digests only. The host reloads grants on each request and before first dispatch; revocation does not depend on a stale cache.

Rotating `credential_sha256` while retaining the same principal/client and grants does not revoke that principal's accepted answer awaiting first dispatch. To block dispatch, remove its write grant or its principal/client authority row. The host rechecks principal authority before dispatch; a changed credential hash is not grant revocation. Keep a separately authenticated operator with read + stop authority for recovery.

This is a trusted-process profile. A token file does not isolate a hostile Worker with the same UID. Existing local socket endpoints, including `session.send`, `attention.answer`, `attention.abandon-receipt`, and `task.cancel`, can still operate on the same Session under their original authority rules. Engineering credentials do not replace those rules. Every local caller must be trusted. This pilot does not establish production isolation qualification.

## 2. Observe one reply

Run these commands with the same private home and authenticated client. Save every `--request` or `--action` idempotency key. After a timeout, retry the unchanged request with the same key. Do not change the key to guess the outcome.

`action_id` uses the home's global attention namespace, shared by all principals and legacy commands. Generate and save a globally unique UUID for each new answer, or use its actual Mission UUID with a suffix such as `actualMissionUUID:answer-001`. Do not reuse plain `answer-001` across Missions. `request_id` is unique within the principal/client pair.

```sh
osstack engineering adopt \
  --scope SCOPE_ID --task TASK_ID --run RUN_ID --session SESSION_ID \
  --goal "Observe the reply to this compatibility decision" --request adopt-001 --json

osstack engineering observe --mission MISSION_ID --json > "$OSSTACK_HOME/mission-view.json"
```

Read the question, explicit choice IDs, Mission revision, Wait ID, and state in this file. The file contains a short-lived interaction token. Protect the file and do not commit it. Send an explicit choice. Generate the following UUID once. Preserve `ANSWER_ID` for retries and queries:

```sh
ANSWER_ID="$(node -p 'require("node:crypto").randomUUID()')"
osstack engineering decide --observation "$OSSTACK_HOME/mission-view.json" \
  --wait WAIT_ID --action "$ANSWER_ID" --choice CHOICE_ID --json

osstack engineering observe --mission MISSION_ID --json
```

For a question that allows original text, use `--text "original answer"` instead of `--choice`. Do not supply both. The system does not map “continue” to an assumed choice. Text does not authorize a risk action.

`--observation` uses the exact Mission revision, decision reference, and token in the saved file. The CLI does not silently refresh them before submission. The host checks current source identity, grants, and expiry again.

Interpret each state by its evidence:

| State or fact | Meaning |
|---|---|
| Answer recorded / reserved | The answer reservation is durable. Worker execution is not yet proven. |
| dispatch_committed | This dispatch is committed. An unknown result cannot cause an automatic resend. |
| applied | The full reply turn completed and was stored. This is more than transport acceptance. |
| delivery_unknown / needs_reconciliation | Evidence is incomplete. The original receipt and responsibility remain. |
| Mission completed + ObservationProof | The exact reply turn is confirmed, with no new decision, unresolved wait, unknown effect, or cancellation intent. |

If the reply asks a new question, observe again and handle the new Wait. An older terminal Run, plain `done` text, or an idle Session cannot independently complete this Mission.

If the original answer turn completed but a person advances another manual turn before the next observation refresh, the latest turn no longer matches that answer. The original Mission can remain `observing`. Query the original action receipt and inspect the Session turn records. If this Mission no longer needs observation, explicitly use `end-observation`. Do not resend the answer or invent a completed state.

## 3. Defer, cancel, and end observation

Deferral only changes the recheck schedule. It does not answer or grant permission.

```sh
osstack engineering defer --observation "$OSSTACK_HOME/mission-view.json" \
  --wait WAIT_ID --request defer-001 \
  --revisit-at 2026-10-26T12:00:00Z --reason "Waiting for product input"

osstack engineering cancel --mission MISSION_ID --revision REVISION \
  --request cancel-001 --reason "Stop this work"

osstack engineering end-observation --mission MISSION_ID --revision REVISION \
  --request end-001 --reason "Stop observing this reply"
```

`cancel` stores a stop intent and requests an abort through an independent stop path. An unknown answer does not block it. Neither `stop_requested` nor `stop_unknown` proves termination. An action already in flight can still complete.

`end-observation` ends this Mission's observation and prevents its later first dispatch. It does not stop the Worker, claim success, or erase committed/unknown receipts. The original attention reconciliation responsibility and Session send guard remain active. If the original answer is still waiting for repository writer admission, the host releases that queued work only after durable proof confirms `cancelled_before_dispatch`. This releases work that never started; it does not abort a committed Worker.

When cancellation proves that dispatch never occurred, replay of the original answer with the same key and payload returns `cancelled_before_dispatch`. A changed payload returns `action_conflict`. A new action_id submitted after the Mission ends returns `mission_terminal`. The legacy `session.send` endpoint returns the error code `cancelled_original_answer` for replay of that cancelled message. None of these outcomes permits reopening or replacing the original answer.

| Operation | Current authority required |
|---|---|
| adopt | Scope read + write; records an immutable owner |
| decide / defer / dispose_wait | That owner with current read + write |
| cancel | Current scope read + independent stop, and either the owner or an explicit scope-stop operator |
| end-observation | Owner with read authority, or operator with read + stop |

Other writers cannot replace the owner. Write authority does not imply stop authority. An owner can still cancel after write revocation if read and independent stop remain valid. Read revocation prevents Mission access; a separately authenticated operator provides recovery. If the whole credential is revoked, a separately authenticated scope-stop operator provides recovery.

## 4. Reconcile

Query the original action. This query does not resend it:

```sh
osstack engineering reconcile --kind query_action \
  --mission MISSION_ID --action "$ANSWER_ID" --json
```

If a person handled the question in the original Session, and the old Wait has no answer action or unknown effect in flight, explicitly remove that observation obligation. First read a fresh snapshot:

```sh
osstack engineering observe --mission MISSION_ID --json > "$OSSTACK_HOME/mission-view.json"
osstack engineering reconcile --kind dispose_wait \
  --observation "$OSSTACK_HOME/mission-view.json" --wait WAIT_ID --request dispose-001 \
  --disposition human_answered_out_of_band --reason "Handled in the original Session"
```

The other disposition is `no_longer_relevant`. Disposal binds the exact old Wait and current observation digest. It is an authorized change to the observation goal. It does not create applied evidence, termination evidence, or execution authority. A Wait with an answer action must use receipt query or cancellation; a human statement cannot clear unknown effects.

## 5. Interface and limits

Every command accepts `--input FILE` instead of its business flags. `--json` can be used with it. The request must be strict JSON in a regular, non-symlink file of at most 1 MiB. Unknown fields, duplicate flags, and `actor` or authority claims are rejected. Zod definitions and generated JSON Schemas are in `packages/protocol/src/engineering.ts` and `packages/protocol/schemas/engineering-*.schema.json`.

For text that starts with `--`, such as `--help`, use `--input FILE` with the complete request JSON. Set its `answer` to `{"kind":"text","text":"--help"}`. This fragment is not a complete request. `--text -h` works; `--text --help` is rejected as a missing value.

For `observe`, `--cursor` is an event sequence and `--limit` is 1–100. Check cursor, has_more, and unresolved Waits. Incremental events do not replace the current wait view. Restrict permissions on saved JSON that contains interaction tokens.

| Error | Next action |
|---|---|
| permission_denied | Ask the host operator to check current identity and exact scope grants. Do not add an actor claim to JSON. |
| draining | The host paused new work. Read, query, and authorized stop remain available. After an aborted upgrade, use the recovery procedure below; do not bypass the pause with a new key. |
| dispatch_gate_required | The unified dispatch gate must execute the original answer. Preserve its action and query it through engineering; do not bypass the gate through legacy session.send. |
| dispatch_inconsistent | Dispatch phase, message, or cancellation evidence is inconsistent. Stop new writes and preserve evidence for host-operator investigation. Do not edit the ledger. |
| stale_decision / source_changed | Observe again. Query the old action before creating a new answer, so an accepted effect is not duplicated. |
| action_conflict / action_id_conflict | Preserve the original key and payload. Use a separate request for a distinct intent. |
| delivery_unknown | Query the original action. Do not resend with a new key. |
| signed_approval_required | Use the formal risk/task approval endpoint. |
| executor_not_qualified | Check default tenancy, Session state, native ID, and the supported Adapter profile. |
| not_dispatched_use_cancel | Cancel a proven uncommitted reservation. Do not classify it as an unknown sent message. |
| cancelled_original_answer | The original message was cancelled before dispatch. Query its receipt; do not resend with a new key. |
| authority_already_adopted | This exact decision was already adopted, including observation ended/cancelled without an answer. Use the original Mission/Session endpoint. |
| budget_exhausted | A persistent host or Mission limit was reached. Inspect the ledger; do not reset the database. This home currently permits 1000 cumulative Missions, including terminal records. |
| engineering_busy | Dispatch slots are full. Retry the unchanged request later. Read and stop remain available. |
| mission_terminal | The Mission ended. Read its outcome; do not turn a retry into a new goal or answer. |
| interaction_expired | Query the original action first. If it was never accepted, observe again for a current token and submit an explicit new request. |
| interaction_mismatch | Check the principal/client and original observation file. Do not combine tokens, Waits, or decision references manually. |
| durability_required | The actual daemon write connection is not verified as synchronous=FULL. Correct host configuration; do not bypass the durability check. |
| stop_attempt_budget_exhausted | This Mission has accepted eight stop attempts. The first stop intent remains. Query its receipt and ask the host operator to resolve it; a new key cannot bypass the limit. |

The host permits at most 16 concurrent in-memory dispatch attempts and scans at most 16 reserved actions and 16 active Missions per watchdog page. A reply has a 5-minute host deadline. Expiry requests an abort; it does not prove process termination. Each deferral produces at most one reminder event, visible through `observe`; this pilot sends no external notifications.

The pilot stores at most 1,000 Mission records per home and 64 Waits per Mission. Each Mission permits 256 general control requests. Cancellation and ending observation have separate limits: cancellation permits at most eight accepted stop attempts per Mission, including the first. Each attempt keeps the first stop intent and targets only that Mission's unresolved original committed messages. An identical replay does not consume another attempt. Ending observation is a single terminal operation. Interaction tokens expire after five minutes; a Mission retains at most 32 active tokens. Neither `budget_exhausted` nor `stop_attempt_budget_exhausted` authorizes deletion of unresolved evidence. Query the receipt and ask the host operator to inspect the limit.

`completed` and `failed` are absorbing states. A new cancel or end-observation request returns `mission_terminal`; it cannot change the outcome or abort a later manual instruction in the same Session. An accepted identical request remains available as a read-only replay. After observation ends, the independent stop path can still request abort for this Mission's unresolved committed messages within the stop-attempt limit.

`cost_evidence` reports `status: unknown` and `hard_cap_enforced: false`. The adoption pilot does not meter Provider usage or treat missing usage as zero. The 5-minute host deadline is not a token or cost limit. A real coding reply can exceed it. An abort can leave an unknown receipt and partial workspace edits. This profile is not suitable for unbounded long reply turns.

### Disable and recover

Disabling `OSSTACK_ENGINEERING` does not erase dispatch phases or release the Session guard. An existing `reserved` action still blocks new manual instructions, and legacy `abandon-receipt` requires cancellation first. The disabled engineering endpoint cannot cancel it. Re-enable `OSSTACK_ENGINEERING=1` and `OSSTACK_ATTENTION=1` for the same home, then use a valid credential to query and resolve the original action before disabling again. Do not rewrite or delete database receipts to unlock it. A committed/unknown action still requires its original reconciliation and must not be resent after re-enablement.

### Upgrade, rollback, and service recovery

Schema 47 is a database migration boundary. After migration, a binary that supports only the old schema cannot open this home. Reinstalling an older npm version or replacing only the binary is not a valid rollback. This pilot has no supported database downgrade or automatic rollback path. A backup alone does not authorize rollback: retain post-migration actions and evidence of external effects.

Upgrade checks `attention_dispatch_holds`. A hold clears only when the original committed message is `applied`, or complete proof establishes `cancelled_before_dispatch`. A committed message without applied evidence continues to block upgrade. A failed or unknown receipt, `abandoned_unknown`, ending observation, or disabling the feature cannot clear it. For a failed or unknown action without original applied evidence, the hold can persist indefinitely. This pilot has no supported automatic release procedure. Preserve the home, ledger, and available effect evidence for a separately designed and reviewed offline recovery procedure. Do not edit phases, messages, receipts, or the schema version, and do not delete the database to force an upgrade.

Managed upgrade writes a persistent `upgrade-operation.json` during `resolveAuthority`, before drain or installation. Do not start a managed upgrade while a hold exists. If an unresolved hold then blocks the upgrade, the operation fence and upgrade journal remain, and the operation requires recovery (`recovery_required`). `daemon.resume` only restores admission in the surviving process. It does not remove that fence; a later managed restart can fail with `upgrade_start_blocked`. Existing upgrade reconciliation cannot automatically resolve an indefinite hold for an unknown committed action. This pilot has no supported fence-clear or operator-release procedure for that failure. Preserve the fence, journal, and original home for a separately reviewed and implemented recovery procedure. Do not edit or delete those files, and do not invoke a nonexistent complete or force-clear command.

Even when `daemon.drain` returns `drained: false`, the daemon remains draining. It refuses new tasks and Session writes. An aborted upgrade does not automatically restore admission. First confirm that no install, restart, or other maintenance is still running. Then inspect the hold. An original reserved answer with proof that dispatch never occurred can be explicitly cancelled while draining. An unknown committed action cannot be released this way.

If you abandon this upgrade and keep running the current version, a trusted host operator must call the `daemon.resume` RPC. Then check that `osstack health` reports `result.draining: false`. This version has no `osstack daemon resume` or generic `osstack rpc` command. The following Node command uses the existing local socket RPC and does not open the database. Replace `OSSTACK_SOCKET` with the exact absolute socket path for this home from its daemon startup log. Keep `OSSTACK_HOME` set to that home:

```sh
export OSSTACK_SOCKET=/absolute/path/from-daemon-startup.sock
node --input-type=module <<'NODE'
import { connect } from 'node:net';
import { isAbsolute } from 'node:path';
const path = process.env.OSSTACK_SOCKET;
if (!path || !isAbsolute(path)) throw Error('Set OSSTACK_SOCKET to the exact absolute daemon socket path');
const socket = connect(path);
let bytes = Buffer.alloc(0), done = false;
const fail = message => { if (done) return; done = true; clearTimeout(timer); socket.destroy(); console.error(message); process.exitCode = 1; };
const timer = setTimeout(() => fail('daemon.resume timed out'), 5000);
socket.on('error', error => fail(error.message));
socket.on('end', () => { if (!done) fail('Incomplete RPC response'); });
socket.on('connect', () => {
  const body = Buffer.from(JSON.stringify({ id: 1, method: 'daemon.resume' }));
  const header = Buffer.alloc(4); header.writeUInt32BE(body.length);
  socket.write(Buffer.concat([header, body]));
});
socket.on('data', chunk => {
  bytes = Buffer.concat([bytes, chunk]);
  if (bytes.length < 4) return;
  const size = bytes.readUInt32BE(0);
  if (size > 1048576) return fail('RPC response exceeds 1 MiB');
  if (bytes.length < size + 4) return;
  try {
    const response = JSON.parse(bytes.subarray(4, size + 4).toString('utf8'));
    if (response.id !== 1 || response.ok !== true || response.result?.draining !== false) throw Error('Resume was not confirmed');
    done = true; clearTimeout(timer); socket.end(); console.log(JSON.stringify(response));
  } catch (error) { fail(error.message); }
});
NODE
osstack health
```

Resuming admission lets eligible queued work run again. First cancel any reserved answer that must not execute. `daemon.resume` does not clear an upgrade hold, prove that unknown work stopped, or roll back the database. A bad health condition, such as low disk space, can raise draining again. This RPC uses the existing trusted local host interface; it does not use engineering credential authorization.

Independent checks still required: live Provider replies, physical power loss and filesystem durability, process-domain termination across restarts, hostile same-UID Worker isolation, nondefault tenants, and remote hosts. Unit tests, the full test suite, and model audits do not replace those qualifications.

See the [revised runtime contract](../design/2026-10-25-engineering-agent/runtime-contract-v2.md) and [pilot scenarios](../design/2026-10-25-engineering-agent/pilot-scenarios.json).

# V2 决策：审计后的实施契约

状态：设计规范，尚未实现。由 Claude Code `claude-fable-5-1` 三轮挑战和宿主逐项源码核验形成。本页细化主设计与试点；冲突处理必须修改相关正文，不依赖实现者猜测。

## ADR-01：先采纳现有会话，再实现从目标自动派发

第一试点采用 `adopt_session` 模式。用户通过一个入口采纳精确的 Task/Run/Session，处理决定并观察后续结果。首个试点仅采纳当前为 awaiting_decision、具有有效普通产品选择/外部输入问题且 native_session_id 非空的 Session。它不扫描旧合同启动工作，不启动初始 Worker，不自动选择 Loop/Graph。后续 `goal_dispatch` 模式才交付“一句话目标 → 自动工程执行”。两个里程碑分别验收，不能以采纳试点完成代替最终目标。

最小 Mission 仅有身份、关联、用户目标、完成级别、状态、修订号、scope/policy 摘要及事件。step 在试点中是稳定的 Session/Run 绑定；以后增加计划时保持 step_id，变更依赖需要新的计划版本，不删除旧义务。

试点对同一来源决定实行 once-adopt：只要该精确决定已有 Mission，就不能再次采纳，返回 `authority_already_adopted`。即使原 Mission 尚未创建回答 action，用户随后 cancel 或 endObservation，也不释放此决定的采纳权威。用户可直接处理原 Session，或在真实新 turn/新问题出现后采纳新决定；不得改写 decision_id 伪造新来源。

第一试点沿用已启用 attention 的 daemon、已准入 Session 和单一默认租户。仅支持 `tenant_id IS NULL`。有租户、来源类型不支持、未启用 attention 时，在任何写入前返回 `executor_not_qualified`/`attention_disabled`，不用 `source_changed` 隐藏限制。

## ADR-02：批准合同与允许自动派发分开

旧 `contract_approvals` 行仍只有原来语义。缺少自动派发授权时，状态 approved 不能触发主控派发。不得扫描历史 approved 合同“补跑”。

后续 `goal_dispatch` 使用新的 `ControllerDispatchAuthorization`，引用原合同权威。字段包含 contract_id、contract_digest、policy_digest、repo identity、精确 argv/effect digest、issuer、dispatch_mode=`controller_once`、grant_id、expires_at。默认/旧数据为 `manual`。它不是复制合同批准结果，而是授权一个新的执行动作。

授权、一次性消费和派发 action 预留在同一持久事务中绑定。审批仍需当前有效，且宿主必须验证所有绑定。开 PR 是对外副作用，需要该仓库的具体授权；用户明确要求“开 PR”可进入既有授权流程，不要求重复确认同一已授权范围。合并和部署不由开 PR 授权推导。

## ADR-03：一个 daemon owner；三种不同版本

试点控制逻辑运行在现有 attention daemon 内。只有既有进程锁获得者可 claim `daemon_owner`。不新增 per-mission lease 表，不允许第二进程绕过进程锁抢占 owner。

| 字段 | 含义 | 检查位置 |
|---|---|---|
| daemon_generation | home 控制者代数 | 所有控制平面写入与宿主 dispatch 准入 |
| source_instance_id / source_generation | 被观察的执行器实例；不能用 daemon generation 代替 | 观察、应用/停止证据、源替换 |
| mission_revision | 用户目标与控制状态 CAS 版本 | Mission 写接口 |
| item_revision / content_hash | 已展示问题投影的精确版本与正文 | AttentionActions.reserve |
| session_version / turn_id | 原始 Session 当前状态 | 原有 Session guard |

daemon 换代不能改变原动作、原 Session 或原 Worker 的身份。新 owner 可以对账旧动作，不能以换代为由重新发送。后续多进程规划通过 RPC 进入该 daemon 的事务边界，不自行成为第二写入权威。

## ADR-04：回答版本、幂等与身份

`session_decision` 引用必须携带 scope_id、item_id、item_revision、session_id、turn_id、decision_id、source_version、content_hash。`engineering.decide.if_revision` **只表示 mission_revision**。wait_revision 不复用作 item_revision。

interaction_token 包含 principal_id、client_session_id、mission_id、mission_revision、wait_id、item_id、item_revision、content_hash、nonce 和 expires_at。请求正文必须与 token 中的绑定一致；不一致拒绝。服务端不得偷偷用当前 revision 替换旧 revision。

处理顺序：先认证并校验 actor 对该 scope 的读取权；再查 action_id。若同一 actor、scope 和 payload 的动作已存在，则只返回原动作回执，不因 token 过期产生第二次副作用。其他情况才验证 token 时效与所有当前绑定，并尝试首次预留。禁止向其他 actor 泄漏已有回执。

兼容决定：`action_id` 保留现有 attention 账本的全局唯一命名空间，跨 Mission、principal 和旧 attention 命令共享；本试点不迁移旧键，也不静默加前缀。客户端为每个新回答生成一次全局 UUID（或包含全局唯一 Mission ID 的键，例如 `MISSION_ID:answer001`），持久保存该键，并在同一回答的重放和查询中复用。不同动作复用同一键会冲突，不能因失败自动换键。`request_id` 则在认证 principal/client 范围内唯一；同一键改变操作类型或正文返回 `action_conflict`。

同一个 decision_id 的内容不允许原地改写。当前 `projectDecision` 已拒绝该冲突。问题变化必须产生新 ID 和有依据的 supersession；旧回答返回 stale_decision。即使仅投影版本变化且正文相同，也保留现有拒绝语义，返回新视图供用户重试。

`mission_events.answer_recorded` 与 reserve 在同一事务记录 actor、渠道、interaction_token 摘要、原文或受控引用、action_id、权威引用和 payload digest。它是身份与因果证据；`attention_actions/session_messages` 仍是发送与回执权威。该事件本身不能批准动作或证明投递成功。

## ADR-05：三个线性化点与独立停止通道

回答接收、执行承诺和停止请求是三个不同动作。试点以一对一扩展表在**现有回答 action**上增加持久 dispatch phase，不另造发送 outbox。具体 SQL 约束、守卫和入口规则见 ADR-11。旧行缺少 phase 时按 legacy_unknown 处理。

| 顺序 | 原子处理 | 结果 |
|---|---|---|
| T-answer | 校验身份/版本；预留现有 message；记录 answer_recorded；phase=reserved | 已收到回答，不表示已开始执行 |
| T-dispatch | 同一事务检查 Mission 未取消、授权有效、当前 daemon fence；CAS reserved→dispatch_committed | 执行意图已不可当成“未发生”；之后只允许这一次原始调用 |
| T-cancel | 持久记录 stop_intent、推进 mission revision；禁止后续 T-dispatch | 发送线程、模型调用均不是停止请求入口 |

若 T-cancel 先于 T-dispatch，宿主不调用 resume。只有统一 dispatcher 能证明 action 从未进入 dispatch_committed 时，才以原子 CAS 写 `cancelled_before_dispatch` 处置及其证明。证明绑定 action/message、phase 转换、daemon generation、stop_intent 和事务事件序号。相应扩展须显式修改现有 receipt resolution/reconcile/guard 语义，不以普通文本或通用 abandon 模拟。

若 T-dispatch 先提交，随后取消，则请求中止对应 run/worker。即使调用尚未被外部观察，也不能直接宣称未执行；保留 dispatch_committed/unknown，直到有回执。宿主可以在调用前再检查取消以减少执行，但没有证据时不能据此自动释放发送保留。

重启后，仅由新协议创建、受统一派发门保护的 reserved 行可恢复其**尚未发生的首次派发**。必须验证协议版本、原 action/message/payload、原 source identity、原 turn、当前 session.version 等于持久 reservation_version、message 仍 accepted、权限仍有效、无 stop_intent，以及独占宿主准入。旧 owner 仍可能持有写权则不准入。全部成立后才进入同一个 T-dispatch CAS；否则保持可解释的 reserved/needs_reconciliation，不换键重发。有 stop_intent 的 reserved 行只走 cancelled_before_dispatch。已有 dispatch_committed 永不自动再调用；它可能已经产生副作用，不能利用本例外恢复。旧行或绕过新 dispatcher 的入口没有资格提供“未发送”证明。

stop_intent 的权威是 C02 的 mission_events.stop_requested（request_id 唯一、绑定 mission/action/run/invocation、actor、reason 与事件序号），Mission 持久保存 stop_intent_id 引用；T-cancel 在同一事务更新它。后续 stop_requested/confirmed/unknown 的回执事件引用同一意图；模型内存不是停止权威。停止走现有 `task.cancel`/Adapter abort 路径，并补持久 stop receipt；不经 `reserveSessionInstruction`。现有 abort 是请求，不是停止证明。持续 unknown 的回答可以阻塞新回答，但不得阻塞停止、读取、查询和人工对账。

现有 `task.cancel` 仅查进程内 activeRuns，并立即返回 cancelled。新的工程入口只能将它映射成 stop_requested；重启后的 not_active 不等于进程已退出。D04 还须通过精确宿主 invocation 记录查询/请求停止。宿主不支持跨重启停止时返回 stop_unknown，不承诺能够自动终止遗留进程。

不变量是“取消之后没有新的 dispatch commitment”，而非“不可能再有任何在途副作用”。已在途动作可能完成；报告必须保留这一事实。

## ADR-06：applied 的实际含义与无循环恢复

现有 daemon 在 `executeReservedSessionTurn` 中调用 `resumeSession`，等整个回合产生成功 terminal，再由 `completeInboundTurn` 同事务写新 turn 和 message.applied。**applied 表示该回复执行回合完成并持久化，不是仅收到回答。**

承载这次回答的 resume 是 T-dispatch 的受控动作。它不以 obligation 已清除为前置条件，否则形成循环。其他依赖步骤继续受 obligation 阻塞，直到原 action 的 applied 与新 turn 等证据满足清除谓词。

UI 显示：已收到回答 → 已预留执行/正在执行（必须有可信开始证据）→ 本轮已确认完成；若出现下一个决定，则展示新决定。无开始证据时不能写“Worker 已继续”。不得在 applied 后再调用一次 resume。

延迟分别测量接收落盘、宿主准入/开始、完整执行回合。删除“applied 在 5 秒内”的隐含要求。5 秒目标只能用于健康、已准入宿主上的 dispatch 开始，不包括排队、Provider、模型和完整回合；报告分母与排除原因。

## ADR-07：停止证明与人工干预

不采纳“Worker 自持 flock + PID”作为完整静默证明。Worker 可能遗留子进程、释放锁或修改工作区内锁文件。现有 `confirmAdapterStopped` 只检查 trusted adapter 的 stopped/evidence 返回，不能独立证明任意进程树隔离。

资格证明必须绑定 host、invocation_id、source instance/generation、工作区、取消请求和 worker containment domain。宿主掌握启动与退出证据，且能拒绝旧实例再次获得该域的写权限。Linux 可由受限 cgroup/容器 job 证明域内全部进程已退出并关闭；其他宿主必须提供等效被测试的实现。仅观察到主 PID 消失不够。

试点可运行在受信、受限的实际 Adapter profile，但必须如实标注威胁模型。未证明停止的 profile 保持 unknown，禁止自动替代写者和清理。操作员可通过精确宿主证据进行人工对账；“强制忽略”不能转换为已停止。完整不可信代码模式仍要求独立权限边界。

来源 turn 前进本身也不清除旧决定。有效 supersession 必须有：绑定精确旧问题的可信人工回答/处置，或经授权的新计划明确移除该阻塞义务，且关联证据可读取。普通新消息、done 文本或仅有最新 turn 变化均不够。否则状态为 needs_reconciliation，并展示为何无法判断，而不是持续要求用户重答同一问题。

`superseded` 不自动等于“依赖已满足”。仅经授权重规划移除该依赖，或精确处置证据证明替代条件成立时，步骤才可运行。保留原义务和原因。

## ADR-08：持久性与实际迁移谱系

试点所有可授权外部执行的写事务，必须在实际 daemon 写连接上使用并读回验证 `synchronous=FULL`，且提交成功后才进入外部调用。执行 profile 不满足该要求时禁用自动继续；只读观察可用。性能变化另行测量，不静默退回 NORMAL。

接收端按 message_id 去重/查询是较高恢复等级的条件。没有该能力时使用 `stop_and_reconcile` profile：仍可保留未知、停止和查询，但不能承诺自动完成恢复。FULL 与接收端去重都不能证明任意硬件的断电行为；要对支持的文件系统与宿主做故障验证。

F51-11 的“attention 表均为未发布实验表”推断被完整源码否定：基线 main 的 migration 40 创建 daemon_owner 和 attention 表，41–43 继续演进，当前 schema 为 46。`assertMigrationLineage` 拒绝的是与当前 user_version 对应的**期望表集合不符**的历史/混合库，不是拒绝所有 attention 表。`OSSTACK_ATTENTION=1` 控制服务启用；不是另一个 DB 谱系。

新表走编号递增迁移，保留该检查。旧未知实验库不自动导入；不能 reset user_version。旧二进制遇到新 schema 可以明确拒绝，回退使用当前兼容的只读/对账工具，不保证老二进制能读写新库。

## ADR-09：资格矩阵、差分规则与自举

保留 `capabilities.json` 为设计快照，const false 防止误标启用；它不承担运行时资格验证。新增 [资格契约](qualification-contract.schema.json) 定义运行时证据记录的结构草案。Schema 验证仅检查形状，不能验证签名、证据真实性或启用资格。

每条资格绑定 capability、行为契约摘要、source manifest 摘要、目标代码摘要、OS/架构/文件系统、隔离 profile、daemon 版本、Adapter 版本、Provider/model、Executor/template。证据 bundle 包含场景 ID、候选、检查器身份/版本、结果与限制；记录 signer、有效期、撤销版本和签名。

资格记录还绑定实际 host identity、required scenario set 摘要和前置资格摘要。contract_tested 由 CI verifier 签发；host_verified 由 host qualifier 签发并引用相同代码/契约/来源/registry 的 contract_tested；journey_verified 引用同一实际宿主 profile 的 host_verified。trust store 将 signer_key_id 绑定具体公钥、允许的 issuer_role、level、能力与环境范围；签名 payload 自报的 role 不能扩大密钥权限。CI key 不能签发 host_verified。撤销状态由配置中固定的运维信任根签名发布，单调 epoch 与撤销 key/record 清单持久化；拒绝回退 epoch。离线只能使用仍在明确 freshness 窗口内的缓存；过期或无法取得可信当前状态则停止新的资格启用。Worker 和普通资格签发者不能重设该根或清空撤销状态。CI 的宿主是构建宿主，不能替代部署宿主证明；跨级只放宽这一已定义的 CI→host 身份差别，不放宽代码或契约绑定。必需场景由版本化 verifier policy 指定，签发者不能自选一个容易通过的场景集合。

由受信 CI 证据签发者和宿主资格签发者分工签名。它们不归 Worker 控制。验签器使用宿主私有 trust store；按 [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) 规范化签名 payload，拒绝未知字段、重复键、非法数值和不可接受的编码。引用的证据须取回并重算摘要。绑定不匹配、撤销、过期或证据不可达都不能升级为 enabled。

启用是计算结果：精确 profile 的要求证据均通过 + 当前未撤销的运维启用授权 + 当前任务权限。任何一个维度不足只影响相应 profile，不能用 macOS 通过代替 Linux 通过。设计文件中没有生产签名者或真实合格记录。

试点不加载该运行时注册表。它使用编译期封闭 profile 和显式开关，待真实试点证据形成后，再签发首批资格。R 系列可以并行，但不是 D08 的前提。

能力移植差分规则见 [语义差异清单](semantic-divergences.json)。只允许精确条件下的已审查差异；输出为 equivalent / allowed_divergence / fail。未知差异不能自动加入 allowlist。enqueue 已关闭、OSStack 仍待 turn 完成的不同属于保留的更严格语义。

## ADR-10：预算、选项和路由

试点硬预算只包含可由宿主控制的动作/调用次数、运行时长、并发数和提醒次数。token/费用为 observed，除非 Provider/profile 能证明确切硬上限。未知费用保留 conservative charge；已知每次最大额度时可按上限核销，无最大额度时保持 unknown 并限制新计费调用，不伪造实际用量或释放为零。

试点输入只接受明确 choice_id/选项按钮，或外部输入问题允许的原文 text。自由文本不由模型自动映射成具有授权意义的选项。产品选择有歧义时展示具体选择；不要求无歧义、已授权的每个动作都二次批准。问题与选项以不可信数据呈现，不能按敏感关键词的有无推导权限；真正权限由 gate kind、权威记录与宿主策略决定。

ExecutorEnvelope 类别引用现有 CapabilityKind，模板引用精确模板 ID/version；行为注册表引用稳定行为 ID。受信构建生成声明，实际宿主证据决定资格。影子路由只计算建议；执行器质量对照使用隔离重放/测试仓库，不对生产重复执行写动作。

首个试点前记录现有手工流程的干预基线。仅使用授权、脱敏样本；没有样本则标为待测，不编数字。用户收益指标在首条旅程就测量，不等全量实现完成再评估。


## ADR-11：派发扩展表、版本和单一入口

基线 migration 41 的 receipt resolution CHECK 只允许 abandoned_unknown，不向它塞入新枚举，不重建该表。按实施时 main 的下一个迁移号（当前基线为 46）新增 attention_dispatch_phases。该表是既有 action 的一对一状态扩展，不是第二消息队列：action_id 为主键并引用 attention_actions；message_id 唯一并引用 session_messages。额外字段为 protocol_version、phase（reserved / dispatch_committed / cancelled_before_dispatch）、source_instance_id、source_generation、original_turn_id、source_version、reservation_version、reserved_by_generation、committed_by_generation、stop_intent_id、proof_json、created_at/updated_at。空值和状态组合由 CHECK/受信 store 校验，phase 不允许倒退。

在 T-answer 外层事务内，原 reserve、扩展行和 Mission 事件一起提交。source_version 是预留前的 v；reservation_version 是 applyInbound 返回的 v+1。不得使用 replay 返回的 0 重建版本。原 Session payload 从已存 message 读取，重新核验 action/payload digest；重启不从最新 UI 文本构造新消息。正常 completeInboundTurn 写入 v+2，并在同一 completed 钩子记录精确 action/message/source/completed_turn_id/session_version 证据。

固定顺序：先以原 message_id 获得独占 Session admission；确认没有 drain/abort；在一个同步 FULL 写事务内 assertOwner、校验 scope/policy/source/version/stop_intent，并断言 attention_actions.state=reserved、attention_receipt_resolutions 中无该 message_id 的任何处置，再 CAS reserved→dispatch_committed；提交后立即把同一个 lease/controller 传给 executeReservedSessionTurn。CAS 前失败不更改 phase；释放已取得 admission。CAS 成功者持有仅本次调用可消费的内部派发许可，中间不再异步获取准入；执行器消费许可后才调用 Adapter。任何 CAS 后失败都不复原 phase、不自动再调用。

所有能调用 executeReservedSessionTurn 的路径必须检查 message 是否属于此扩展表；属于时只能凭同一个 CAS 胜出调用的内部许可进入。engineering、attention.answer、session.send 和 continuation 路径不能各自恢复它。无扩展行的旧路径保留原语义，不能获得新协议的未发送证明。当前 handleSessionSend 对既有 accepted 消息实际返回 delivery_uncertain，并未发现现有绕过漏洞；这是新增恢复路径必须守住的约束。

reserveSessionInstruction 的不确定消息守卫只额外排除由受信 dispatcher CAS 形成、action/message 绑定正确且 proof 完整的 cancelled_before_dispatch 行。reconcile 优先读取该明确处置，显示“已取消且未派发”，不能映射为 applied 或 abandoned_unknown。若同时出现 applied 与 cancelled_before_dispatch，视为一致性错误并阻断新写入。

旧入口与投影必须在 D04 同一变更中接线：AttentionActions.reconcile/recover 首先读取 phase。新协议 reserved 且无 resolution 时保持 action=reserved，不把 accepted 消息一律投影为 uncertain。cancelled_before_dispatch 映射为明确 cancelled 状态；已 committed 的实际结果继续由原 receipt 决定；存在任何 receipt resolution 时阻止首次派发，并展示相应处置，不自动重置 action 回 reserved。phase=reserved 但 action 已 uncertain/abandoned_unknown 等不一致时进入 needs_reconciliation，不能自动“修正”后派发。

既有 abandon-receipt 在受信事务内检查 phase。对 reserved 返回 not_dispatched_use_cancel，明确“尚未派发，本次未作放弃；请取消原动作”，不插入 abandoned_unknown，不改变 phase；对 cancelled 返回原取消回执。对于 committed/legacy 的未知结果保留既有受控处置语义，且此类处置永远不成为重试许可。拒绝一次 abandon 不等于已经执行取消，界面必须准确表述；用户的取消命令仍需按 T-cancel 持久提交。测试分别检查：已有 resolution 时零次派发；abandon 被拒绝时自身无写入或发送；随后 cancel 提交后永久阻止该 action 派发。不得把“拒绝了错误操作”测试成“用户已成功取消”。

取消结果按入口精确表述：`engineering.decide` 以相同 action_id 和相同正文重放原动作，或 `engineering.reconcile query_action` 查询该动作，返回状态 `cancelled_before_dispatch`；旧 `session.send` 对相同原消息的重放返回错误码 `cancelled_original_answer`；attention.answer replay 和只读视图显示同一已证明取消处置，不能再显示 delivery_uncertain。证明不完整或与 applied 矛盾时保持一致性错误，不能仅凭 phase 标签宣称未派发。committed 未确认的旧行为仍保留未知。写入和 dispatcher 共享 FULL 写事务与 owner fence，不能先在事务外检查 resolution，再在事务内盲目 CAS；只读视图不执行迁移或修复。

保留 attention_actions.item_id UNIQUE：重启继续原 reserved action，不创建第二回答。取消是该动作的终结；原 action 的同正文重放仍返回 `cancelled_before_dispatch`，改变正文返回 `action_conflict`，不能重新开启。取消或结束观察后，使用新 action_id 提交本 Mission 的新回答返回 `mission_terminal`；这与旧 `session.send` 的 `cancelled_original_answer` 是不同入口的契约。新问题、新 turn 可以产生新 action。试点不支持对同一个旧 item 再答，也不允许通过另建 Mission 重采同一决定，即使原 Mission 从未创建回答 action 也返回 `authority_already_adopted`。用户可直接处理原 Session，或在有真实新来源问题后重新采纳；不得伪造新 decision_id 绕过约束。该边界不阻塞同 Session 的其他合法新指令，也不把用户重新授权推导为旧动作未执行。

## ADR-12：Session 来源身份及版本推进

试点 source_instance_id 为带版本前缀的 SHA-256(RFC8785({session_id, native_session_id}))，native_session_id 必须非空；source_generation 固定为 1。Session ID 不复用，native ID 不原地重绑定。检测到 native ID 变化或 NULL，保留原绑定并进入 needs_reconciliation；重新采纳新源需新 Mission，不在旧 Mission 内悄悄重置。该身份不等同进程 invocation；停止证明仍须另外绑定实际 invocation/containment。

mission_revision 只在影响用户意图或有效交互的变化递增：目标/权限/计划变更、取消、人工处置、首次回答接受和 Mission 终态。纯观察新鲜度与心跳不递增；用事件序号和 observed_at 表达。wait_revision 仅在该义务的语义状态改变时递增。question identity/item revision/session version 各按其原权威更新。所有首次写动作仍核对当前原始来源，不能因 Mission revision 稳定跳过 freshness 检查。

## ADR-13：无 action 的人工干预处置

engineering.reconcile 是类型化联合：query_action 保留只读查询；dispose_wait 用于明确调整当前观察任务。后者包含 request_id、mission_id、if_revision、wait_id、if_wait_revision、disposition（human_answered_out_of_band / no_longer_relevant）、observed_turn_id、observed_snapshot_digest、note。身份从可信通道得到，要求 scope 写权及 mission.steer 授权。试点在 engineering.adopt 验证 scope 写权后，将该认证 principal 记为不可变 owner_principal_id，并授予仅此 Mission 的 steer；其他 principal 不因同 scope 写权自动获得它。试点不提供转让接口；Worker/模型不能自报该身份。每次使用仍检查当前 scope 权限未撤销，且是普通产品选择/输入义务，不是风险批准或任务授权。

服务重新读取当前 Session，核对来源身份、精确旧 item/turn 和观测快照。用户签名/认证的声明是一次目标调整，**不是机器证实回答已经送达**。无原回答 action、且不涉及未知在途副作用时，CAS 写 steering_recorded，保留旧义务为 superseded，记录“经用户授权撤出观察依赖”。不写 session_messages，不写 answer_applied，不调用 resume，不授权后续 Worker。普通操作员写权不能替代 mission.steer。

若已有 reserved/dispatch_committed/unknown action，dispose_wait 拒绝并指向 query_action、cancel 或原 receipt 的受控对账；不能用人工声明释放未知发送保留、证明停止或跳过安全审批。移除旧观察义务后仍展示新问题与未完成事项。该处置本身不构成工程完成，也不产生 observed_turn 成功证据。

## ADR-14：采纳试点的完成定义与后续工程交付

试点 completion_level 固定为 observed_turn：它只承诺记录并观察由本次回答触发的回复回合，不承诺 Run、整个工程目标或代码检查全部完成。采用这一等级时用户入口明确显示“观察回复回合”。完整 goal_dispatch 沿用主设计的工程交付等级。

成功终结要求：至少一个属于本 Mission 的原 action 已 applied；精确 action/message/source/completed_turn_id/session_version 证据已落库；当前最新 turn 正是该已证明 turn，状态 idle 或 completed；在同一归约快照中没有新决定、未清除义务、未决副作用或取消意图。此时 Mission=completed，输出独立 ObservationProof，包含上述身份和回合输出摘要，不伪造代码 candidate/test 证明。新 turn 仍 awaiting_decision 则建立新义务并继续观察；未记录对应 applied 的 idle 不能触发成功。

不采用单独以 Run terminal 判断成功的建议：基线 handleSessionStart 即使 Session 等待决定也会 finalizeRun(completed)，因此该 Run 终态可能早于采纳。Run terminal 可作关联事实，但不足以证明此次回复回合。失败映射为 failed/needs_reconciliation；unknown 保留。用户直接处理源会话、仅 dispose_wait 后没有本 Mission 的完整回复证据时，显示“已撤出旧等待，尚无本次回复回执”；用户可明确结束观察，记录 observation_ended（非成功终态），不无限等待或强迫重新回答。结束观察不等于停止 Worker，也不移除未知执行记录。未知发送仍归现有 attention receipt/daemon 对账职责管理；终结 Mission 不能使该职责消失，后续会话写入仍受原守卫约束。

若原回答已完成，但在下一次 refresh 前用户已推进后续人工 turn，最新 turn 与原回复证据不同，原 Mission 可保持 observing。用户须读取原 action 回执和 Session 回合记录；不再需要观察时可明确 endObservation，而非重发回答或强制写 completed。

D07/D08 仅验收场景清单中 delivery_stage=adopt_session 的全部条目。其余条目由命名的后续工作包验收；不能标通过或删除。第一试点并不具备生产隔离资格。


## ADR-15：取消与结束观察权限（P2 定案，2026-10-25）

Engineering 入口只接受经宿主凭据认证的 principal。客户端 JSON 的 actor、role 或权限声明不得成为权威。读、写、停止与 operator 身份分别按 scope 授权，恢复派发前重新读取当前宿主权限。

| 操作 | 允许的主体 | 限制 |
|---|---|---|
| adopt | 当前具备 scope read+write 的认证主体 | 记录不可变 owner_principal_id |
| decide / defer / dispose_wait | owner，且当前 scope read+write 有效 | 其他 writer 不能接管目标；未知发送不能经 dispose 清除 |
| cancel | owner 且独立 scope stop 权有效；或明确的 scope-stop operator | write 不是 stop；只停止已绑定的 Mission/Run/action。owner 写权被撤销后，仍有效的停止权可用 |
| endObservation | owner 且 scope read 有效；或明确 operator 且 scope read+stop 有效 | 结束观察不是停止 Worker；不是成功；不清除未知回执 |

完全撤销的凭据拒绝一切操作。恢复通道由宿主另行授权的 scope-stop operator 提供，不临时扩大其他 writer 权限。权限配置必须保留明确的停止责任人；不能把“停止不被未知发送阻塞”解释为未认证用户也可停止。

cancel/endObservation 均先验证身份和精确 scope，再处理同 principal/request/payload 的只读重放；首次写入使用 Mission revision CAS。结束观察禁止本 Mission 后续首次派发；仅严格证明未提交的 reserved action 可变成 cancelled_before_dispatch，committed/unknown 保留原 attention 责任。宿主停止回执不确实时显示 stop_unknown，绝不把权限通过当成停止成功。

本地试点凭据文件位于独立 OSSTACK_HOME，由宿主控制；只适用于受信进程环境。同 UID 恶意 Worker 的隔离没有因此得到认证。实现细节与并行边界见 [实施交接](implementation-handoff.md)。

ADR-15 clarification (implementation review): current scope read permission is a prerequisite for every Mission RPC, including cancel. Cancellation additionally requires the owner’s independent scope stop permission, or scope stop plus operator permission. Write revocation does not revoke read or stop. A stop-only principal without read is denied because the response contains Mission and receipt data. This pilot does not expose a blind-stop endpoint.


## ADR-16：schema 47 升级阻断与明确恢复边界

schema 47 迁移后，旧 schema binary 拒绝打开该 home。只替换旧 binary 或退回旧 npm 版本不是受支持回退；本试点不交付数据库 downgrade 或自动 rollback。备份不构成丢弃迁移后动作/外部副作用证据的许可。

升级只接受原消息 applied 或严格证明 cancelled_before_dispatch 的 dispatch 行。reserved、committed 未 applied、缺失或矛盾证明均形成 attention_dispatch_holds。committed 的 failed/unknown/abandoned_unknown 处置仍保留 hold；取消意图、结束观察、关闭功能和恢复 daemon 接收工作都不清除它。没有原 applied 证据的未决 committed 行可无限期阻止升级。本试点没有受支持自动解除或数据库回退通道；保留原 home、账本和外部证据，待另行审核的离线恢复方案处理，不能手改数据库绕过。

托管升级的 resolveAuthority 在 drain/安装之前写入持久 upgrade-operation.json。已有 hold 时不要发起托管升级；后续失败仍保留 operation fence 和 journal，标记 recovery_required。daemon.resume 只恢复存活 daemon 的接收状态，不清除 operation fence，后续托管启动仍可能 upgrade_start_blocked。committed 未知动作的持续 hold 也阻止现有 upgrade reconcile 完成；本试点没有针对这类失败的受支持 fence 清除/操作员放行通道。必须保留 fence、journal 与 home，待另行审核并实现的恢复方案处理；不得手改文件解除、伪造 complete 命令或声称 resume 已完成升级恢复。

升级调用 daemon.drain 会先锁存 draining，即使结果 drained=false 或升级随后中止也不自动恢复。原 reserved 可经已授权的精确 cancel 取得未派发证明；未知 committed 不能借此释放。放弃升级并继续运行当前版本前，操作员先确认无安装/重启/其他维护仍在进行，再显式调用 daemon.resume RPC，并读取 health 确认 draining=false。该动作恢复正常准入，包括符合条件的待派发工作；应先处理不应执行的 reserved。它不是清除 hold 或停止未知 Worker 的证明。持续不健康条件仍可再次触发 draining。

已核对当前 CLI：没有 osstack daemon resume 或通用 osstack rpc 子命令。现有 osstack health 可查状态；精确 socket 的单次 Node RPC 操作步骤见[中文运行指南](../../guides/engineering-session-adoption.md)与[英文运行指南](../../guides/engineering-session-adoption.en.md)。不以不存在的子命令描述恢复。以 -- 开头的业务文本通过 --input 的严格完整请求 JSON 传入，避免把文本当作选项；此方式不改变身份或授权边界。

运行错误须保留准确含义：draining 表示暂停准入，可读/查询/已授权停止仍保留；dispatch_gate_required 要求原动作通过统一派发门，不能改用旧 session.send 绕过；dispatch_inconsistent 表示 phase、message 或 proof 不一致，须保留证据并停止新写入调查。

/** Runs only with an explicit trusted port. A persisted plan never grants permission.
 * Every side effect has a durable started record; incomplete prior attempts are never replayed. */
export async function coordinateUpgrade(input: {
  journal: UpgradeJournal; plan: FrozenUpgradePlan; groupId: string; port?: NativeUpgradePort;
  nowMs?: () => number; monotonicMs?: () => number; signal?: AbortSignal;
}): Promise<UpgradeExecutionResult> {
  const plan = freezeUpgradePlan(input.plan.plan); if (plan.digest !== input.plan.digest) throw Error('upgrade_plan_digest_mismatch');
  const group = plan.plan.groups.find(g => g.group_id === input.groupId); if (!group) throw Error('upgrade_group_missing');
  const result = (state: UpgradePhase, reason: string | null = null): UpgradeExecutionResult => ({ state, plan_digest: plan.digest, group_id: group.group_id, reason });
  await input.journal.create(plan); const prior = await input.journal.status(plan.digest, group.group_id);
  if (prior.completed) return result('verified');
  if (prior.phase === 'recovery_required' || prior.records.some(r => r.phase !== 'qualification_pending')) return result('recovery_required', 'prior_attempt_requires_reconciliation');
  if (!input.port) return result('qualification_pending', 'native_updater_not_qualified');
  for (const previous of plan.plan.groups.slice(0, plan.plan.groups.indexOf(group))) {
    if (!(await input.journal.status(plan.digest, previous.group_id)).completed) return result('qualification_pending', 'preceding_group_not_verified');
  }
  const unqualifiedIdentity = group.homes.some(home => !home.identity || home.identity.home_id !== home.home_id
    || home.identity.deployment_kind !== 'npm' || home.identity.build_digest === null || home.identity.build_evidence !== 'host_manifest'
    || home.identity.database_schema > plan.plan.target.database_schema
    || home.identity.database_schema < plan.plan.target.readable_schema_min || home.identity.database_schema > plan.plan.target.readable_schema_max
    || home.observed_at_ms > plan.plan.created_at_ms || plan.plan.created_at_ms - home.observed_at_ms > 30000);
  if (plan.plan.budget.max_steps < 5 * group.homes.length + 2 || group.deployment_kind !== 'npm' || unqualifiedIdentity || group.reasons.some(reason => !['shared_consumers_not_attested', 'native_updater_not_qualified'].includes(reason)))
    return result('qualification_pending', 'plan_has_unqualified_consumers');
  const port = input.port; const now = input.nowMs ?? Date.now; const mono = input.monotonicMs ?? (() => performance.now());
  const startedAt = mono(); let steps = 0; let authority: UpgradeAuthority | undefined; let writer: UpgradeJournalWriter | undefined;
  let phase: UpgradePhase = 'preflight'; let installStarted = false; let sideEffectStarted = false; let closed = false;
  const stops: UpgradeStopLease[] = [];
  const clockCheck = () => {
    if (closed || input.signal?.aborted) throw Error('upgrade_cancelled');
    if (now() < plan.plan.created_at_ms || now() >= plan.plan.expires_at_ms) throw Error('upgrade_plan_expired');
    if (mono() - startedAt >= plan.plan.budget.max_total_ms) throw Error('upgrade_budget_exhausted');
    if (authority) {
      if (now() >= authority.expires_at_ms) throw Error('upgrade_authority_expired'); synchronous(authority.assertCurrent);
    }
  };
  const append = async (status: 'started' | 'confirmed' | 'failed', home: UpgradePlanHome | null, evidence?: unknown, evidenceRef?: string, reason?: string) => {
    if (!writer) return;
    await writer.append({ phase, status, at_ms: now(), home_id: home?.home_id ?? null, evidence_digest: evidence === undefined ? null : upgradeDigest(evidence),
      evidence_ref: evidenceRef ?? null, reason: reason ?? null });
  };
  const call = async <T>(operation: (signal: AbortSignal) => Promise<T>, mutating = false): Promise<T> => {
    clockCheck(); if (steps >= plan.plan.budget.max_steps) throw Error('upgrade_budget_exhausted'); steps += 1;
    const controller = new AbortController(); let rejectAbort!: (error: Error) => void;
    const cancelled = new Promise<never>((_, reject) => { rejectAbort = reject; });
    const abort = () => { controller.abort(); rejectAbort(Error('upgrade_cancelled')); };
    input.signal?.addEventListener('abort', abort, { once: true }); if (input.signal?.aborted) abort();
    const remaining = plan.plan.budget.max_total_ms - (mono() - startedAt);
    let timer: ReturnType<typeof setTimeout> | undefined;
    try {
      const deadline = new Promise<never>((_, reject) => { timer = setTimeout(() => { controller.abort(); reject(Error('upgrade_operation_unknown')); }, Math.max(1, Math.min(remaining, plan.plan.budget.max_step_ms))); });

      const value = await Promise.race([Promise.resolve().then(() => { clockCheck(); if (mutating) synchronous(writer!.assertCurrent); return operation(controller.signal); }), deadline, cancelled]);
      clockCheck(); return value;
    } finally { if (timer) clearTimeout(timer); input.signal?.removeEventListener('abort', abort); }
  };
  try {

    authority = { ...parsed, assertCurrent: assertCurrent.bind(resolved) }; clockCheck();
    writer = await input.journal.claim(plan.digest, group.group_id); clockCheck(); await append('started', null, parsed, parsed.authorization_ref);
    for (const home of group.homes) {
      const observation = await call(signal => port.observe(home, signal));
      const identity = DeploymentIdentitySchema.parse(observation.identity);
      if (observation.healthy !== true || upgradeCanonical(identity) !== upgradeCanonical(home.identity)) throw Error('upgrade_identity_changed');
      ref.parse(observation.receipt_ref); await append('confirmed', home, identity, observation.receipt_ref); clockCheck();
    }
    phase = 'draining';
    for (const home of group.homes) {
      await append('started', home); clockCheck(); sideEffectStarted = true;
      const lease = await call(signal => port.drain(home, signal), true); const receipt = StoppedSchema.parse(lease.receipt);
      if (receipt.home_id !== home.home_id || receipt.generation !== home.identity?.generation || typeof lease.assertHeld !== 'function') throw Error('upgrade_stop_binding');
      const frozenLease = { receipt, assertHeld: lease.assertHeld.bind(lease) }; synchronous(frozenLease.assertHeld); stops.push(frozenLease);
      await append('confirmed', home, receipt, receipt.receipt_ref); clockCheck();
    }
    const quiescent = () => { clockCheck(); for (const stop of stops) synchronous(stop.assertHeld); if (stops.length !== group.homes.length) throw Error('upgrade_all_consumers_required'); };
    quiescent(); phase = 'quiescent'; await append('confirmed', null, stops.map(s => s.receipt)); quiescent(); phase = 'snapshotting';
    for (const home of group.homes) {
      await append('started', home); quiescent(); const receipt = ReceiptSchema.parse(await call(signal => { quiescent(); return port.snapshot(home, signal); }, true));
      quiescent(); if (receipt.home_id !== home.home_id || receipt.source_generation !== home.identity?.generation) throw Error('upgrade_snapshot_binding');
      await append('confirmed', home, receipt, receipt.receipt_ref); quiescent();
    }
    phase = 'installing'; await append('started', null); quiescent(); installStarted = true;
    const installed = InstallSchema.parse(await call(signal => { quiescent(); return port.install(plan, group, signal); }, true)); quiescent();
    if (installed.plan_digest !== plan.digest || installed.installation_id !== group.installation_id || installed.version !== plan.plan.target.version || installed.build_digest !== plan.plan.target.build_digest) throw Error('upgrade_install_mismatch');
    phase = 'installed'; await append('confirmed', null, installed, installed.receipt_ref); clockCheck(); phase = 'restarting';
    for (const home of group.homes) {
      await append('started', home); clockCheck(); synchronous(stops[group.homes.indexOf(home)]!.assertHeld);
      const receipt = ReceiptSchema.parse(await call(signal => { synchronous(stops[group.homes.indexOf(home)]!.assertHeld); return port.restart(home, signal); }, true));
      if (receipt.home_id !== home.home_id || receipt.source_generation !== home.identity?.generation) throw Error('upgrade_restart_binding');
      await append('confirmed', home, receipt, receipt.receipt_ref); clockCheck();
    }
    phase = 'verifying';
    for (const home of group.homes) {
      await append('started', home); clockCheck(); const observed = await call(signal => port.observe(home, signal)); const identity = DeploymentIdentitySchema.parse(observed.identity);
      if (observed.healthy !== true || identity.home_id !== home.home_id || identity.generation === home.identity?.generation || identity.deployment_kind !== 'npm'
        || identity.version !== plan.plan.target.version || identity.build_digest !== plan.plan.target.build_digest || identity.build_evidence !== 'host_manifest'
        || identity.protocol_version !== plan.plan.target.protocol_version || identity.database_schema !== plan.plan.target.database_schema) throw Error('upgrade_version_mismatch');
      ref.parse(observed.receipt_ref); await append('confirmed', home, identity, observed.receipt_ref); clockCheck();
    }
    phase = 'verified'; clockCheck(); await append('confirmed', null);
    try { await writer.releaseVerified(); } catch { closed = true; return result('verified', 'claim_release_requires_reconciliation'); }
    closed = true; return result('verified');
  } catch (error) {
    if (error instanceof Error && error.message === 'upgrade_already_verified') return result('verified');
    const message = error instanceof Error && /^upgrade_[a-z_]+$/.test(error.message) ? error.message : 'upgrade_port_failure';
    if (!writer && message !== 'upgrade_recovery_required') {
      const status = await input.journal.status(plan.digest, group.group_id).catch(() => null);
      if (status?.completed) return result('verified', status.recovery.claim_cleanup_pending ? 'claim_release_requires_reconciliation' : null);
      return result(!status || status.phase === 'recovery_required' ? 'recovery_required' : 'qualification_pending', message);
    }
    const state: UpgradePhase = message === 'upgrade_recovery_required' || sideEffectStarted && !installStarted ? 'recovery_required'
      : !installStarted ? 'aborted_before_install' : message === 'upgrade_version_mismatch' ? 'version_mismatch' : 'recovery_required';
    phase = state; closed = true;
    // A failed journal write leaves its previous started record. Never undo an external fact or steal the claim.
    try { await append('failed', null, undefined, undefined, message); } catch { /* Caller must inspect the retained claim and previous record. */ }
    return result(state, message);
  }
}

  private async lockHomeDatabase(home: string, homeId:string): Promise<void> {
    const path = join(home,'state.db'); if (!existsSync(path)) throw Error('upgrade_database_missing');
    const { default: Database } = await import('better-sqlite3'); this.assertOperation();
    const db = new Database(path,{ fileMustExist:true,timeout:0 }); const release=this.stopLocks.get(homeId)!;
    try {
      db.exec('BEGIN EXCLUSIVE');
      const schema=db.pragma('user_version',{simple:true}) as number;
      // Deliberately qualified, not CURRENT_SCHEMA_VERSION: a future migration
      // needs its own stopped-home compatibility review before this gate opens.
      if(schema<33||schema>47)throw Error('upgrade_schema_unqualified');
      const tables = new Set((db.prepare("SELECT name FROM sqlite_master WHERE type='table'").all() as {name:string}[]).map(r=>r.name));
      const expected=['graph_runs','graph_action_admissions','graph_actions','improvement_pr_deliveries','improvement_executions'];
      if(schema>=45)expected.push('follow_up_delivery_attempts');
      if(schema>=47)expected.push('attention_dispatch_phases','engineering_missions','session_messages');
      if(expected.some(name=>!tables.has(name)))throw Error('upgrade_schema_tables_missing');
      if((db.prepare("SELECT count(*) n FROM improvement_executions WHERE state IN ('claimed','running')").get() as {n:number}).n>0)throw Error('upgrade_unknown_actions');
      if(graphUpgradeHolds(db)>0)throw Error('upgrade_graph_holds');
      if((db.prepare("SELECT count(*) n FROM graph_actions WHERE state IN ('running','unknown','cancel_pending')").get() as {n:number}).n>0
        ||(db.prepare("SELECT count(*) n FROM improvement_pr_deliveries WHERE state IN ('push_dispatched','pr_dispatched')").get() as {n:number}).n>0)throw Error('upgrade_unknown_actions');
      if(tables.has('follow_up_delivery_attempts')&&(db.prepare("SELECT count(*) n FROM follow_up_delivery_attempts WHERE state IN ('started','delivery_unknown')").get() as {n:number}).n>0)throw Error('upgrade_unknown_delivery');
      if(schema<47&&tables.has('attention_dispatch_phases'))throw Error('upgrade_schema_unqualified');
      if(engineeringUpgradeHolds(db)>0)throw Error('upgrade_unknown_actions');
      this.stopLocks.set(homeId,()=>{try{db.exec('ROLLBACK');}finally{db.close();release();}});
    }catch(error){db.close();throw error;}
  }
  snapshot(home: UpgradePlanHome, signal: AbortSignal, suffix = '') { return this.track(()=>this.doSnapshot(home,signal,suffix)); }
  private async doSnapshot(home: UpgradePlanHome, signal: AbortSignal, suffix = '') {
    this.assertOperation(); const c = this.consumer(home); if (!this.stopLocks.has(c.home_id)) throw Error('upgrade_stop_lost'); signal.throwIfAborted();
    const base = join(c.home,'upgrade-snapshots'); await mkdir(base,{mode:0o700}).catch(e=>{if(e.code!=='EEXIST')throw e;}); privateDirectory(base);
    const dir = join(base,this.plan!.digest + suffix); await mkdir(dir,{mode:0o700});
    for (const name of ['state.db','state.db-wal','state.db-shm']) {
      signal.throwIfAborted(); const path = join(c.home,name); if (!existsSync(path)) continue;
      if (realpathSync(path) !== path) throw Error('upgrade_snapshot_symlink'); await copyFile(path,join(dir,name),constants.COPYFILE_EXCL);
      const fd = await open(join(dir,name),constants.O_RDONLY|constants.O_NOFOLLOW); try { await fd.sync(); } finally { await fd.close(); }
    }
    await syncDirectory(dir); await syncDirectory(base); this.assertOperation();
    return { home_id:c.home_id,source_generation:home.identity!.generation,receipt_ref:`snapshot:${this.plan!.digest}:${c.home_id}` };
  }
  install(plan: FrozenUpgradePlan, group: UpgradePlanGroup, signal: AbortSignal) { return this.track(()=>this.doInstall(plan,group,signal)); }
  private async doInstall(plan: FrozenUpgradePlan, group: UpgradePlanGroup, signal: AbortSignal) {
    this.assertOperation(); if (this.stopLocks.size !== group.homes.length) throw Error('upgrade_all_consumers_required');
    for (const c of this.config.consumers) if (await this.backend.service(c.label,signal) !== 'absent') throw Error('upgrade_stop_lost');
    await this.backend.assertConsumers(this.config,[],signal);
    const release = join(this.config.root,'releases',plan.plan.target.build_digest); this.assertOperation();
    if(upgradeCanonical(verifyRelease(this.config.root,plan.plan.target.build_digest).target)!==upgradeCanonical(plan.plan.target))throw Error('upgrade_release_metadata_changed'); await switchRelease(this.config.root,release,signal); this.assertOperation();
    return {plan_digest:plan.digest,installation_id:group.installation_id,version:plan.plan.target.version,build_digest:plan.plan.target.build_digest,receipt_ref:`release:${plan.plan.target.build_digest}`};
  }
  restart(home: UpgradePlanHome, signal: AbortSignal) { return this.track(()=>this.doRestart(home,signal)); }
  private async doRestart(home: UpgradePlanHome, signal: AbortSignal) {
    this.assertOperation(); const c = this.consumer(home); if (!this.stopLocks.has(c.home_id)) throw Error('upgrade_stop_lost');
    const permit = join(this.config.root,'restart-permit.json');
    if (!existsSync(permit)) await publishPrivate(permit,{plan_digest:this.plan!.digest,build_digest:this.plan!.plan.target.build_digest});
    const expected = JSON.parse(readPrivate(permit).toString()); if (expected.plan_digest !== this.plan!.digest || expected.build_digest !== this.plan!.plan.target.build_digest) throw Error('upgrade_restart_permit_binding');
    this.stopLocks.get(c.home_id)!(); this.stopLocks.delete(c.home_id);
    await this.backend.start(join(this.config.root,'services',`${c.home_id}.plist`),signal);
    while (!existsSync(c.socket)) { this.assertOperation(); await pause(signal); }
    this.assertOperation(); return {home_id:c.home_id,source_generation:home.identity!.generation,receipt_ref:`restart:${this.plan!.digest}:${c.home_id}`};
  }
  /** Fresh explicit approval performs forward repair from observed facts, never a blind rerun.
   * A successful target is kept; absent services alone may be bootstrapped. Unknown observations stop. */
  reconcileForward(plan: FrozenUpgradePlan, group: UpgradePlanGroup, journal: UpgradeJournal, expectedHistory: string, signal: AbortSignal){return this.track(()=>this.doReconcileForward(plan,group,journal,expectedHistory,signal));}
  private async doReconcileForward(plan: FrozenUpgradePlan, group: UpgradePlanGroup, journal: UpgradeJournal, expectedHistory: string, signal: AbortSignal) {
    this.plan = plan; this.group = group;
    if (this.input.approvedPlanDigest !== plan.digest || this.config.installation_id !== group.installation_id
      || upgradeCanonical(this.bundle.target) !== upgradeCanonical(plan.plan.target)
      || upgradeCanonical(group.homes.map(h=>h.home_id).sort()) !== upgradeCanonical(this.config.consumers.map(c=>c.home_id).sort())) throw Error('upgrade_approval_binding');
    this.ownerRelease = acquireDaemonLock(join(this.config.root,'upgrade-owner.pid')); this.assertPins();
    const previous=await journal.status(plan.digest,group.group_id);
    if(previous.completed){
      if(upgradeDigest(previous.records)!==expectedHistory)throw Error('upgrade_reconciliation_changed');
      if(realpathSync(join(this.config.root,'current'))!==join(this.config.root,'releases',plan.plan.target.build_digest)||upgradeCanonical(verifyRelease(this.config.root,plan.plan.target.build_digest).target)!==upgradeCanonical(plan.plan.target))throw Error('upgrade_release_metadata_changed');
      // Terminal history already contains verified identities. This only repairs
      // interrupted fence cleanup, never replays work or claims current health.
      signal.throwIfAborted();
      await journal.cleanupVerifiedClaims(plan.digest,group.group_id,expectedHistory);
      await this.complete();return{state:'verified' as const,history_digest:expectedHistory,reason:'verified_history_fence_cleanup_only',services_observed:false};
    }
    this.assertOperation();
    let history = await journal.recordReconciliation(plan.digest,group.group_id,expectedHistory,{verified:false,evidence:{registry:this.input.registryDigest,artifact:this.input.artifactDigest},reason:'explicit_forward_reconciliation'});
    try {
      const current = realpathSync(join(this.config.root,'current'));
      const target = join(this.config.root,'releases',plan.plan.target.build_digest);
      if(!existsSync(target))await stageRelease(this.config.root,this.bundle,signal);
      if(upgradeCanonical(verifyRelease(this.config.root,plan.plan.target.build_digest).target)!==upgradeCanonical(plan.plan.target))throw Error('upgrade_release_metadata_changed');
      signal.throwIfAborted();this.assertOperation();const targetActive = current === target;
      const toStart: UpgradePlanHome[] = [];
      for (const home of group.homes) {
        signal.throwIfAborted(); this.assertOperation(); const c = this.consumer(home);
        const state = await this.backend.service(c.label,signal);
        if (state === 'running') {
          const observed = await this.observe(home,signal);
          if (targetActive && observed.identity.build_digest === plan.plan.target.build_digest) continue;
          if (targetActive) throw Error('upgrade_reconciliation_running_wrong_build');
          await this.drain(home,signal);
        } else {
          await this.holdStoppedHome(c.home,c.home_id,c.socket,signal);
        }
        toStart.push(home);
      }
      const runningPids:number[]=[];for(const home of group.homes){const c=this.consumer(home);if(await this.backend.service(c.label,signal)==='running'){const health=z.object({pid:z.number().int().positive()}).passthrough().parse(await upgradeRpc(c.socket,'health',signal));runningPids.push(health.pid);}}await this.backend.assertConsumers(this.config,runningPids,signal);
      if (!targetActive) {
        for (const home of group.homes) {
          await this.snapshot(home,signal,`-reconcile-${history.slice(0,16)}`);
        }
        if (!existsSync(target)) await stageRelease(this.config.root,this.bundle,signal);
        if(upgradeCanonical(verifyRelease(this.config.root,plan.plan.target.build_digest).target)!==upgradeCanonical(plan.plan.target))throw Error('upgrade_release_metadata_changed'); this.assertOperation();
        await switchRelease(this.config.root,target,signal);
      }
      if(upgradeCanonical(verifyRelease(this.config.root,plan.plan.target.build_digest).target)!==upgradeCanonical(plan.plan.target))throw Error('upgrade_release_metadata_changed');
      for (const home of toStart) await this.restart(home,signal);
      const identities = [];
      for (const home of group.homes) {
        const observed = await this.observe(home,signal); const i = observed.identity;
        if (!observed.healthy || i.version !== plan.plan.target.version || i.build_digest !== plan.plan.target.build_digest
          || i.protocol_version !== plan.plan.target.protocol_version || i.database_schema !== plan.plan.target.database_schema
          || i.generation === home.identity?.generation || i.build_evidence !== 'host_manifest' || i.deployment_kind !== 'npm') throw Error('upgrade_version_mismatch');
        identities.push(i);
      }
      this.assertOperation(); history = await journal.recordReconciliation(plan.digest,group.group_id,history,{verified:true,evidence:identities,reason:'reconciled_target_verified'});
      await this.complete(); return {state:'verified' as const,history_digest:history};
    } catch (error) {
      await journal.recordReconciliation(plan.digest,group.group_id,history,{verified:false,evidence:{error:'reconciliation_unknown'},reason:'reconciliation_unknown'}).catch(()=>{});
      throw error;
    }
  }
  /** Kernel locks may be released; the persistent operation fence survives every failure. */
  async close(): Promise<void> { this.closed=true;await Promise.allSettled([...this.pending]);for (const release of this.stopLocks.values()) release(); this.stopLocks.clear(); this.ownerRelease?.(); this.ownerRelease=undefined; }
  complete():Promise<void>{return this.track(()=>this.doComplete());}
  private async doComplete(): Promise<void> {
    this.assertPins();
    if(!this.plan||!this.group||!this.ownerRelease)throw Error('upgrade_operation_binding');
    const operation=join(this.config.root,'upgrade-operation.json'),permit=join(this.config.root,'restart-permit.json');
    const fenced=existsSync(operation);
    if(fenced){this.assertOperation();await finishPrivatePublication(operation);}
    if(existsSync(permit)){const bytes=readPrivate(permit);if(fenced){const value=JSON.parse(bytes.toString());if(value.plan_digest!==this.plan.digest||value.build_digest!==this.plan.plan.target.build_digest)throw Error('upgrade_restart_permit_binding');}await finishPrivatePublication(permit);}
    // Make absence of the blocking fence durable before removing startup permission.
    // A crash at either boundary is safe and the same authorized cleanup is resumable.
    await unlink(operation).catch(e=>{if(e.code!=='ENOENT')throw e;});await syncDirectory(this.config.root);
    await unlink(permit).catch(e=>{if(e.code!=='ENOENT')throw e;});await syncDirectory(this.config.root);
  }
