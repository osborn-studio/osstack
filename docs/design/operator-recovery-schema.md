## Storage and freeze procedure

`bootstrap.sql` adds only `operator_recovery_decisions`, `operator_upgrade_journal`, their indexes and immutable-history triggers. `source-hold.sql` creates a foreign-key-valid schema-47 Attention dispatch in `dispatch_committed` with accepted message, uncertain action, delivery-unknown wait and abandoned-unknown resolution. It contains no synthetic completion. `future-storage.sql` defines separate method binding/object, active pointer, trial consumption and engineering-goal shapes for later migrations.

The manifest freezes raw SHA256 of SQL and fixture bytes; `schema_spec_digest` hashes the exact change ID, adjacent source/target numbers, those digests, the source/target schema catalog digests and sorted full expected target table list under `osstack.joint.schema-spec.v1`. It excludes future receipts/builds, avoiding a circular hash. The `future_storage_digest` is a separate raw template-byte pin and intentionally outside `schema_spec_digest`; changing a later storage template cannot qualify or invalidate a bootstrap receipt. J12 qualification additionally binds candidate commit, executable build digest and measured support profile. Schema catalog digests are raw SHA256 of joint-canonical-v1 JSON over SQLite `sqlite_master` rows `{type,name,tbl_name,sql}`, ordered by `(type,name)` and excluding SQLite internal objects whose names start with `sqlite_`. This freezes original CHECKs, indexes, views and triggers as well as tables. The schema-47 migration source and complete catalog must match the candidate base. A changed number, SQL byte, fixture or candidate requires new evidence.

48 is a candidate number, not a global reservation. The state-owner serializes `control_plane_schema`. J08/J10/J13 each supply their own `schema_spec → recovery → scoped` proof against their actual composed main. Their templates are not part of bootstrap and have no allocated schema number. File blobs are durable before transactional digest/ref insertion. Active pointers, qualification refs and consumption update under a single fenced transaction. A file rename is not a multi-object transaction.

## Recovery entry and bootstrap algorithm (J12 required)

1. Resolve the explicitly supplied recovery home; reject default/reserved or mismatched homes according to the serving/recovery policy. Authenticate the operator from the host context and verify current scope rights. Never trust operator fields supplied in a request.
2. Open through a dedicated recovery path before normal migration. Check exact version and lineage before changing pragmas/DDL. Acquire exclusive maintenance ownership and fence previous control-plane writers. Process lease expiry alone does not prove that a worker stopped.
3. Set `synchronous=FULL`; begin the owner-fenced write transaction. Recheck source version, lineage, owner generation, current operator grant and a fresh request identity inside the transaction.
4. Compare the SQL bytes to the frozen digest and a closed allowed-statement manifest. The only bootstrap effects are the listed new tables/indexes/triggers and the atomic version/lineage declaration. Reject UPDATE/DELETE/ALTER on original action, message, phase, hold, budget or worker records. Do not implement a regex-only SQL security filter; execute the pinned embedded statements.
5. Create the whole ledger and set the target version in the same transaction. On interruption, retain either source schema without any new ledger or the complete target. Never reset `user_version`. Start no worker.
6. Reopen using the matching recovery build, verify complete lineage and original rows, then allow operator recovery. The old schema-47 binary must reject 48 before migration/normal writes. Deployment must separately stop/fence an already-open old writer; a version check at open cannot fence an existing connection.

Ordinary upgrades remain blocked by unresolved holds. The bootstrap exception only adds recovery capability. For a pre-hold-table source version, use its explicitly registered compatibility rules; absence of a table is not evidence that an invocation did not start. Unsupported or mixed lineage fails closed.

## Request, proof, receipt and idempotency

J01 exports `RecoveryRequest`, `RecoveryProofEnvelope`, `RecoveryReceipt`, `RecoverySubject` and `MigrationSpec`; committed JSON shapes live in `packages/protocol/schemas/joint/joint-contract.schema.json`. Runtime request input must use `decodeJointContractAs('recovery_request', raw)` or its bytes equivalent; trusted receipt/envelope loads use their own exact kind. Generic union decoding is not an authority boundary. Parsing remains structural and never grants authority. Request carries request ID, subject, expected revision, requested decision, proof refs and expected schema spec. Operator, phase and generations are loaded from trusted state. A request cannot directly submit them as facts.

Within the current owner transaction, resolve `(principal, request_id)` first. Use `recoveryRequestInputDigest` under the registered `osstack.joint.recovery-request-input.v1` domain over schema version, authenticated principal/scope/tenant and the entire parsed request. Trial consumption uses its separate registered constructor/domain; root IDs use `trialRootEffectId`. Identical input returns the existing receipt only after current authentication/scope checks. Different input returns idempotency conflict. The recovery revision is 0 when this subject has no ledger entry; otherwise it is `MAX(prior_revision)+1` from this subject’s immutable ledger. It is distinct from the session/message/binding revision. Compare it to `if_revision` inside the write transaction; appending a row advances it exactly once even for preserve_unknown. Re-read and compare the original subject facts, live owner and binding/source generations in that same transaction; ledger revision alone cannot fence a source change. The local-home ledger rejects broker subjects; J17 owns the broker-side ledger and cannot reuse a home owner generation. Receipt proofs name their immutable record refs; preserve_unknown has no proof, and each resolving decision has exactly one matching typed proof. The ledger's unique `(subject_digest, prior_revision)` prevents concurrent different requests from deciding the same revision. A replay does not insert a second row. A retry after preserve_unknown uses a new request ID and current revision. A terminal decision seals this subject chain; later contradictory decisions require a new protocol version, not a new revision. SQL insertion guards reject skipped revisions and replacement even when SQLite recursive triggers are OFF. BEFORE INSERT duplicate checks intentionally precede conflict handling, including IGNORE/REPLACE/upsert; the tests pin these behaviors. SQL duplicates phase/decision and internal home equality checks as defense in depth. Only the host can compare the claimed home with the actual serving home or authenticate proof bytes; SQL is not a complete protocol validator.

Load proofs by immutable host refs. Before ledger insertion, call `verifyRecoveryProofEnvelopes` on the host-constructed receipt and host-loaded envelopes. Each envelope must carry and exactly match `owner_generation`, `binding_generation`, `support_profile_digest`, `prior_phase`, `schema_spec_digest` and `recovery_build_digest`. The helper also checks one-to-one immutable record references, canonical proof content, subject identity and envelope observation no later than the receipt. Missing or mismatched fields fail closed; do not synthesize missing legacy fields or downgrade to generic parsing. For `legacy_unknown`, only Attention subjects with null binding generation/profile and `preserve_unknown` are allowed. Committed Attention subjects may use actual containment evidence.

This helper establishes structural consistency only. J12 must additionally verify current owner/source/binding generations, exact invocation/attempt/workspace, cancellation CAS or containment/completion provenance, current scope/authorization and evidence freshness against trusted storage. Matching envelope and receipt fields do not establish that either is current. Replay lookup still requires current authority; it does not require changing historical receipts to the latest build/profile. The host must separate authorized replay of an immutable old receipt from admission of a new decision.

 Recompute raw evidence digests and verify producer authorization, subject, candidate/build/schema/profile and timestamps. A matching SHA256 is not producer authentication. Broker proof also binds broker ID, lease, broker schema and broker owner generation. Home ownership never substitutes for broker evidence. Receipt records actual trusted state, not the client's desired state. Receipt insertion and any required original-subject hold/accounting CAS commit atomically in FULL mode. A denied/conflicting request changes nothing.

## Verifier and post-state matrix

| Trusted state | Decision | Additional required proof | Required J12 persisted consequence (not implemented by J11) |
|---|---|---|---|
| Any supported subject | preserve_unknown | Current authority, target and revision | Increment recovery revision, append receipt; preserve original phase/hold/resources/reserved budget/wait; upgrade blocked |
| Reserved, resolution=none | proven_not_started | Dispatcher transaction confirms never committed, stop intent, exact cancellation CAS | Original action permanently cancelled before dispatch; release only provably unexecuted reservation; wait remains unfulfilled; no resend |
| Committed or broker unknown | proven_stopped | Independent exact invocation containment/termination record | Append resolved_stopped; retain original immutable phase/hold history; release concurrency only; unknown finance stays reserved; wait remains unfulfilled; no resend |
| Committed home subject | applied_observed | Existing exact completed turn + applied message, or exact Graph completion receipt | Project the existing completion; preserve provenance; do not manufacture success from exit 0 or an operator note |
| Legacy unknown | preserve_unknown only | Current authority and known legacy target | Never convert absence of evidence into stopped/not-started |
| Abandoned resolution on reserved | preserve_unknown only | Current authority | Do not revive a terminal disposition or dispatch again |

Other state/decision pairs fail without mutation. New effect subjects require binding generation and profile; legacy Attention/broker subjects can explicitly carry null identities. Subject digest includes the discriminant and all typed keys. The receipt proof and effect/broker identity must agree. Self-reported roles do not establish independence.

`proven_stopped` is an accounting resolution, not completion. A compatible upgrade requires every relevant hold accounted for, no active dispatcher, intact reserved unknown finance and an explicit maintenance journal transition. `operator_upgrade_journal` records fenced → verified → installed_inactive (or failed) with revisions/evidence. SQL enforces append-only revision order and the listed state transitions only; it does not prove hold clearance, evidence completeness or a successful installation. The `{}` journal evidence used in storage tests is intentionally not an admissible J12 verified/install record. J12 must authenticate typed evidence, bind the exact recovery-ledger revisions, check all current holds and fence the live owner before those transitions. Installation never resumes dispatch automatically. A failed upgrade retains the recovery build and obligations; downgrade is unsupported.

## J12 acceptance obligations

The J11 tests execute SQL in isolated in-memory databases. They check exact digests/lineage, preservation of all original rows, valid foreign keys, rollback at injected transaction boundaries, old migration-runner refusal, immutable history and permit uniqueness. These are specification checks, not process-crash qualification.

Before J12 can pass, add file-backed WAL/FULL subprocess kill tests before/during/after DDL and commit; old-owner and already-open old-writer fencing; missing/mixed lineage; wrong migration number/DDL/build/profile; malicious original-table mutations; duplicate and conflicting requests; stale subject revision; trusted-proof forgery and subject mismatch; all six envelope-context mismatches, wrong-kind decode, missing/duplicate/rebound immutable proof refs, future/stale proof observations, source/binding generation changes between load and CAS; cross-row phase regression and terminal state changes checked against trusted live state; same principal/request ID with identical versus different recoveryRequestInputDigest and owner/grant changes on replay; accounting and wait assertions for every matrix cell; original-message non-replay; broker orphan proof on the exact broker tuple when enabled. Re-run against the exact composed candidate. Independent oracle authorship and trusted provider measurements remain separate gates.

The narrow local-home gate applies only with broker disabled. It does not satisfy Firstmate's full home+broker recovery gate. No later migration may reuse the bootstrap test result as proof of its own recoverability.


## Reproduction and schema queue

Build protocol/core, then run `node packages/core/fixtures/operator-recovery/freeze.mjs <reviewed-base-commit>` only after state-owner review of the current main. It creates an in-memory database, validates the source hold and regenerates the manifest. Copy the new manifest.spec into the schemaSpecDigest vector input in reference-vectors.json, then run the Python script without --check to regenerate the independent expected digests; review that input change before running the check. Run `python3 packages/protocol/scripts/joint-reference-vectors.py --check --recovery-root packages/core/fixtures/operator-recovery` to independently verify SQL/catalog/spec digests. SQL bytes are pinned with `-text` attributes. Do not copy these fixture DDLs into a production migration without the J12 recovery certificate.

An unrelated schema change intentionally invalidates this candidate's `CURRENT_SCHEMA_VERSION===47` assertion. Its state-owner must re-freeze this fixture on the new composed base or explicitly supersede it; deleting the assertion is not an acceptable rebase. `content_ref` in future method storage is an opaque host registry key, never a filesystem path supplied by a worker. SQL composite foreign keys enforce binding/qualification object kinds; host loaders enforce registry identity and content digests. Permit IDs are host-issued globally unique IDs, additionally bound to scope/tenant and original input. Consumption cannot be deleted, replaced or reset; only consumed → unknown/reconciled → reconciled transitions are permitted.

Future storage templates do not install active-pointer CAS or goal phase monotonicity triggers. J08/J10/J13 must implement and test those transitions under owner fencing. Their existing local CHECKs allow stopped resolutions from committed or observed phases and do not imply a runtime state machine.

SQL's phase/decision matrix is only the local enum/cross-field subset, not the complete verifier/post-state matrix. Proof presence/cardinality/type, new-effect identity, canonical subject digest and full receipt schema remain mandatory TypeScript parser/verifier checks before insert. The 40-combination SQL test uses Attention subjects; it does not claim SQL proves effect identity or proof validity. A reserved → committed phase change between preserved observations can be legitimate; J12 checks live phase continuity and rejects regressions/rewinds under the owner transaction. The recovery ledger alone cannot authenticate that transition.

The freeze helper rejects state implementation changes against the explicit base (including migration DDL helpers, excluding tests), then force-builds core before dynamically importing its runner. Review the full source/target catalogs and independent digest output after regeneration; this developer helper is not a production migration or a build attestation.
