# Bot 合并：设计草稿

日期：2026-11-25。状态：**负责人 2026-11-25 接受 §8 全部推荐（“都按推荐，开 PR”）**。不改代码；真实合并仍需 M-E0 的 ADR-008。

上位文档：[ADR-006](../decisions/ADR-006-bridge-s0-decisions.md) 决定 2（自动合并的门槛）、“Shadow first”、“Residual race”、风险 4、探针 P-12；[App E 影子合并者](2026-11-06-bridge-shadow-merger.md)（门槛 G0–G8）；[桥接运行手册](../runbooks/bridge.md) §6.1、§6.2；B9 沙箱修订 `docs/design/2026-11-25-b9-sandbox-shared-computer.md`（#569）。

## 1. 目标

负责人的目标：osstack 自动写代码、开 PR、修 PR（内循环）；Grok Bot 发现问题、批准 PR，PR 自动合并（外循环）。现在缺的是最后一段：**谁批准、谁合并**。

今天的规则：Mission PR 和本地失败修复的 PR 都由人合并（运行手册 §6.1）；App E（`osstack-merger`）只在影子模式运行，`OSSTACK_MERGER=1` 启动即拒绝（`MERGER_LIVE_NOT_IMPLEMENTED`）。

## 2. 两个问题要分开

**谁执行合并**和**谁的批准算数**是两件事。

- 执行合并：调用 GitHub merge API 的那个身份。`main-update` ruleset 只让 App E 通过 PR 更新 `main`（门槛 G8），App A 被拒（探针 P-12）。
- 批准：`main-quality` ruleset 要求至少一个批准、最后一次推送之后的批准、会话全部解决。ADR-006 探针结论：**GitHub App 的批准不满足这条规则**，只有用户账号的批准算数。App E 自己的门槛 G6a 更严：只认登记表 `counted_approvers` 里的用户，今天只有 `gilosbornhello`。

所以“让 Grok Bot 批准”不是开一个开关就行：Bot 作为 GitHub App 发的批准，GitHub 平台本身就不算。

## 3. 建议：App E 合并，不新建合并 Bot

**谁执行合并：PR Merger（App E）打开 live 模式。不新建一个合并 Bot，也不两个都做。**

| | App E live | 新建一个 Grok Bot 来合并 |
|---|---|---|
| 判断方式 | 确定性代码，13 条门槛（G0–G8），每条读实时 PR，二次读取防 TOCTOU | 模型判断；门槛只能写在提示里 |
| 已有证据 | 影子期在跑，有影子决定与真实合并的对照（`osstack mission merger report`） | 无 |
| 密钥在哪 | 主机（Mac mini），Bot 碰不到 | Grok 共享电脑。Bot 有 root，账号下所有 Bot 共用凭证（B9 沙箱修订 §2） |
| 平台规则 | `main-update` 已只放行 App E | 要改 ruleset，再加一个能写 `main` 的身份 |
| 被伪造的风险 | 需要攻破主机 | 任何一个 Bot、或任何读到那台电脑的代码，都能以合并者身份合并 |

两个都做更差：两个合并者会争同一个 PR，能写 `main` 的身份从一个变两个，而且新 Bot 那条路的安全性决定了整体下限。

**Grok Bot 的角色**：发现问题、触发修复、做评审并给出批准或要求修改。它的批准是 App E 门槛的一个输入，不是合并命令。合并由 App E 在门槛全部成立时执行。

## 4. 谁的批准算数：三个选项

这是负责人要决定的核心（§8 决定 2）。

| 选项 | 做法 | 自动化程度 | 代价 |
|---|---|---|---|
| A. 人批准，App E 合并 | G6a 不变，仍需 `gilosbornhello` 在 live head 上批准。批准之后其余全自动 | 每个 PR 你点一次批准（手机上可做） | 不是全自动 |
| B. Bot 用户账号批准，限低风险 | 给 Grok 评审 Bot 一个**用户账号**（GitHub App 批准不算数），登记进 `counted_approvers`，但只对满足 §5 低风险条件的 PR 计入 | 低风险 PR 全自动；其余回到 A | 要一个机器用户账号及其凭证；它的令牌放在哪决定了谁能冒充它（见下） |
| C. 不要批准 | 把 `main-quality` 的批准数降为 0，只靠 App E 的机器门槛 | 全自动 | 平台不再重查任何批准；一个出错的修复只要通过检查就会进 `main`。**不建议** |

选项 B 的关键风险：评审 Bot 的用户令牌如果放在 Grok 共享电脑上，所有 Bot 和那台电脑上的任何代码都能以它的身份批准。B 的安全性因此依赖：

- 机器门槛本身已经足够挡住坏修复（§5 的条件，不靠 Bot 判断）；
- 批准只是“多一道”，不是“唯一一道”。

**建议：先 A，再 B。** 先用 A 在沙箱上把 App E 的真实合并跑通；影子与真实对照满足 §6 的门槛后，再在沙箱上开 B；最后才考虑主仓库，并且只对 §5 的低风险类开 B。C 不做。

## 5. 低风险 PR 的条件（选项 B 计入 Bot 批准的前提）

全部是机器可判定的条件，任何一条不满足就回到人批准：

1. App E 现有门槛 G0–G8 全部成立（含 G4b：PR 不改 `.github/workflows/`、`.github/actions/`）。
2. 风险分类为最低一档（`packages/autonomy/src/risk.ts`），不触碰受保护路径集合（`missionProtectedSetDigest` 所覆盖的文件）。
3. 改动规模上限：文件数、行数（数值待定，§8 决定 4）。
4. 验证结果来自 GitHub Actions 的 `osstack/verify-actions` check（§5a），在同一 head 上 `success`，并且其他 GitHub Actions 必需检查全绿。
5. 不依赖 Grok 共享电脑或 Mac mini 产生的任何结果：云端验证程序（B9）与主机复验（B7d）都不计入本条件（§5a）。
6. 没有任何人或 Bot 的仍有效的“要求修改”（G6d），会话全部解决（G6c）。

## 5a. 验证结果由 GitHub Actions 写出（2026-11-25 修订）

负责人要求：验证程序不搬离 Grok 共享电脑，Mac mini 也不重复验证。Bot 在那台电脑上有 root，那里产生、那里签名的结果都能被伪造，这一点没有技术能绕过。所以那台电脑只**发起**验证，验证本身跑在 GitHub 托管的 runner 上，结果由 GitHub 写出。

**流程**

1. Grok Bot（Watcher）发现需要验证的 Mission PR，用自己的凭证发 `workflow_dispatch`，参数只有 PR 号。它能做的只是触发或不触发。
2. 工作流 `.github/workflows/osstack-verify.yml` 来自 `main`（`workflow_dispatch` 总是运行默认分支上的工作流文件）。它：
   - 用 `GITHUB_TOKEN` 读 PR，取 `headRefOid` 为 `H`；PR 关闭、来自 fork、不是 `osstack/mission/` 分支时直接结束；
   - 按 SHA 检出 `H`，`persist-credentials: false`；
   - 工作流 `permissions` 只给 `contents: read`、`checks: write`、`pull-requests: read`；不引用任何 secret；
   - 运行固定的验证命令（今天 verification profile 的命令，改写成工作流步骤）；
   - 在 `H` 上写 check run `osstack/verify-actions`，`external_id = <PR 号>:<H>`，结论为 `success` 或 `failure`。
3. App E 读 `H` 上的这个 check：`app.id = 15368`（GitHub Actions），名称、`head_sha`、`external_id` 都必须对上。

**为什么 Bot 伪造不了**

- check run 的写入身份是 GitHub Actions。Bot 没有能以 15368 身份写 check 的凭证；它的凭证只能触发工作流。
- 工作流文件来自 `main`。PR 不能改它（G4b 拒绝改 `.github/workflows/` 的 PR），而修改 `main` 只有 App E 能做（`main-update` ruleset）。
- runner 每次都是新的临时机器，跑完销毁。

**不依赖“别人不是 admin”**（2026-11-25 修订，见 §5b）

- 工作流内容由 App E 自己核对：主机私有的 `merger.json` 登记 `osstack-verify.yml` 的 git blob SHA。App E 读该 check 所属工作流运行的 `head_sha`（`main` 上的提交），取那个提交里的工作流文件，blob SHA 不等于登记值就不合并。任何人改了这个文件，App E 都停止，直到负责人在主机上更新登记值。
- 仓库里没有其他工作流能以 `osstack/verify-actions` 为名写 check run。App E 再加一条：同名 check 只认 `osstack-verify.yml` 这个工作流的运行（通过 check suite 的 `head_branch` 与工作流 run 的 `path` 核对）。
- `pull_request_target` 不得用于这个工作流（它会以 base 权限跑 PR 代码）。

**被取代的部分**

- App E 门槛 G3（App B 的 `osstack/verify`）与本地失败修复路线的“验证 App 结果 + 主机复验”，对合并判断而言改由 `osstack/verify-actions` 取代。
- B8、B9 的云端验证程序与发布程序：只服务这次沙箱演练，不进入合并门槛；演练后是否退役，另行决定。
- Mac mini 不做合并前的重复验证。

**代价**

- 消耗 GitHub Actions 分钟（公开仓库免费，私有仓库计入套餐额度）。
- 验证命令要能在 `ubuntu-latest` 上跑；需要的工具版本在工作流里固定。

## 5b. 三个账号保留 admin 和合并权（2026-11-25 负责人决定）

**读回事实（2026-11-25，只读）**

- `osborn-studio/osstack` 的四个 ruleset（`main-quality`、`main-update`、`mission-history`、`mission-writers`）全部 `enforcement: disabled`；`rules/branches/main` 为空。
- `gilosbornhello`、`gilberthello`、`Rubebun-Jadeem`（User，id 243772068）在 `osstack` 上都是 `admin`。
- 最近的主仓库 PR 由 `gilberthello` 或 `Rubebun-Jadeem` 批准并合并；沙箱 #30–#34 由 `Rubebun-Jadeem` 批准、App E 合并。
- `gilberthello` 是负责人个人使用的账号；`Rubebun-Jadeem` 是 Grok Bots 共用的登录。

**决定**：三个账号都不降权，都可以照常合并；App E 是额外的合并者，只合并满足门槛的 Mission PR。

**为此对 App E 的改动**

1. **工作流内容固定**（§5a）：用登记的 blob SHA，而不是依赖“Bot 改不了 `main`”。
2. **G6e、G8 改为只记录**：ruleset 的 bypass 名单与启用状态写进影子/合并记录，但不作为拒绝条件。App E 自己核对批准、检查、base、会话，不依赖平台替它把关。
3. **批准登记**（`merger.json`）：
   - `counted_approvers`（人工，对所有 Mission PR 计入）：`gilosbornhello`、`gilberthello`。`gilberthello` 只能由负责人本人使用，不交给任何 Bot。
   - `bot_approvers`（只对 §5 低风险 PR 计入）：`Rubebun-Jadeem`。可以登记多个机器账号用于容错（令牌失效或限流时切换），但它们信任等级相同，不叠加成“两道”批准。
4. **非 App E 合并提醒**：每个周期检查 `main` 上新合并的 Mission PR，`mergedBy` 不是 App E 时发 attention 通知（`OSSTACK_ATTENTION_NOTIFY`），记录 PR、head 和合并者。只提醒，不回滚。

**保证范围**

| | 结果 |
|---|---|
| App E 合并的 PR | 验证结果不可伪造（工作流内容固定、check 由 GitHub Actions 写出、head 绑定）。低风险 PR 全自动 |
| 三个账号直接合并的 PR | 不经过 App E 门槛，没有上述保证，由合并者负责 |
| Bot 用 admin 改验证工作流 | App E 发现 blob SHA 不符，停止合并 |
| Bot 用 admin 直接合并 | 不能阻止；由第 4 条提醒。Grok Bot 的 routine 规定 Mission PR 只批准、不合并（约定，不是技术限制） |

## 6. 打开 App E live 的前提

ADR-006 要求“先影子、后真实”，并要求单独的设计与后续 ADR。草稿提议：

1. **影子对照**：在沙箱上，影子决定与真实结果的对照里，`would_merge` 而真实上不该合并的情况为 0，样本至少 N 个 PR（N 待定，§8 决定 3）；每一条 `refused` 的原因可以解释。
2. **残余竞态**（ADR-006 “Residual race”）：GitHub merge API 只绑定 head，不绑定 base，也不重查批准者身份。处理方式二选一：
   - 记录为已接受风险（窗口是一次周期内的秒级）；
   - 或在合并前立刻再做一次完整读取，并把 `main-quality` 的 `strict_required_status_checks_policy` 设为 `true`，让平台在合并时要求 base 最新。
3. 新的 ADR（ADR-008）记录：App E 可以真实合并、哪些仓库、哪个批准选项、撤销方法。
4. 开关：`OSSTACK_MERGER=1` 只对登记表 `merger.json` 里的仓库生效；第一版只允许沙箱仓库（与 `OSSTACK_BRIDGE=1` 的沙箱限制同样方式实现）。
5. 熔断：`OSSTACK_MERGER=0` 立即停止所有真实合并；App E 私钥可以随时在 App 设置里删除。
