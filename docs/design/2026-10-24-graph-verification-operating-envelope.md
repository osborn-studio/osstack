# Graph verification resource and recovery boundaries

This document defines the PR #244 verification limits. These are fail-closed resource ceilings and recovery rules, not a latency service-level agreement or qualification of real Docker deployments.

## Candidate and repository limits

Each candidate content pass admits at most 128 MiB aggregate opened-file bytes. Tracked-content passes cap tracked files and symlinks at 10,000; the full review inventory counts files, symlinks and directories against its 10,000-entry aggregate budget. The exact-file visit walk does not charge directories as entries: directory listings are individually capped at 10,000, and expected parent directories are derived from the tracked set. Thus 10,000 is not a uniform upper bound on all nodes visited by every pass. Each repository metadata walk admits at most 256 MiB of described file bytes and 20,000 entries. A larger valid candidate or Git repository is rejected; it is not silently truncated. Restore uses an independently verified full-history bundle, so even a small working tree can exceed the metadata ceiling through history or loose objects. A directory with 20,001 actual entries is covered by a rejection test. Existing larger histories require an explicit future resource-policy design before being supported.

These ceilings bound resource consumption; they do not guarantee completion within any particular run deadline. The graph protocol accepts a caller-selected `limits.deadlineSeconds` from 1 through 604,800 seconds. The test fixture's 120-second graph limit is not a universal product limit. The broker separately caps command/contained suite execution at 120 seconds; that execution cap does not include artifact preparation. Original adapter.invoke has no broker wall-clock execution timeout. Reviewer/implementation adapter duration is governed by the adapter; an action admitted shortly before the run deadline can overrun it. Adapter cancellation grace is 50 milliseconds and is not a total-runtime limit. GraphActionStore checks the run deadline at admission, invocation issuance and apply dispatch; prepareSelection itself does not read deadlineSeconds or interrupt synchronous restore work at the deadline. Its callbacks and lease checks are not a hard real-time preparation deadline. A late stopped result may still be recorded as evidence; it does not authorize a new invocation. This document does not claim that GraphVerificationStore.commit imposes a terminal wall-clock deadline gate. Resource ceilings alone do not establish deadline compliance.

Freeze and verification intentionally have different admission domains: freeze accepts a compressed bundle up to 256 MiB, while verification applies the stricter uncompressed candidate and described-metadata ceilings above. A highly compressible candidate can therefore freeze successfully and fail later verification, as can a full-history bundle near its limit once restored metadata overhead is counted. The current behavior rejects at verification after materialization: prepareSelection verifies the artifact, calls restore (which writes/fsyncs every file and recaptures the tree), and only then applies the verification content ceiling. The verification ceilings introduced here do not bound earlier restore memory, I/O, or elapsed time. Freeze success is not a promise of downstream admission. A pre-restore uncompressed-size check is a follow-up, not implemented here. Aligning these admission domains earlier is a documented liveness improvement, not implemented by this change.

There is no claimed maximum file count that always completes within 120 seconds. Storage latency, file count, artifact history and durability syncs affect preparation. On the recorded local fixture, a 1,500-file candidate required 60.641 seconds to prepare: restore took 58.951 seconds, two additional artifact verifications 0.892 seconds, and the final exact-file check 0.175 seconds. Restore includes its own verification, batched Git extraction, per-file durable writes/fsync, and recaptured-tree verification. A larger candidate can exhaust a caller's deadline. For planning only, the observed restore cost was about 39 milliseconds per file; use measured repository-specific preparation plus execution/stop margins when choosing a run deadline, not 120 seconds by default for a large tree. Do not linearly extrapolate this sample as a guarantee or remove durability to meet it.

## Observation and publication

Persistence makes four complete candidate observations: its initial validation, immediately before create-only link publication, after that link, and after final durability/temporary-link cleanup. Cheap live authority checks still surround asynchronous storage steps. Raw content observations are not cached across publication boundaries. A review observation covers tracked content and the complete candidate inventory. Tests observations cover tracked content, index, HEAD and its tree, the contained digest, and the identity of the worktree, .git and .git/objects directories. Git metadata is structurally checked at each observation but its bytes are not hashed. Untracked test outputs are permitted and are not re-inventoried. This is not an atomic filesystem snapshot against an arbitrary same-UID writer. A mutation after the initial observation that is restored before the pre-link observation can be undetected across compaction, evidence write, fsync and chmod; this window is wider than observing at every cheap authority check. This design explicitly accepts that residual observation window for the four-boundary contract: it does not promise detection of transient writes between observations, while still freshly checking raw content at publication boundaries. The broker may await after persistence returns and before recording the action outcome; the last observation does not eliminate that later non-atomic window. A rejected post-link publication can leave an unreferenced digest-named envelope; consumers must require a verified ledger reference rather than treating file presence as successful delivery.

## Stop confirmation

Contained actions require a stopped journal bound to the launch, two fresh daemon identity checks, and a fresh container-absence response. Each Engine request has a five-second timeout. Post-execution contained confirmation uses the existing 30-second contained cancellation grace. A contained suite confirms up to sixteen invocation proofs concurrently within one 30-second suite-level confirmation envelope, not thirty seconds per check. If any proof is missing, inconsistent, or too slow, the action remains unknown and the write lease is retained. A timeout is never proof of stopping. Non-contained post-execution confirmation retains its one-second boundary.

The regression fixture delays a real simulated Engine 404 response by 1.1 seconds and still exercises the executor journal and daemon identity checks. It proves that the previous one-second outer race could reject a valid proof. It does not establish the exact cause of every earlier intermittent suite failure or certify production Docker latency. A slow or overloaded real daemon can still fail closed under the documented envelope.

## Validation gates

The default functional gate runs the complete verification test file with the performance experiment disabled, as configured by `it.skipIf(!OSSTACK_REVIEW_INVENTORY_REPORT)`. The explicit performance experiment is a separate opt-in diagnostic qualification, not part of the default CI correctness gate. It does not need to run concurrently with all functional cases to establish its observations. Run it independently with the reporting environment variable and its existing 120-second test deadline. Retain failures: the combined diagnostic invocation timed out once for an unestablished cause; the historical r4 independent experiment passed in 89.531 seconds, and its historical default file passed 52 tests with that diagnostic skipped. Both r4 runs predate the r9 GovernedExecution change. The current r10 full functional run after that change passed 52 tests, skipped the one opt-in diagnostic, and exited 0 in 83.43 seconds. The r4 benchmark remains a historical diagnostic on unchanged benchmark/verification bytes; it uses stub acquisition callbacks and does not exercise GovernedExecution. Both production source identity and actual exit status must accompany evidence. No timeout was raised to turn that diagnostic green.

## Conservative recovery and trusted registrations

A failed settlement can leave a durable intent. Replay returns unknown without repeating execution. Same-generation stranded intents do not globally block all subsequent admissions: terminal projection and delivery inventory reject incomplete delivery. The specialized unstarted-worker recovery deliberately refuses a run with action rows. Generic GraphReconciler recovery requires independently verified administrator-attested worker, quiescence and outcome proof plus a final recheck; an absent execution reference is insufficient. There is no wired automatic operator exit for an unprovable intent.

Executor and stop callbacks are trusted host registrations. Their implementation is not cryptographically fingerprinted by an adapter ID. Each reconciliation caller now runs its own trusted verifier, including when the lease is already released or another release/reconciliation is pending. Concurrent callers still coalesce physical release.

A reconciliation verifier joining an already-started normal release can reject its own promise, but does not undo physical release already authorized by the normal path. The first path’s release preconditions remain authoritative. A cheap default-gate exact observation-count assertion and per-proof failure identifiers are deferred P3 diagnostics; the exact count is currently asserted by the independent opt-in experiment.
