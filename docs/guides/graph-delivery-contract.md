# Graph delivery contract and prompt evidence

Graph contract support is opt-in on a trusted host registration. The initial supported combination is implement + local_verified + artifact_only, exactly one required registry check whose success exit code is 0, and no publication/merge authority. Other combinations fail closed. The V2 contract declares required behavior; the registration's live grant, committed host policy, explicit Graph budgets and independent reviewer authority still authorize execution.

Local owner-only Graph config may contain `registration.deliveryContract` (a strict V2 contract), and `registration.executionContextPath` for an explicitly pinned local knowledge configuration. Config alone is insufficient: the daemon must inject `LocalGraphRegistrationOptions.resolveDeliveryContractPolicy`, and when context is enabled, `resolveExecutionContext`. Missing resolvers reject the registration. Context initially supports only the default tenant; other Graph registrations remain available without context.

The policy resolver returns `policyDigest`, `reviewPolicyRef`, all seven Graph limit fields and synchronous `assertCurrent`. Limits are explicit trusted ceilings for epochs, branch attempts, readers, one writer per repository, action starts, deadline seconds and token reservation. They cannot be inferred from the untrusted request. Policies are rechecked on execution/resume, each effect and completion. Deadline checks are cooperative, not a hard process-stop guarantee.

The context resolver returns a configuration digest, private receipt root, synchronous authority check and per-attempt adapter factory. It can reuse `createExecutionContextAdapters`; the supplied adapter observes the exact final task after mandatory instruction/safety/contract and optional knowledge have been assembled. Graph records the final reviewer prompt digest at that point. Each factory instance permits exactly one actual adapter invocation. Both prepared and adapter-observed records must exist, match their raw SHA-256 and belong to the actual run/task/session/contract/repository. A durable host link binds both raw receipt hashes and the final prompt digest to the full Graph effect identity. Completion rereads that link and both phase records for the current writer and reviewer. They attest AgentTask input, not provider wire or independent model identity. An adapter that produces no event cannot provide the observed phase and cannot claim verified completion.

The host freezes contract, selected registry entry, policy and optional context configuration digest into a versioned envelope. Its digest becomes the internal input artifact reference before the existing durable run reservation, so input identity and idempotency include the host binding. External callers still must present the original registered input reference. Legacy runs without a contract keep their original input digest. The frozen v4 graph compiler, registry and worker wire have unchanged semantics; supporting multiple checks will require a separate compiler/topology version.

Checks and review still operate on independently restored copies of the same immutable candidate. Path restrictions compare every repair candidate against the contract's original base, including both ends of renames and ignored untracked output before serialization. Graph's `commit-tree` serializes an artifact in an isolated object repository; it does not commit to the source workspace. Integration tests assert that source HEAD, refs, index and tracked file bytes remain unchanged.

`graph.result` retains its existing status shape. A successful contract run adds a `graph-contract:<digest>` evidence reference alongside the immutable join reference. `graph.contract` accepts the same scoped request as `graph.status` and reads the referenced strict `osstack_graph_host` receipt only after the run is ready. It binds run/input/spec/generation/epoch, contract/policy, exact candidate and real check/review effect evidence. `local_verified` does not mean a PR was opened, code merged or a service deployed.

Completion is published in the existing transaction only after fresh synchronous checks of the original snapshot, including admission release state, worker exit and executor inventory. A durable file created before grant revocation or a revision change is an orphan, not a successful completion. Unknown stop, failed verification, stale epochs and unpublished receipts cannot be queried as completed contracts. Repair uses new invocation/effect/context evidence and cannot transfer prior candidate checks.

Existing cancellation and reconciliation behavior is unchanged. This does not add arbitrary checkpoint restart, remote publishing, a filesystem sandbox, a hermetic test environment or provider attestation. Parent integration must separately validate actual daemon factories, platform workers, full regression and startup budgets.
