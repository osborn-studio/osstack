# Public follow-up delivery ledger (O2a)

This increment implements local preparation, signed authorization, single-attempt dispatch, revocation and explicit reconciliation. No production transport, external target registry or authorization issuer is configured by default. Real public delivery remains **qualification_pending**. The built-in code never generates a signing key or treats a caller's actor name, approval boolean, receipt JSON, or task success as permission to send.

## Review and authority

`follow-up-delivery prepare --repo /canonical/repo --default-tenant --input prepare.json` accepts a file containing `obligation_id`, `expected_obligation_revision`, `destination_ref`, `body`, and `idempotency_key`. The body is exact UTF-8 data, not instructions. The destination reference must resolve in a host-owned registry to a fixed GitHub account, repository, issue number and immutable target node ID and expected actor node ID. Arbitrary URL/recipient/provider fields in the request are rejected. Output contains the complete frozen envelope and digests for review.

Preparation is not authorization. An external trusted authority must review and sign `authorization_subject` plus a unique `grant_id`, `issued_at_ms`, `expires_at_ms`, and `max_calls: 1` using Ed25519 over `deliveryCanonical(body)`. Host trust registration restricts the public key's purpose, canonical repository, provider, destination references and maximum validity. No issuer or private-key handling is included in this increment. A signature made with a caller-generated unregistered key has no authority.

`follow-up-delivery authorize ID --repo /canonical/repo --default-tenant --revision N --grant grant.json` imports `{ body, key_id, signature }`. Grant fields bind the exact attempt, scope, provider/account, target digest, body digest and envelope digest. Dispatch rechecks signature, key registration, exact target, expiry and O1 obligation revision **inside the transaction that consumes authorization and records started**, immediately before the transport call. Host key removal or scoped revoke before this transaction prevents sending. Revocation after it cannot undo a call already in progress.

The CLI uses the existing daemon's authenticated local RPC. Root wiring must inject host registries; requests never select a transport or public key. Constructor `FollowUpDeliveryService(db, dbPath, options)` performs no I/O/migration. Methods are `follow-up-delivery.prepare|list|inspect|authorize|revoke|dispatch|reconcile`; all require an explicit canonical repository/default tenant. Writes use the existing DB lease. Same-user database/host-registry compromise is outside this boundary.

## Results and recovery

`dispatch ID ... --revision N` performs at most one `sendOnce` call for that attempt. Missing transport, test transports without the host's explicit test flag, and adapters declaring automatic SDK retries yield `qualification_pending` without consuming the grant or creating started. Transport qualification labels are host configuration, not self-proving attestations; deployment must establish qualification separately.

A durable started row is written before the call. Disconnect, timeout, invalid receipt, process death or lost response leave started/`delivery_unknown` with consumed authority. Neither duplicate dispatch nor a new idempotency key for the same unresolved obligation can resend. A timeout's late response never silently overwrites the returned outcome. Abort is best effort and is not proof that the provider stopped.

`reconcile ID ... --revision N` calls only the registered provider's receipt lookup. The CLI cannot submit delivered=true or receipt data. A valid receipt must match provider, account, immutable target, pinned author node ID, body digest and attempt correlation; it stores bounded provider message/request IDs and its digest. Lookup failure or absence is still unknown. A future real provider must verify author, target and content from its authoritative response; this generic service cannot independently authenticate arbitrary adapter claims.

`revoke ID ... --revision N --reason TEXT` makes an unsent prepared attempt definitely_not_sent. If sending already started, it remains unknown. `inspect ID` and `list [--limit 1..50] [--after ID]` read scoped state. List uses UUID keyset order with explicit continuation, not a snapshot; concurrent inserts before the marker require a new scan. History is append-only. O1 `fulfilled_local` and external sending remain independent: delivery never resolves the promise.

Output is JSON, bounded to 64 KiB with terminal controls escaped and exact body preserved on parse. Prepare reserves room for the largest valid receipt before any send. Files must be regular, bounded, valid UTF-8, and not symlinks. `dispatch`/`reconcile` exit 0 only with `delivered` and `production_qualified`; test/sandbox evidence and uncertain/pending results exit 1, with the actual evidence still printed.

## Qualification and rollback

Local tests exercise actual SQLite transactions and signatures, two connections, CLI-to-service invocation, a SIGKILL child immediately after committed consumption, response loss, timeouts and late completion, target/author/body mismatch, key removal, revocation, scope, stale revisions and bounded outputs. Fake send counts prove local invocation behavior only; no real message is sent and no real provider delivery guarantee is claimed.

O2b must separately supply a reviewed provider adapter, explicit human target/body approval issuer, pinned credentials/account, disabled SDK retries, real sandbox receipt lookups and controlled disconnect/crash qualification. Until then retain empty production registries. To roll back, disable the command/provider registration and retain migration 45's ledger. Do not drop unknown attempts, reset grants or down-migrate a serving DB to enable retries. Outstanding uncertainty requires reconciliation or operator investigation outside automatic sending.

Revocation records a logical nondecreasing ledger time when the host clock regresses; it remains available to remove authority even then. Grant validation and dispatch still use strict wall-clock checks. Once consumed, grant status stays consumed permanently; a later revocation is a separate immutable transition event, not a rewrite of consumption. If revocation or reconciliation races an in-flight send, the stale sender does not overwrite the newer uncertainty state. An explicit authoritative lookup can subsequently prove delivery.

A completed delivery does not authorize another message. A later update for the same obligation needs a new prepared envelope, a new attempt ID and a newly reviewed signature. Unresolved attempts block this path. An expired or removed-key grant on a prepared attempt is safely unsent but continues to reserve its obligation; inspect and explicitly revoke it before preparing a replacement. There is no automatic expiry cleanup or resend.

## Daemon shutdown contract

The host must stop accepting new calls, track every `service.handle(...)` promise and await their settlement before closing the database. Transport and lookup waits have a logical maximum of 30,000 ms each (default 5,000 ms); the final ledger transaction must also finish before the handle settles. Do not close the DB merely because a shorter shutdown deadline elapsed. Uncooperative asynchronous transports can remain alive after abort, but their late fulfillment/rejection has no database continuation: the already-settled race discards it. A blocking synchronous adapter or synchronous DB lock cannot be preempted by a JavaScript timer; host adapters must avoid blocking the event loop. No background timer initiates another dispatch or reconciliation.

## Durability and clock boundary

O2 writes temporarily require `journal_mode=WAL` and verified `synchronous=FULL`; on macOS they additionally enable and verify `fullfsync`. The synchronous transaction commits before the provider call, then restores the connection's prior settings without an intervening await. Other OSStack DB behavior is unchanged. This follows SQLite's documented [WAL durability settings](https://www.sqlite.org/pragma.html#pragma_synchronous) and [macOS fullfsync flag](https://www.sqlite.org/pragma.html#pragma_fullfsync). SIGKILL tests prove process-crash recovery, not physical power-cut or storage-device qualification; the filesystem/VFS/device must honor synchronization, which remains part of deployment qualification.

Migration 45 also retains the maximum valid clock observed by O2 writes. A rejected expiry check persists its observation before returning, so a later clock rollback cannot revive that known-expired grant, even after service restart. Admission rejects a clock below this durable record. Post-send evidence and revocation use logical nondecreasing ledger timestamps, so a regressed clock does not prevent recording an irreversible result or removing authority. This is not an independent trusted time service: time never observed by the ledger cannot be reconstructed after downtime, and host-clock integrity remains a deployment requirement.

Read/list/revoke/reconcile match the original stored canonical path string without requiring its directory to remain present; they cannot rebind the record to a moved directory or follow a new symlink. Prepare/authorize/dispatch still require the live canonical directory. Thus a moved/deleted repository can be inspected and its old authority removed using its exact historical scope. Body controls are permitted as exact data but escaped in review JSON; a future provider may reject them and must not silently normalize approved text. Pagination UUID case is normalized before comparison.

## Remaining availability limits before O2b qualification

A trusted-clock excursion far into the future can conservatively quarantine future admissions until that observed time is reached. Inspection/revocation still work. There is no automatic high-water reset: silently lowering it could revive already expired grants. Reviewed clock-recovery tooling is follow-on work.

Reconciliation currently requires the original destination registration and the same qualified transport to remain registered. Retain that historical registration until uncertain attempts are resolved. A transport without receipt lookup can currently send, but cannot automatically recover uncertainty; it must not be production-qualified under this contract. Inspect/list may combine adjacent committed attempt/grant observations under concurrent writes; mutation CAS remains authoritative. These are recorded reliability limitations, not real-provider qualification. Daemon/CLI integration qualification and its final audit are still required.
