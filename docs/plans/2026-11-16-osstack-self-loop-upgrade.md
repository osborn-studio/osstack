# osstack 自循环升级方案

**日期** 2026-11-16。**基线** `osborn-studio/osstack` main `04b947aa`。
**状态** 待负责人批准。本文只含只读核对和方案，没有改任何代码或远端。
**目标** 让 osstack 配合云端 Grok Bots 成为自动开发的自循环：自动发现问题、改代码、发 PR、改 PR、验证合并、关单；只有需要负责人拍板时才找人。
**来源** Agent Autoloop `v1.7.1`（本地源码与研究报告）、Lauren Tan 在 AI Engineer Code Summit 2026 的演讲、osstack 源码核对、`2026-11-11-grok-bot-closure-delivery.md`（下称“闭环计划”）。OSBot 不作为依据。

文中的源码位置都在本次对照过（基线 `04b947aa`）。动工前仍应在各节点自己的 worktree 里再读一次。

## 1. 结论

1. **两份材料都有用，但管的不是同一件事。** Lauren Tan 讲的是地基：让 PR 默认就是对的，人才敢放手。Agent Autoloop 讲的是运行机制：循环转起来以后怎样少打扰人、不重复干活。
2. **osstack 离自循环差的不是执行能力，是三个接口。** 发现问题的入口太窄（只认 CI 真失败）；等待和停住的时候看不见；需要拍板的事散在七个入口里，大多不通知人。
3. **不要再加一套调度器。** osstack 的预算、授权、不确定结果不重发、确定性门禁都比 Autoloop 严，应保留。要学的是它的产品闭环，不是它的存储和调度。
4. **第一步仍是闭环计划的 N2–N5**（可见性、证据脚本、沙箱无人派发真链）。本方案在它之上加四项：决定收件箱、发现入口、回执修复、确定性检查。

## 2. 两份材料的启发

### 2.1 Lauren Tan：信任金字塔

| 她的做法 | 对 osstack 的含义 |
|---|---|
| 修一次 agent 的错，就把它变成确定性检查，不在规则文件里加一句话 | `AGENTS.md` 里有多条只靠文字的规则（见 U6）。每条都该问：能不能变成 lint、测试或运行时拒绝 |
| 需要微妙技巧才能用对的东西，直接禁掉，只在框架内部放行 | osstack 已这样做了一部分：所有 git 写入必须过 W13 的门，有静态扫描测试。应推广到临时目录、正式数据库、暂存方式 |
| 用目录结构和依赖图禁止错误的 import | osstack 有启动依赖图预算和导出清单检查。包边界（`@osstack/core` 的枚举 export map）已是硬约束 |
| 禁掉绝大多数注释，因为注释不强制、会过时、还给 agent 找借口 | 不建议照搬。osstack 的注释多数在解释不变量。可取的是：评审时把“注释里的借口”当作缺一条检查的信号 |
| 评审变成看验证产物：视频、截图、图表、形式化验证 | 对应闭环计划的 N3：一条链是否合格由程序判定，评审看证据记录而不是看聊天 |
| 用 TLA+ 验证核心流程 | osstack 已有：`docs/design/specs/bridge.tla`，穷举 TLC 通过，变异全部被捉到 |
| 撤回率稳定在 0.5%，才敢让 agent 自己合并 | osstack 目前没有这个数。U2 要补“合并后被撤回或热修”的统计，作为放开自动合并的依据 |
| 先打地基，再自动化；循环产出垃圾时，自动化只会产出更多垃圾 | 顺序上支持先做 U1–U3 和 U6，再扩大发现入口和修复轮数 |

**不适用的部分：** 她的数字（每月 11000 个 PR、227 个贡献者）来自一个大团队和单一产品代码库。osstack 现在的瓶颈不是产量，是一条链能不能无人值守走完。

### 2.2 Agent Autoloop：运行机制

| 机制 | 它怎么做 | osstack 现状 |
|---|---|---|
| 问题卡片 | 一张卡有标题、正文、选项、推荐项；第一次回答生效，重复回答无效；答完用同一个 CLI 会话接着干 | 会话决定已有同等甚至更严的检查（版本、内容摘要、来源未变）。**已核对** `packages/core/src/state/attention-actions.ts:99-206` |
| 通知与重发 | 飞书、桌面、webhook；0–55 分钟内重发 9 次 | 只有本机 spool 目录，且要开 `OSSTACK_ATTENTION_NOTIFY=local`。**已核对** `packages/cli/src/daemon.ts:4317` |
| 回执修复 | 活干完了但结果格式坏了：让同一会话只重述结果，最多 2 次；不变成业务重试 | 没有。结果格式坏了就整轮重跑，或停下等人（见 U5） |
| 按事项聚合 | 同一事项的新事件并入已排队的那一轮，不另起一轮 | 全部靠轮询，没有事件入口：CI 观察 30 秒、评审链 60 秒、停止链 10 分钟。存储层已保证一个 PR 不会起两轮模型；但 CI 链是“先到先得”，之后的事件不会并入（`packages/cli/src/contained-mission-github-ci.ts:275-279,309`） |
| 确定性故障模拟 | 带种子的随机模拟 20 万步，覆盖丢响应、重复提交、重启、晚到结果、时钟回拨、重复回答；另有 8! 种顺序穷举 | 修订链、主机进程、图运行时各有属性测试、崩溃点测试或 TLA+ 模型。会话转发、attention 回答、loop 执行器三处只有手写的例子测试，没有属性测试、崩溃点或模型 |
| 一次无害试跑 | `try` 命令发一张“选颜色”的卡，走完“接活、提问、回答、续办” | 没有 |

**它明确的弱点，不要学：**

- `askFirst` 只是提示词，工具调用前没有拦截。osstack 的门禁是执行路径上的拒绝，不能退回到提示词。
- 它是至少一次执行。osstack 对“可能已发送”不自动重发，这个取舍要保留。
- 卡片链接不是认证，谁拿到都能答。osstack 接外部入口时必须绑定身份。

## 3. 自循环六个环节的现状

| 环节 | 已有证据 | 缺口 | 对应升级项 |
|---|---|---|---|
| 发现问题 | 只认 GitHub Actions 的真实失败（沙箱 #30、#31） | Watcher 的 `verify-*` 失败只出现在聊天里；没有定时巡检入口；loop 的 `git_diff` 发现没有稳定 id，每轮都会重新发现同一任务 | U4 |
| 改代码 | 同 PR 一次快进修复 | 每条链只一轮；文件白名单很窄 | U8 |
| 发 PR | App A 发布 | 无 | — |
| 改 PR | 正式评审驱动的修订有 5-G 第四轮 13/13 | 云端评审身份（App C/D）没接上 | U8 |
| 验证与合并 | Watcher 审批加 App E 合并（沙箱） | 主仓库的 #436 靠 Chief of Staff 派发；等待阶段不可见；合格与否靠手写链接 | U1、U2 |
| 找人拍板 | 七个入口各自为政 | 没有统一列表；除会话决定外基本不通知 | U3 |

## 4. 升级项

优先级：P0 是自循环成立的前提；P1 是“突破”所在；P2 降低长期成本；P3 等数据再定。

### U1（P0）沙箱无人派发的真失败链

即闭环计划的 N4、N5，本方案不改内容。

- **复用：** #437、#438 合入的 CI 失败读取、修复、App E 合并；沙箱四条 `active` 规则；两条沙箱 Routine。
- **要改：** 无代码改动。需要负责人在 Grok 端确认 Routine 启用状态。
- **验收：** 从登记到 `github_ci_chain.state=closed` 无人派发；Docker 停止；另做两条演练（推送后重启 daemon；推送前撤销许可）。

### U2（P0）等待可见、合格可判

即闭环计划的 N2、N3，加一个撤回率统计。

- **复用：** `mission status --json` 的 `github_ci_chain`；`packages/cli/src/bridge-stats.ts` 的聚合框架。
- **要改：**
  1. `github_ci_chain` 现在只有四个后段状态（`closed`、`merge_held`、`merge_reserved`、`merge_reconciling`），合并动作之前是 `undefined`（`packages/cli/src/contained-mission-host.ts:129-144`）。等待类事件只在事件尾部里。补上等 CI、已观察到失败、修复中、修复失败、等 Watcher、等 Merger，以及每段的等待起点。
  1. 扫描出错现在只打一行日志（`contained-mission-github-ci.ts:302`）。改为留一条持久记录，否则读 GitHub 持续失败时链看起来只是“在等”。
  2. 新增多链列表（目前没有 `mission.list`）。
  3. 只读证据脚本：给定仓库、PR、Mission，输出一条证据记录和 `qualified` 判定。
  4. 新增 CI 链统计。`bridge-stats.ts` 现在只读评审链的表，且有七项指标标为 deferred（`bridge-stats.ts:44-52`）。至少补：每跳等待时长、首轮通过率、合并后 7 天内被撤回或被热修的比例。
- **验收：** 对沙箱 #31 输出 `qualified:true`，对 #29 输出未关单及原因；工作时间外静止的链显示“等待 Watcher，自某时起”，而不是无状态。

### U3（P0）决定收件箱：把需要拍板的事接回来

这是 Autoloop 最值得学的一点，也是 osstack 最散的一处。

**现状。** “等人”的入口至少七种，各有各的命令：

| 来源 | 等人的状态 | 现在怎么答 | 通知 |
|---|---|---|---|
| 会话决定 | `awaiting_decision` | `attention.answer`（查版本、内容摘要、来源未变） | 本机 spool，需开关 |
| Contained Mission | `awaiting_decision`、`needs_reconciliation`、`stop_unknown` | `mission.decide`，9 种决定 | 无 |
| CI 修复 | `awaiting_decision(publication_pending)` | `mission.approve_ci_repair` | 无 |
| 修订链 | `ready_for_human`、`awaiting_decision` | `mission.chain_decide`；`grant_revisions` 要本机私钥签名加终端确认 | 无 |
| CI 试点放行 | 无状态，靠私有文件 | 负责人手工改文件 | 无 |
| Autonomy | `awaiting_approval` | `autonomy approve --decision FILE`（外部签名） | 发件箱有，生产没接发送器 |
| Hermes 运行 | `approvals` / `clarifies` 为 `pending` | `approval.resolve` / `clarify.resolve` | 靠 kanban 拉取 |

没有任何一个查询能列出全部。最接近的 `attention.inbox` 只覆盖单个 scope 的会话决定（`packages/cli/src/supervision-service.ts:441-460`）。

**设计。** 不新建第二套状态机。attention 已经有完整的“条目、回答、回执、不确定结果”模型，把其他来源**投影**成 attention 条目，回答时**转发**到各自原有的命令。各来源仍是自己状态的唯一权威。

```text
Mission / 链 / CI 修复 / Autonomy / Hermes
        │ 只读投影（来源 id + 来源版本 + 内容摘要）
        ▼
   attention 条目 ──► 发送器 ──► Grok Bot 聊天 / 桌面 / 本机 spool
        ▲                              │ 负责人选一项
        │ attention.answer（幂等键、版本、摘要、身份）
        └──────── 转发到原命令（mission.decide 等）──► 原状态机继续
```

- **可直接复用：**
  - 表与状态：`attention_items`、`_actions`、`_deliveries`、`_reminders`、`_dead_letters`（`packages/core/src/state/migrations.ts:1781-1862`）。
  - 回答检查：同一 `action_id` 不同内容报冲突、相同内容算重放；条目必须 `open` 且版本与内容摘要一致；来源变了报 `source_changed`（`attention-actions.ts:110-159`）。
  - 不确定结果：`answer_uncertain` 状态和 `reconcile`（`attention-actions.ts:207-364`）。
  - 过期提醒：`attention-reminders.ts`。
  - 出站发送：本机 `codex/grok-webhook` 分支的单次 POST 适配器（限定官方地址、禁止跳转、8 秒超时、`unknown` 不重发）。
- **需要改：**
  1. **投影器。** `projectDecision` 现在只接会话决定（`attention-observer.ts:441`）。为 Mission、链、CI 修复、Autonomy、Hermes 各加一个只读投影，条目里带来源种类、来源 id、来源版本、允许的选项和推荐项。
  2. **回答转发。** `attention.answer` 现在只会续接会话（`daemon.ts:1345-1349`）。按来源种类转发到 `mission.decide` 等原命令。
  3. **补幂等。** `mission.decide`、`approval.resolve`、`clarify.resolve` 没有客户端幂等键和期望版本。转发前必须补上，否则响应丢失后重试会重复执行。`approval.resolve` 现在恒写 `accepted`，要改成按回答写。
  4. **跨 scope 列表。** 新增一个列出全部未决条目的只读查询。
  5. **身份。** `attention.*` 现在只靠 socket 文件权限，回答不绑定任何主体。接外部入口前，回答必须带 `mission.*` 那套凭据（`engineering-access.ts:9-18`），并记录是谁答的。
  6. **发送器。** 生产启动时没有传 `notificationSender`（`bin.ts:719-734`）。接上一个真正的发送器，并给失败投递设重发上限。
- **必须留在本机的决定。** `grant_revisions`、风险审批、任务授权、Autonomy 审批都要本机私钥签名（`attention-actions.ts:63-69`，`contained-mission-grant-command.ts:40,96,136`）。这类条目仍进收件箱并通知，但卡片只显示“需在本机执行”和确切命令，不提供远程回答。这条边界不放松。
- **外部入口的规则。** Bot 只做展示和转交。卡片正文、Bot 回传的自由文本一律当数据，不当指令。同一条目只认第一次有效回答。
- **验收：**
  1. 一个查询列出七类来源的全部未决条目，每条有来源、等待起点、选项、是否需本机签名。
  2. 对一条 Mission 决定：远程回答一次生效；同一 `action_id` 重发得到重放结果；Mission 在此期间变了得到 `source_changed`，原状态机不动。
  3. 回答转发途中杀掉 daemon：条目进入 `answer_uncertain`，重启后只读对账，不重复执行决定。
  4. 需签名的条目不能被远程回答，返回 `signed_approval_required`。（2026-11-24 订正：统一入口 `decisions.answer` 实际返回 `local_only`，并附本机命令；`signed_approval_required` 是会话来源自己的错误码。边界见 `docs/guides/pending-decisions.md`。）
  5. 无凭据或凭据无写权限的回答被拒。
  6. 一次无害试跑：发一张测试卡、回答、看到“已续办”，全程不触碰任何真实 Mission。

### U4（P1）扩大发现入口

自循环现在只在 CI 变红时才启动。这是“自动发现问题”还没突破的主要原因。

- **复用：**
  - #431–#434 的本地失败授权与回执合同、`readCiFailureHints`、`LocalFailureIntakeStore`。注意它的表定义自称“未注册”，没有任何迁移引入它（`packages/core/src/state/engineering-local-failure-intake-ddl.ts:1`），要用就得先注册迁移。
  - 现有的有界修复入口：W13、文件白名单、一次性发布许可、同 PR 更新。
- **需要改：**
  1. **Watcher 独有的失败（handoff 的 D3）。** CI 全绿但 `verify-*` 失败时，结果现在只在 Grok 聊天里。定一个结构化结果合同：仓库、PR、完整 head 和 base、技能版本、失败码、证据引用、去重键。载体用 GitHub 上的持久对象（例如指定格式的 check run），不用普通评论，也不用聊天文本。优先让同一失败能在受信 CI 里复现，这样就能走已有的 CI 修复链。
  2. **定时巡检入口。** 参照 Lauren 的做法（每次发版自动 fuzz，发现一个 bug 开一个带修复的 PR）：一个定时 Routine 运行 `verify-osstack`，把发现写成上面的结构化结果，osstack 据此登记 Mission。
  3. **给 loop 的发现结果一个稳定 id。** `git_diff` 发现的任务用 `randomUUID()` 作 id（`packages/loop/src/discover.ts:71`），而去重只比对已完成任务的 id（`loop-engine.ts:564-568`），所以同一个改动每轮都会被重新发现。改为用内容摘要生成 id，并跨来源去重。这是三处里最小、最先该修的一处。
  4. **CI 链并入后续事件。** 现在一个根 Mission 只记第一次失败，也只派一次修复（`contained-mission-github-ci.ts:275-279`）。放开多轮（U8）之前，先让同一 PR 的后续失败并入同一事项，而不是被丢掉。
  5. 各种入口都只产生“诊断请求”，是否修、修哪些文件仍由 osstack 的受保护配置决定。
  6. **指令与数据分离，作为硬规则**（负责人 2026-11-16 同意）。凡是外部写入的内容（Watcher 的验证结果、定时巡检的发现、issue 或 PR 的文字）一律按数据存放，并标为参考材料；它永远不进入提示词的指令部分。能做什么只由本机受保护的配置决定。
- **验收：** 沙箱里一次真实的 `verify-*` 失败：可信结果被读到，登记一条 Mission，一次受控修复，新 head 复验通过，审批、合并、关单。负向用例：来源不可信、旧 head、重复结果、无法复现，各自停住并有原因。

### U5（P1）区分业务失败与回执失败

- **Autoloop 的规则：** 活干完但回执读不出时，恢复同一会话，只让它重述结果（“不要重做，不用工具”），最多 2 次。修复失败不变成业务重试，而是保留原结果、丢弃回执、发一张卡。
- **osstack 现状：没有这条路径，三处都把“报告坏了”当成“活没干成”。**
  - **loop 执行器。** 协议错误（`missing_done`、`invalid_done_payload` 等七种，`packages/loop/src/executor.ts:60`）一律记为 `failed`。工作区改动保留，但验证器会加一条 `execute.outcome_not_completed`，即使检查全过也不算通过（`verifier.ts:119-127`）。下一轮是带着这条反馈的**整轮重跑**（`loop-engine.ts:1144-1170`）。
  - **评审者的报告。** 结构化评审格式坏了，记为 `verify.review_artifact_invalid`（`verifier.ts:874`），结果是让**写代码的一方重做**。
  - **偏差声明行。** `OSSTACK_IMPLEMENTATION_DEVIATIONS` 缺失或格式错时返回空数组，不报任何错（`packages/agents/src/adapters/deepseek-command.ts:343-372`）。偏差声明被**静默丢掉**，这比重跑更糟。
  - **Contained Mission。** 补丁缺结束标记等情况停到 `awaiting_decision`（`patch_invalid:<原因>`，`contained-mission-runner.ts:488`）。唯一出路是人做决定，而 `extra_repair` 会起一整轮新的执行并计入预算（`:258-265`）。
- **需要改：**
  1. 新增一类失败码，把“工作完成、报告无效”与“工作失败”分开。
  2. 在 `executor.ts:248-251`、`verifier.ts:870-876`、`contained-mission-runner.ts:488` 三处插入“只修回执”：恢复同一会话，只要求重述结果，不执行工具，上限 2 次，不计入业务轮数。
  3. 评审报告无效时，重试的是评审者，不是写代码的一方。
  4. 偏差声明格式错要有自己的失败码，不能静默变成“没有偏差”。
  5. 仍失败则保留工作区、按 U3 发一张决定卡。
- **验收：** 注入一个格式错误的结果：工作区改动保留，执行器没有被重新启动，回执修复后验证照常进行；连续两次修复失败后停在待决定，预算里业务轮数没有增加。

### 9.3 实际运行中学到的

- **本地门禁要与 CI 对齐。** 两天内有四次 CI 失败来自本地没跑的检查：导出清单、Biome lint、新迁移在 CLI 的登记、迁移列表的测试。现在的规则是：每个节点跑 `pnpm lint` 和导出清单检查；带迁移的节点在 CLI 的只读视图和原生升级门登记，并完整跑一遍 CLI 套件。
- **合并后的结果要重新验证。** 两个各自通过的 PR 合并后曾让 `main` 上的确定性规则失败。只做冲突检查不够。
- **多个迁移并行会互相冲突。** 迁移注册表和若干测试钉死了迁移列表。按编号顺序合并，后合的变基。
- **CLI 启动依赖闭包有上限。** 每个新的 core 状态模块都会占用名额，需要把非每次调用都用到的包移出 `bin.ts` 的静态引入。
- **这台机器一次只能跑一个重任务。** 多个会话并行开发时，构建、测试和代码生成任务通过一把先来先得的锁排队。
