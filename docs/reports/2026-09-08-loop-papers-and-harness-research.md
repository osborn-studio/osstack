# Loop 论文、Harness 经验与 OSStack 升级方向

日期：2026-09-08。状态：研究与需求增补，尚未实施。关联：[主 RFC](../design/2026-09-08-collaborator-and-self-improvement-rfc.md)。

## 阅读范围与证据等级

用户先后粘贴《刚刚，GPT-6 Astra 背后的 Loop 技术全被挖出来了》和《一篇 Loop+Harness 的自进化 Agent 最新综述》正文。本报告据此查找一手资料；公众号标题、技术类比、作者实验结果与 OSStack 的已验证能力分开记录。最早的另一篇微信链接仍未取得正文。

论文存在、作者报告结果、独立复现、生产泛化是不同证据等级。本文没有运行论文模型训练，也没有开展 OSStack 收益实验。

## 1. 四种循环需要分开设计

| 层次 | 改变什么 | OSStack 能做什么 |
|---|---|---|
| 模型内部计算 | 隐状态、层复用、深度与模型权重 | 闭源 API 下不能直接控制；只使用适配器明确支持的模型、effort 和预算参数 |
| 单任务执行 | 规划、工具调用、验证、返工 | 协作者按证据和委托接续；按失败原因选择修复或停止 |
| 跨任务学习 | 可复用技能、事实记忆、检索与恢复机制 | 留存有来源的经验，检验其在新任务上的价值，修订或退役 |
| 系统版本演化 | OSStack 工具、调度器及自身代码 | 在隔离候选中修改，经独立评价与授权晋升；控制包走独立变更流程 |

更深的模型计算不自动产生跨任务学习；保存更多经验不自动提升交付质量；模型意见也不产生 GitHub 审批或发布权限。

## 2. 前一篇文章的五组论文核查

| 一手来源 | 核实结果 | 不能推出的结论 |
|---|---|---|
| [Universal Transformers](https://arxiv.org/html/1807.03819v3)，§2.2 | 既研究固定深度，也提供按位置自适应停止 | “循环模型每个 token 一律相同计算量”并非通则 |
| [Scaling up Test-Time Compute with Latent Reasoning: A Recurrent Depth Approach](https://arxiv.org/html/2502.05171v2)，§5–6 | 3.5B 是实际参数；50B 是计算量等效口径。不同任务有饱和和非单调现象 | 不能说 3.5B 已证明达到 50B 模型能力，也不能保证多循环总有收益 |
| [Training-Free Looped Transformers](https://arxiv.org/html/2605.23872v1) | 冻结权重、循环内部层并用阻尼更新；部分知识选择题配置改善，亦有负收益；附录报告完整 decode 循环存在额外耗时 | 无额外训练不等于无额外推理成本；封闭 API 的多次调用不能直接复现此方法 |
| [LoopCoder-v2](https://arxiv.org/html/2606.18023v1) | R=2 指首次计算加一次循环；对照是训练与推理 R 匹配的不同配置。PLT 的延迟/KV 主张依赖其专用架构 | 不能把“Only Loop Once”改写为所有 Agent 最多运行两轮 |
| [Loop the Loopies!](https://arxiv.org/html/2607.16051v2)，§2、§6 | 研究 layer-loop 与 model-loop；equal-compute 主要按固定硬件下实际训练时间配平，非相同 FLOPs；作者承认尚未系统研究推理计算与广泛 agentic 能力 | 不能用发表时间接近证明 Astra 采用该架构，也不能证明 OSStack 增加 API 轮数会更便宜 |

在本轮查阅的 [Astra 官方发布页](https://openai.com/index/gpt-6-astra/)及[系统卡](https://deploymentsafety.openai.com/gpt-6-astra)中，未找到具体采用 Loopie／layer-loop 的披露。这是查证范围内的证据缺口，不是断言内部一定没有该技术。

官方已明确公开的跨窗口笔记、历史上下文检索及异步澄清更贴近 OSStack：保留可恢复工作状态，用户回复到达时继续吸收方向变更。把这些作为 Harness 设计参考，不把它们当成特定神经网络架构的证据。

## 3. 可直接检验的工程假设

### 按失败原因分配下一步

测试失败可定向修复，工具环境故障先诊断环境，验收歧义保留问题并继续独立工作，授权越界停止对应动作。是否增加模型推理、换工具或换评审者，都须在现有预算与能力内。不能因为任务“难”就默认无限加轮数。

改变工具集合、文件摘要或模型自称“换了假设”仅能提示活动变化。它们不证明质量进步。有效证据应关联冻结验收结果、阻塞问题的实质解决与当前工件；暂时没有净收益的探索仍可消耗有限预算，但不能不断重置预算。

### 先观测，再决定是否保存多个候选

先记录“中间候选是否优于最终候选、退步发生在哪里”，并复用已有 Git/工件版本。频繁退步得到证据后，再实现最佳有效候选选择。候选必须按同一受保护验收比较，并在当前目标分支与环境重新验证；代码作者新增的测试不能自行替换决定晋升的验收标准。

### 恢复笔记不等于事实与授权

首版保存目标、冻结验收、工具证据引用与工件版本；假设和未答问题可作为明确标注的不确定信息。恢复时检查版本、撤销及引用可达性。原始历史可按需检索，摘要不取代证据。跨模型切换还需记录当前可用工具和适配器版本，避免沿用上一模型的工具格式。

### 实验设计

- 比较固定 1／2／3 次执行尝试、按失败类型分流、自适应预算策略。这里一次尝试指工程层执行及其验证，不指模型内部 recurrent depth。
- 冻结任务、模型、工具、验收与环境；采用共同成本/时限上限，并报告实际总消耗。共用上限不等于相同实际计算。
- 在任务层随机分配或配对，预先固定分层和分析口径。不能事后比较“完成一轮”和“完成多轮”的任务通过率，以免混入任务难度和停止策略的选择偏差。
- 以配对差值及不确定区间判断是否达到事先定义的最小有用效果；区间重叠不等于无效，样本不足不等于成功。成本容忍范围由产品目标确定，不使用无依据的固定倍率。
- 候选保留、恢复笔记和自适应调度分开消融。策略制定与筛选使用开发集，最终冻结候选限次查询独立晋升集；按时间采样的新任务检验持续效果。
- 计入失败、评审、检索及环境恢复的成本；必须停止、误拦截和无进展任务也在样本中。固定两轮可以成为胜出的基线，但不是从模型架构论文推出的产品上限。

## 4. Harness 综述带来的新增要求

公开入口：[作者资料库](https://github.com/FrontisAI/Awesome-Self-Improving-Agents)、[作者 PDF](https://github.com/FrontisAI/Awesome-Self-Improving-Agents/blob/main/Self_Improving_Agents.pdf)、[OpenReview](https://openreview.net/pdf?id=IUltZSgLMm)。OpenReview 本次触发浏览器验证，正文从作者公开 PDF 核实。PDF 封面日期为 2026-06-25，署名单位包括清华大学与 Horizon Research, Frontis.AI；作者仓库标为 OpenReview Archive，没有查到已完成同行评审的一手证据。

§2 区分原始轨迹与筛选、归因后的经验；§7 区分内容资产、任务代理机制和独立持续 meta-layer，通用元演化仍属开放问题；§8 要求新任务收益、旧能力保留、跨时间稳定性、成本与归因。本文用其分类梳理可修改对象，不把它视为通用自进化已经实现的实证。

对 OSStack 的新增产品要求是：能回答“哪条经验在什么新任务中被用过、产生什么可核验结果、何时应撤销”。仅证明循环持续运行、技能已入库或同类任务成功均不够。

```mermaid
flowchart LR
  T[真实任务与工具回执] --> C[有来源的候选经验]
  C --> V[在新任务中独立验证]
  V --> A[有限范围启用]
  A --> U[记录加载与可观测采用]
  U --> O[验收与延迟反馈]
  O --> R[保留 修订 或退役]
  R --> C
```

记忆保存有来源的事实，技能指导重复执行，偏好记录用户选择。三者不能相互冒充。经验策展是一项职责，可由现有调度器触发有限工作，不要求新建一个全天运行的模型角色。

第一份可见产物应是一张经验效果卡：来源故障、候选变更、适用范围、基线与候选版本、冻结任务集及裁判、实际成本、配对结果、未解决反例和当前启用状态。没有跑过实验的字段显示“待验证”；不用虚构数字演示已改善。

### 技能研究给出的反例

| 来源 | 已核实的限制与设计启发 |
|---|---|
| [SkillsBench v4](https://arxiv.org/html/2602.12670v4)，§5.1.1、附录 D.6 | 自生成技能在三个被测配置中出现负收益；论文承认发现失败、生成与求解干扰、错误内容等混杂，部分配置 effort 不一致。不能推导所有自动生成技能无效；要分开测试技能生成、加载和求解 |
| [SkillsWild](https://arxiv.org/html/2604.04323v1)／[作者代码](https://github.com/UCSB-NLP-Chang/Skill-Usage) | 从强制加载精选技能到大池检索，部分收益被检索困难消耗；当前任务改写也有负例且需要额外探索。库规模和技能命中率不能代替端到端收益 |
| [SkillOS](https://arxiv.org/html/2605.06614v1) | 冻结 executor 权重、训练独立 curator 修改技能库，评价后续相关任务。只支持其具体实验范围，不能推出无限生产自升级；本轮未找到作者官方代码 |
| [SkillOS 独立复现修订记录](https://github.com/belt-sh/skillos/blob/main/docs/repro_report.md) | 该团队撤回过被认证故障污染的退化结论，并更正旧基线导致的收益夸大。它不是官方实现；旧搜索摘要不可代替当前报告。OSStack 应保留基础设施异常和实验撤回历史，重测同期基线 |

基础设施错误不能静默丢弃，也不能伪装成模型回答。报告系统交付率时必须计入造成的未交付与成本；分析技能能力效果时另列 `infra_error`、缺失与有效配对数，按预先规则重试/补测，不能只删除候选组的坏结果。

候选造成的超时、无效调用、额度耗尽或环境破坏属于候选效果，不能重标为外生故障后排除。主要结果按原分配组纳入全部任务；按预先规则排除外生故障的有效配对分析只作补充，报告各组缺失和补测分布。

### 源码映射：最先应修的证据语义

源码基线仍为 `c9c3cd2`，以下是静态审计，没有打开服务数据库：

- `packages/core/src/state/lessons.ts:47,65,117` 的 `verified_count` 混合首次入库、不同 run 再次观察，以及同技术栈任务成功。`packages/cli/src/bin.ts:6207` 只传 loop_id 与技术栈，没有绑定 lesson 使用记录。因此旧计数不能证明经验有效；迁移应保留为历史混合计数，不能反推观察类型或验证历史。后续修复状态见[实现记录](2026-09-08-collaborator-foundation-implementation.md)。
- `packages/loop/src/lesson-draft.ts:218` 的人工 promote 能追加 SKILL.md 并移动草稿，未包含独立效果评测。它是已有编辑流程，不是自动经验晋升门禁。
- `packages/core/src/state/feedback-assets.ts:7` 有来源 trace 与候选状态；`packages/core/src/state/memory.ts:108,124` 已有替代和归档；`packages/skill-registry/src/manifest.ts:13` 有来源版本。应扩展这些结构，而非再造平行知识库。
- `packages/autonomy/src/progress-budget.ts:43` 把文件及验证 hash 同时变化也视为 improved。这是停滞启发式，不能直接用于自改进收益判定。

最小增量是不可变经验版本、实验分配/加载事件、任务验收与成本关联。初版不新增“确定因该技能而成功”字段；实际脚本执行可记客观事件，模型自报采用只记自报。随机分配与配对撤除实验负责估计因果效果；有加载记录仍不等于有效。

### 第一项可推翻的实验

选一个真实、可重放的工具失败，在新任务上比较：现有基线、加载候选技能、直接修正工具接口。三组冻结任务与验收，按任务配对、随机执行顺序并隔离状态；同步测旧任务及不应触发该经验的反例。首次只有一个技能时用 Git 历史与工件引用管理，不预建复杂技能图谱。

首实验测定向注入候选内容的效果，尚未覆盖真实技能库检索。未加载仍留在原分配组，加载状态只作诊断；不能据此宣称检索或完整学习闭环已经有效。

若接口修正胜出，就把经验固化为受评测的代码改进。若仅原故障复现通过、新任务无收益，则不能宣称泛化。候选未被加载、被加载后无改善以及成本过高分别报告。无证据或效果不稳定时维持原版本；用户尚未确定的成本容忍度和最小效果阈值必须在真实实验前冻结。

## 5. 工业界公开材料的直接借鉴

| 一手材料 | 产品启发与适用边界 |
|---|---|
| [Cursor：持续改进 Harness](https://cursor.com/blog/continually-improving-agent-harness)，2026-04-30 | 联合离线评测与真实使用观察，按模型和工具区分错误；更贵的摘要模型也可能不值得。OSStack 应允许删除无效上下文、技能和调用，并在底模变化后重新检验旧经验 |
| [Cursor：real-time RL](https://cursor.com/blog/real-time-rl-for-composer)，2026-03-26 | 公开记录了丢弃无效工具调用造成逃避负反馈、过多澄清规避编辑等问题。OSStack 必须完整计入失败与未交付，不能优化“少打断”或“已记录成功”单一指标 |
| [Composer 2 技术报告](https://cursor.com/resources/Composer2.pdf) | 同部署工具与 Harness 的训练环境说明环境一致性很重要；该公司拥有训练底模的条件，不代表 OSStack 调闭源 API 就能做同样的权重更新 |
| [Anthropic：长运行 Harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)，2025-11-26 | 结构化进度、可运行验证与交接支撑跨窗口任务；这些可先用已有工件/历史完成，无需立即建设知识图谱 |

真实用户反馈也不是绝对真值：未删代码可能只是尚未审阅，用户没有回复不能记为满意。OSStack 应保留明确验收、返工与观察期未结束等不同状态。

## 6. 与已有路线的关系

这些研究不改变主 RFC 的先后依赖：先解决真实等待、授权接续与状态真实性，再形成一个真实候选的独立评价，最后扩展持续演化。自适应计算和通用记忆架构属于可选实验；经验效果归因是宣称“自我改进”前的必要证据。

GitHub 身份、独立云端 App 和委托范围沿用[身份 RFC](../design/2026-09-08-github-identity-and-cloud-steward-rfc.md)。学习不能把技能中的文本转换成组织审批权。组织内经验共享的初始建议是原仓库先验证、跨仓库再验证；用户选择尚待记录。
