# 候选执行控制：Fable 5.1 两轮实现契约挑战

日期：2026-09-09。关联[实施交付说明](2026-09-09-improvement-execution-control.md)和[下一阶段计划](../design/2026-09-09-autonomy-next-implementation-plan.md)。

## 范围和结果

本轮实际执行两次 `claude-fable-5-1` 无工具调用，两次 `is_error=false`，`modelUsage` 均包含该模型及 CLI 辅助 Haiku。使用 safe mode、临时目录、空 MCP、空工具集、禁用 slash commands 和会话持久化。仅发送原创通用契约及反驳，没有源码、私有审计、组织配置或凭证。这里是设计挑战；实际代码与测试由 Codex 在本地审核。

采纳：新记录不能通过缺省参数创建无 owner 旁路；停止要覆盖无 owner 历史记录；人工停止与执行不确定分别记来源；完整基线从一个查询快照计算，停止请求作为重叠标签不能再加进互斥状态总数；不确定执行不能普通失败后放开重试。

修正与分歧：

- 停止后必须有 `stopped` 终态的建议未采纳。只有停止请求时保留 active 占用，状态明确显示为未决，不承诺杀进程。
- `stop_acked_at` 只能证明协调代码观察到了停止，不能证明子进程或已发出的 IO 不再写入；Fable 把 ack 当人工安全清理依据的建议未采纳。真实隔离、进程终止与恢复仍是后续切片。
- 没有把所有历史 API 直接删除：所有新 claim 自动绑定 owner；已有无 owner 记录仍可用历史签名更新，但停止后一律拒绝。新记录的更新必须传入 claim 返回的 worker，属于需要发布说明的 API 收紧。
- SQLite 写事务可能遇到 BUSY 而失败，不声称一定让两个并发调用都成功返回。停止与完成的两种已提交先后次序均通过独立连接测试，失败不能覆盖胜方。没有声称已做上百次多进程故障注入。
- 命令返回非零可能来自信号终止；当前旧命令回执缺少充分分类字段。因此本片保守保留这类验证的占用，标记 system_indeterminate；普通 gate 失败也可能落入其中。下一片应提供结构化进程退出证据来减少误拦截，不能用解析错误文案代替。
- 候选 `candidate_failed` 只在本地执行链的已确认阶段之后由确定性校验失败产生。本片仍依赖现有可信本地操作员边界，不宣称适用于恶意后台 worker；OS 级隔离和停写证明没有交付。

模型观点不能替代测试结果，以下回复中的“必须”“唯一依据”等保留为模型原话，不表示已采纳。

## 第 1 轮 Fable 原始回复

以下基于契约文本推理，未见源码，均为设计层假设，需用测试验证。

**1. 新旧API混用：无owner旧记录绕过代次校验**
契约说旧记录无owner保持兼容，终态提交核对owner+代次。风险：若"无owner"被实现为"跳过核对"，一条旧式running记录可被任意路径提交终态，也可在stop后仍完成提交，stop失效代次对它无效。更危险的是新执行经旧API路径被写入无owner，等于新建了免校验记录。
测试：用新API创建绑定owner的执行，再经旧API（无owner参数）对同一执行提交verified；期望拒绝。另测：stop一条无owner旧记录，再用旧API提交终态，观察是否被计入verified而非stopped——若成功，说明代次校验存在旁路。

**2. stop与running终态的记账竞态**
契约保证stop原子写停止原因并失效代次，终态先发生则返回既有结果，但阶段边界检查与终态提交之间存在窗口：执行器已通过检查、尚未提交，此时stop落地。提交若只校验代次，会被拒绝——那么该执行既无终态又不再运行，占用不释放（契约明确不释放），进入永久悬挂，且基线里"停止请求"与"未决"重复计数或都不计。
测试：在提交前注入延迟，并发stop，断言：终态恰好一个（stopped或verified），不能两者皆无；重复stop返回同一结果；基线中该记录只出现在一个桶。再测：stop后执行器仍完成模型阶段并尝试提交，确认不会以"成功"覆盖stopped，也不会因未知代次抛出未分类错误。

**3. unknown错误终态与占用释放**
契约要求unknown费用不置零，且不自动恢复。未明确：执行器崩溃、shell被外部杀死等未分类错误是否写终态、是否释放单任务占用。若不写终态，占用永久锁死且无lease抢占，符合契约却是自我拒绝服务；若写failed并释放，则"不声称进程停止"与"释放"冲突——子进程可能仍在写worktree。
测试：杀死执行器进程（非通过stop），检查记录状态、占用、worktree登记三者一致性；随后新执行尝试领取同任务，验证要么被拒绝（占用未释放），要么原worktree已被登记为不可用。任何"占用释放但worktree仍被旧进程写入"的组合即为漏洞。

**4. 全量基线快照一致性**
基线声称只读、全量、非分页统计。若各计数分别查询，在并发写入下总数≠各桶之和，或同一记录跨桶。费用unknown不置零，但求和时可能被隐式当作0；lifecycle age若用当前时间减创建时间，对terminal记录会持续增长，混淆为耗时。
测试：并发执行状态迁移时反复生成基线，断言总数恒等于各桶之和且无记录重复；含unknown费用的集合总费用应标unknown而非数值；同一terminal记录两次基线age应相同。frozen request摘要与配置来源应对同一执行两次一致。

经验事实边界：以上未验证任一实际行为，仅指出契约文本未封闭之处。

## 第 2 轮 Fable 原始回复

以下均为对契约文本与回应的推理，无源码验证；标"实证"处需测试确认。

**本片必须修正**

1. stop先赢后记录保持claimed/running，这是无人执行的"running"，与真实运行在基线中不可区分。cooperative边界检查已在读代次，顺手写一个`stop_acked_at`几乎零成本：只有ack能证明worker已看到停止、此后不再发IO。无ack的stop_requested是"未知是否仍在写"，有ack是"已停止发出IO但占用保留"。这是人工清理是否安全的唯一依据，不能等隔离再做。实证：需测worker在ack后确无后续worktree写入。

2. unknown错误复用"停止请求"字段，把人工stop与系统崩溃混在同一子集。需要`stop_source`（user/system-indeterminate）与原因枚举，否则基线stop_requested子集失去含义，也无法为后续隔离恢复提供分类依据。

3. 无owner旧记录：拒绝写只覆盖"已stop"的。未stop的旧记录仍可被旧API任意提交终态，而旧API若还能创建记录，等于新造免校验记录。必须关闭旧API的创建路径，只允许更新既存无owner记录。实证：用旧API创建一条记录，期望拒绝。

4. "同一写事务内检查"成立的前提是行级锁或串行写。实证：两个客户端同一执行并发stop与complete，各跑百次，断言恰好一方胜且落库字段与胜方一致；若出现两者皆写入或交错覆盖，事务边界不真实。

5. "候选边界验证失败记failed"需明确前置条件：自上次确认回执后未发出任何IO。若验证在builder写worktree之后，failed加释放就回到我第三点的漏洞。建议把failed限定为"无未决副作用"的失败。

6. 验证器回执：若已用子进程，waitpid返回本身就是该进程消失的OS证据，孙进程除外。可在本片区分"抛错但已收到wait"（可failed）与"抛错未wait"（不确定）。实证：确认执行阶段是否总在wait后才判定。

**应等worker隔离**

释放占用、stopped终态、恢复命令、基于lease的抢占、进程组kill、worktree回收、自动重试、把不确定停止升级为failed。这些都依赖"进程确已停写"的证据，本片提供不了，勉强做只会把不确定包装成确定。

一句话：本片不该承诺清理，但必须把"我不知道"记得足够精确，否则后续隔离无从接手。
