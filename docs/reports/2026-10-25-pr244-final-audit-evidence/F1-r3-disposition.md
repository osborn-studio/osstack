# Final F1 delta after scoped PASS

The r2 review returned PASS_SCOPED and no correctness blocker. Its source used a Git-dependent storage path. Before accepting that version, the host identified that a non-Git workspace could become Git and change lookup paths. This final delta supersedes that storage strategy entirely; no Git command or repository metadata participates in containment identity or storage.

Every workspace now uses an absolute trusted host control root: OSSTACK_LOOP_CONTAINMENT_ROOT, else OSSTACK_HOME/loop-containment, else ~/.osstack/loop-containment. The filename is SHA-256 of the canonical real workspace path. This identity is stable across stateFilePath changes, Git initialization, git clean, aliases/symlinks to that same workspace, and removal/pruning of Git worktree admin metadata. A configured root inside the candidate (including a symlink alias to it) is rejected before admission, with no dynamic fallback. The helper performs no database access. All tests set the new root in the common Vitest worker setup to a dedicated tests scratch subdirectory and restore it during worker cleanup. Relevant child fixtures inherit the environment; no tested LoopEngine launcher resets to the real user home.

The acceptance boundary is the same canonical workspace and same trusted configured host root. Different canonical workspaces/worktrees or different host roots are different authorization objects. There is no new global repository serialization or claim of isolation from same-uid processes with arbitrary host filesystem access. The root's permissions and stable host configuration are operator responsibilities. These are explicit parent decisions. A trusted process deleting containment records, or a workload with unrestricted host filesystem access doing so, is outside the isolation claim; this is not a sandbox.

One additional conservative entry guard checks the already-existing candidateContaminated field even if a marker disappears during the same process. This is separate from physical-stop classification. containmentPending is a private in-memory field, not a new persisted state schema field. It causes execution_containment_pending stop output instead of idle/completed.

Recovery decision D1: absence of implementation_unconfirmed in LOOP-STATE.json is NEVER permission to delete a containment record. Goal uncertainty, exceptions, integrity failures and interrupted writes need not have that task field. No automated reset, force retry, or safe manual deletion protocol is implemented or advertised. Operational reconciliation is separate and cannot use absence of task metadata as stop proof.

Durability decision D2: the guarantee is successful OS fsync of the record and directory entries before admitting effects, and fail-closed on reported fsync errors. It is not a verified external-SSD power-loss, controller-cache or F_FULLFSYNC qualification. Real hardware power-loss qualification remains unperformed. No claim that every silently dishonest/unsupported filesystem can be detected is made.

The earlier rejection/worktree, executor/verifier/final-preflight/goal classification and publisher finite-contract qualifications remain exactly as scoped in r2. Normally fulfilled optional publisher callbacks do not establish descendant-group stop; rejected calls retain containment. Tests now directly execute non-Git -> git init -> git clean -> verifier unknown -> simulated state-write failure (Error("disk full"), not an OS ENOSPC code), then restart with a different state path, proving no second execution. Host-root inside-candidate/symlink rejection and canonical-workspace alias tests also pass. Test-time and review-time hashes are recorded, rather than claiming the model reproduced tests.
