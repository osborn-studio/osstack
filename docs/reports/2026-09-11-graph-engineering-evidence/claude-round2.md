**总判断：无阻断。研究建议可交付，集成收益仍待实验，不以语言审查代替实验。** 以下 8 项按严重度排列，标注类型：错误 / 取舍 / 待实证。

**先校准上轮。** 我上轮说"只有依赖义务带 from/to"不精确：Kanban 链接也带端点，Autonomy 已有 append-only transition、projection 与 expected_revision。我接受你拒绝的四点：显式 caused_by 不是因果证明，消费关系应从已有 refs/payload 读出；protocol 不先加字段；去重优先于重写 Kahn；superseded_by 一列足以表达血缘。补一句：superseded_by 只给链，不给有效时间，报告已把 valid_time 限定为源提供时才填，两者一致。

**1. 错误：P0 的"解释为什么任务还不能开始"没有权威来源。** Loop Task 无依赖字段；Kanban link 是无类型链接，报告 §3 自己禁止把引用当必须等待；neat 义务是知识治理边，§5 也说不等同任务前驱。所以 P0 只能转述既有阻塞原因（治理决策、限流、状态列），不能从链接推出"被阻塞"。修订：P0 输出改为"关系清单 + 影响提示 + 既有阻塞原因转述"，任何 blocked 标签必须回指一个本身具阻塞语义的源，否则只写 linked。这也回答挑战 1：只读层不是包装的条件，是能回答至少一个单一存储答不了的跨源联查，例如卡片→neat 义务→证据 digest→验证结果。若预注册查询都能由 pnpm 或单条 SQL 回答，按 §9.4 停止。这是待实证假设。

**2. 错误：§6.2 把四类依赖合并去重成 45 条无类型边**，与全报告"带类型边"主张相悖。devDependency 的影响面只到测试与构建，不到运行时消费者。修订：保留边类型，分别报告下游数，影响提示按类型解释。

**3. 错误（若按字面落地）："只读"与"重建放在后台"有张力。** 若关系视图缓存写入 core SQLite 新表，就需要迁移，触碰控制面 DB 纪律，也不再是只读。修订：G1 缓存限定为进程内或 OSSTACK_HOME 下可删除的独立文件，不进 daemon 启动路径，不新增 schema；G2 若需持久化再走迁移评审。

**4. 取舍需明确：权威与派生未分级，冲突无规则。** 修订：读视图给每源标注 authoritative 或 derived，package.json、gbrain 页、拓扑结果均为派生；同一对象对在两源关系不一致时并列返回，不合并不裁决；历史只来自源自身的 superseded/transition 记录，视图不合成历史。coverage 与 staleness 设计已合格。

**5. 漏洞：静态 WorkflowPlan 与 Loop 每轮发现任务的动态模型如何并存未定义。** runCycle 每轮重新发现，计划外任务与计划内节点共享 executor 与写锁，可能出现计划节点在等待而计划外任务先改同一 repo。另外，报告未对照当前分支的 collaborator 会话阶段与阶段结果模型，WorkflowPlan 有成为第三套计划概念的风险。修订：G2 前给出并存规则（计划节点独占其 repo 写窗口，或计划外任务降级只读），并说明与 collaborator 阶段的映射或明确互斥。

**6. 评测可推翻性不足。** 开发集由作者从"已知结果"中挑选，真值由作者给，诊断时间由建造者自测。修订：G1 实现前冻结案例集、真值来源（真实下游验证结果或事后返工记录，而非人工判断）、失败定义与停止条件；诊断时间由未参与构建者测；把"无收益即停"写进 G1 退出条件。同意不设无基线阈值。

**7. 陈述精度，三处。** memory 省略 tenant 即跨租户读取属既有安全事项，应单独报告并给精确锚点，不宜只作图查询注脚。S9"尚不足以统一回答"应改为"未逐一核查全部事件族，已查路径不足"。表 1 中 P1"正确处理汇合和失败"是目标不是现状，应加"拟议"。报告对 Autonomy 与 Loop 并发的描述与我所知一致，未见"没有图"的过度声称。

**8. 与 Loop/Harness 路线的重复。** G2 的就绪判定依赖状态真实性。若 Loop 状态不能区分真实等待与假完成，图上的 ready 只是把不实状态结构化。修订：G2 显式以 Harness 的状态真实性交付为前置，attempt/status 共用一套字段，不另建。

**是否改变首个 pilot 建议：不改顺序，改定义。** 上轮我主张先加 Task.depends_on，理由是 P0 缺少它要解释的关系；你选择只读先行，理由是需求未证实前不改控制路径。第 1 项表明两者都成立：P0 确实没有任务级阻塞关系可解释，但正确回应不是加字段，而是让 G0 记录真实阻塞需求是否存在，并把 P0 缩到跨源关系清单与影响提示。若 G0 发现没有案例需要任务级前驱关系，depends_on 本身就应被否决。
