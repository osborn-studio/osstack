## Product closure still missing

Passing v2 5-G establishes registered-review transport and containment; it does **not** complete Watcher chat failure → local repair → new head → reverify. The current reader fetches reviews/threads/commits/timeline, not check conclusions or ordinary comments ([reader](../../../packages/cli/src/contained-mission-bridge-reader.ts)); `COMMENTED` is inert ([revision selection](../../../packages/core/src/bridge/revision-chain.ts)). The dispatcher requires actual review IDs/digests ([dispatcher](../../../packages/cli/src/contained-mission-revision.ts)); do not fabricate a review to inject a CI or chat failure. Local failed candidate verification already has bounded repair ([runner](../../../packages/cli/src/contained-mission-runner.ts)), but this is not remote Watcher failure intake. Independent local semantic review is also not automatically wired into every contained child merely because LoopEngine supports evaluators.

The missing minimal connection is a distinct local completed-CI-failure intake for the current published head → trusted host-selected verification against that exact head/base → reproducible local failure receipt → bounded local-repair request. Remote CI is only a wake-up hint; commands must never come from check output/comments/chat. It needs a typed source and deduplication key, real identity/head/base/profile/stop evidence, and existing grant, scope, protected paths, rounds, publication leases and cancellation fences. This is proposed work, not implemented acceptance. A Watcher-only chat finding when CI/local verification pass remains outside that minimal CI path; covering it requires reproducible independent local verification or a separately specified authenticated structured failure relay. No new Bot duties, Reviewer dependency/unpause or chat scraper is implied. Full closure needs offline intake cases and a later real failure → local repair → new head → reverify demonstration; full automation is not complete.

Watcher verification and advisory approval remain distinct from counted Mission-main approval. [ADR-006](../../decisions/ADR-006-bridge-s0-decisions.md) retains the owner's human approval gate; [merge gates](../../../packages/core/src/bridge/merge-gates.ts) count configured User identities and reject App-only counted approval. Grok approval and independent Merger operation do not relax that gate. This gap follows the source audit at baseline `d37f8fb3`; it changes neither Bot configuration nor production enablement.
