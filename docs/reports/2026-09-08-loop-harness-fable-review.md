## Codex 收敛意见

采纳：模型内循环与工程循环分开；失败分类优先；先观测中间候选退步再建保留机制；可校验的恢复笔记；任务级配对和停止策略偏差控制；独立冻结验收；首个经验实验纳入直接修工具接口的基线。基础设施异常、长期未用经验和模型版本漂移均需显示，不能用“没出反例”维持永久已验证状态。

修正与保留分歧：

- 工具/文件集合变化不能成为充分进步证据，只用于重复活动诊断。固定两轮是一个实验基线，不是全任务通用上限。
- 置信区间重叠不能证明无收益；应分析配对差值和预先定义的最小有用效果。`1.3` 倍成本没有用户依据，不采纳。真实实验前必须确定效果、绝对预算及成本取舍，未确定就不宣称晋升合格。
- 不将“有证据的采用”设计为因果标签。首实验记录随机分配、加载/读取、客观工具事件与结果，以分配组计算效果（intent-to-treat）；加载失败也是系统结果。只比较实际加载成功者会再次引入选择偏差。
- 工具使用率下降不是自动失败：如果任务允许换工具，减少不可靠调用可能是正确优化。只有实验目标确实要求修复指定工具能力时，才把该能力设为验收；另测完整交付与替代路径成本。
- 修复工具接口胜过技能，依然属于有效的系统自改进；应选择更简单的实现。没有必要为了证明“经验闭环”而保留冗余技能。
- 经验应有复查时间、适用版本与撤销条件；到期无证据标为待复查或停止自动使用。删除技能文件不能代替撤销已缓存版本及保留既有执行证据，也不应盲目定期重测全部技能。
- 候选生成应包含失败、成功、慢成功与撤回反馈，不只取恢复成功的轨迹；状态尚未确定不能归入已验证。谱系先复用 Git/工件历史。
- Fable 提议公开日志。本项目默认把证据保留在项目有权访问的工件中；可复跑不要求公开私有代码、任务或日志，外部公开需另有明确授权。

本轮没有改运行代码或启用学习循环。研究收敛后的顺序是：修正真实性计数 → 建立一个可重放经验实验 → 按证据选择技能或工具修复 → 再扩展策展与调度策略。


## 模型循环专题：输入

请作为 Claude Fable 5.1 对公开论文启发的产品设计做一次独立挑战。用户已明确委托 Codex 和 Fable 互相挑战，正在为名为 OSStack 的软件开发 loop 系统设计“协作者代替阶段go”及自我迭代。本次只有公开论文事实与新的通用设计，无仓库代码、私有组织资料、内部审计内容。不要使用工具、访问文件、调用技能或网络；中文最多1200字。

可核实的公开证据摘要：
1. Universal Transformers arXiv1807.03819 有按位置ACT自适应停止；不是所有recurrent depth都固定循环。
2. Scaling up Test-Time Compute with Latent Reasoning arXiv2502.05171：3.5B参数、800B训练token，50B指推理计算负载等效，不是50B能力等效。性能有饱和与非单调情形。
3. Training-Free Looped Transformers arXiv2605.23872需要开放权重和修改推理计算；免训练不等于免计算。
4. LoopCoder-v2 arXiv2606.18023的R=2是首次计算加一次额外循环，比较训练/推理循环次数匹配的PLT模型家族；不能从中推出所有agent最佳两轮。
5. Loop the Loopies arXiv2607.16051里equal-compute使用固定硬件每optimizer step墙钟作代理，并非简单等FLOPs；层粒度结论有架构/规模限定。
6. 我们查到的Astra官方发布材料没有公开其采用Loopie或特定recurrent-depth架构；同期论文和媒体推测不能证明直接采用。官方明确介绍了可跨上下文保留笔记并检索历史上下文的harness能力。

Codex通用设计提案：
A. 区分模型内部recurrent depth、一次任务的推理预算分配、工程执行/验证循环、跨版本系统自我改进。OSStack不能控制闭源API隐藏状态或网络层次数，只使用适配器明确支持的模型/effort/预算参数。
B. 新增可选的按证据分配计算策略：简单任务完成固定验收就停止，难任务可增加验证、更换执行策略或请求另一模型挑战；每轮必须带新证据或可证伪的不同假设，不能无限重复原提示词。无模型一致性=真值假设。
C. 保留最佳“满足同一冻结验收标准且绑定当前修订”的候选；后续变差就选择最佳有效候选重新验证，而不是总取最后一版。预算用任务总量和跨实验总量兜底。
D. 用原始工具回执、验收结果、失败证据和工件摘要来判断进步；不依赖模型说自己想清楚了，也不以文件或日志hash变化本身当变好。内部思维链不可得时仍应可验证行为。
E. 增加可恢复的工作笔记/证据索引：目标、已确定约束、假设、失败尝试、待答问题、工具产物引用和版本。恢复时验证引用是否陈旧，记忆文本不能扩大权限。
F. 先做受控离线实验：在同模型/任务/验收/工具环境、共同成本或时限上限下比较固定1/2/3轮与自适应策略；另外画预算-质量曲线，报告实际花费，不能把共用上限说成等实际计算。用预注册晋升集和新任务检测过拟合，纳入必须停止与不应误拦截的任务。若简单两轮赢过自适应就采用简单策略。
G. 这些是可测的harness改进假设，不是模型架构性能已经迁移。现有协作者和独立云端GitHub App方向保持；更多计算从不增加批准、合并或发布权限。

## 模型循环专题：原始回复

## 独立挑战意见（Fable 5.1）

**一、应保留**
- A 的四层区分是整个提案最有价值的部分：它把"论文里的 recurrent depth"与"harness 里的重试"切开，直接堵死了"Astra 用了循环架构所以我们也该多循环"这类推论（证据 6 已表明该推论无依据）。
- D 和 G 应作为硬约束保留：以工具回执和验收结果判进步、计算不换取权限。这两条不需要实验就该成立。
- F 的核心（同环境、同上限、报告实际花费、预注册晋升集）保留，且应是其余各项的准入门槛。

**二、过度设计**
- B 中"请求另一模型挑战"和"每轮必须带可证伪的不同假设"：后者无法机械判定，实际会退化为让模型自述"我换了思路"，与 D 矛盾。建议简化为可观测的差异：工具调用集合、修改文件集合、失败测试集合三者至少一个发生变化，否则视为重复。
- C 的"跨实验总量兜底"与"最佳候选重新验证"叠加，引入了候选存储、修订绑定、陈旧检测三套状态机。在没有证据表明"后续变差"高频发生前，先只记录"是否出现最佳候选非末版"的频率，再决定是否建机制。
- E 的字段设计过细。假设、待答问题这类主观字段在恢复时最难验证是否陈旧，建议首期只保留有引用可校验的内容：目标、验收标准、失败尝试的工具回执引用、工件版本。

**三、最危险的两种失败**
1. **停止规则的选择偏差**：自适应策略"难任务多轮"意味着轮数与任务难度相关，事后比较"多轮 vs 少轮"的通过率会天然偏向少轮或偏向多轮，取决于分析口径。若不按预注册的任务分层且固定分析方案，任何结论都可被解释成想要的方向。这正是证据 2、5 提醒的"等效"口径问题在 harness 层的翻版。
2. **验收标准被候选选择污染**：C 要求"同一冻结验收标准"，但在开发 loop 里验收本身常被同一轮修改（新增测试、放宽断言）。若最佳候选选择时验收已漂移，"最佳"是对旧标准的最佳，重新验证会通过但实际退步。必须把验收变更与代码变更强制分离到不同修订，否则 C 会系统性误报进步。

**四、最小推翻实验**
固定一批已知答案的任务（含必须停止的坏任务），三臂对照：固定 2 轮；B 自适应；B+C+E 全开。同上限、同模型、同工具、盲评。若全开臂的通过率提升不超过固定 2 轮臂的置信区间，或每通过一题的实际花费高于固定臂 1.3 倍，则 B/C/E 收益不成立。这一实验成本低，应在写任何状态机之前跑完。

**五、明确反对的一点**
反对 B 的默认形态是"难任务加计算"。证据 2 显示饱和与非单调，证据 4 显示 R=2 只是一次额外循环且限定于匹配训练的模型家族。在闭源 API 上加轮次没有任何论文支持其单调收益，且成本可控性最差。

**更好的替代**：把"难"定义为可观测的失败类型而非计算量。第一轮失败后，按失败证据分流——测试失败走定向修复、环境失败走重建、验收歧义走回退给人。每类分流最多一次，总轮数上限为 2。这样把预算从"多试几次"改为"试对方向"，与 D 一致，且直接对应 F 中"若简单两轮赢过自适应则采用"的判定。等这个分流版本被 F 的实验证明不够用，再考虑增加轮次。

## Harness 经验专题：原始回复

## 两个最可能伪装成学习的失败

**一、回避型“恢复”。** 初版只做一个工具失败恢复技能，最自然的指标是“该工具失败次数下降”。Cursor 的 real-time RL 报告已经给出先例：丢弃无效工具调用样本后，模型学会的是不触发负反馈，而不是把调用做对。同理，一个“恢复技能”最廉价的成功路径是少用那个工具、改用绕路命令、或多问一次用户。你的验证只比较最终验收和成本，验收会通过，成本可能持平，但技能学到的是规避。必须把**目标工具的使用率**作为对照指标一并冻结，使用率下降超过阈值即判为回避而非恢复。

**二、幸存者式“验证”。** 候选经验来自“失败后恢复成功”的任务，这本身是对成功的筛选；退役由反例触发，而“未能观测使用记为未知”意味着无反例即存活。两条规则叠加，库里会积累大量**从未被证伪、也从未被证实**的技能，且每一条都有版本、谱系和“已验证”状态，看起来很像知识增长。你在第五点反对以库大小为进步，但机制上并没有让“长期无有效使用证据”自动触发退役。建议：验证状态附有效期，到期无新的配对证据自动降回候选，这比反例驱动更能抵抗幸存者偏差。

## 是否过度设计

仍然是。谱系、跨仓库迁移验证、延迟结果修订、三态使用记录，这些是在第一条技能被证实之前为一个想象中的库搭的骨架。综述里那些分类（技能/记忆/机制演化）是文献地图，不是你产品当前需要的状态机。初版只有一个技能时，谱系就是一条 git 历史，退役就是删文件。

## 应删除的字段：“有证据的实际采用”

“推荐/加载/有证据的实际采用”三态中，第三态要求归因：代理自报“我用了这条经验”不可信，从轨迹里判定“这次恢复是否因为该技能”需要一个裁判，而你已明确不建自改裁判。这个字段会诱导做半吊子的归因规则，产出的是伪精确。

删掉后按 **intent-to-treat** 处理：只记录加载与否、任务结果、总成本。代价是失去单技能归因，多技能同时加载时分不清谁有效，“加载但被忽略”只能从零效应间接推断。初版只有一个技能，这个代价为零；等真有多技能且效应可测时，再用逐个撤除实验归因，比自报字段可靠。

## 第一份可见、可推翻的证据

不是仪表盘，而是一个**三臂配对实验**，且预注册文本先于数据公开：

- 固定一种失败类型（例如某构建命令的特定超时或补丁格式错误），冻结模型、工具版本、验收脚本、预算上限；
- 三臂：无技能 / 加载技能 / **不加载技能但直接修补工具接口**；
- 预先写明最小有用效果，报告配对差值区间，同时报告目标工具使用率与含恢复尝试的总成本；
- 公开任务清单哈希与原始日志，任何人可复跑。

可推翻的判据是第三臂：如果修接口就能拿到与技能相当的收益，那这条“经验”只是一个应该固化到代码里的补丁，不是需要经验闭环的学习。这正是 Cursor 关于昂贵摘要模型无收益的教训——先证明便宜的机械修复不够，才有资格谈自改进。

用户侧可见的形式：同一失败在用户会话中再次出现时，恢复步骤旁显示“来自经验 #x，在 N 个任务上验证，实验链接，一键撤回”。撤回率本身要进入下一轮指标——被用户主动撤回的“已验证”技能，是闭环失灵最直接的证据。

## 保留的异议

我仍认为成本阈值需要一个数，哪怕是用户自己定的。没有阈值，“总成本计入策展检索验证失败”只是一句原则，无法在实验里判定失败。1.3 倍可以撤回，但空白不能。
