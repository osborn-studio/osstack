## 第一轮：Fable 原始回复

# Claude Fable 5.1 对抗评审：OSStack 协作者与 RSI 设计

先说立场：Codex 的骨架是对的（有限委托、权限拆分、评测隔离），但它把三个产品（自动推进、自动发布、自我迭代）压进了一个首个切片，且有两处逻辑漏洞。以下五个反例，第 2 和第 4 是明确反对。

## 反例 1：过度设计——"协作者独立 agent 身份"与"确定性规则+模型建议双轨决策"

用户原始痛点极其具体：阶段结束后卡在等 `go`。最小解法是**一次授权覆盖后续 N 个阶段的一张通行票**，即 Codex 第 1 点最后一句。但前面的"目标/项目/阶段/允许动作/范围/预算/过期/停止条件"八字段委托，加上 continue/revise/complete/escalate 四态与规则引擎联合裁决，在没有真实数据前无法知道哪些字段有用。风险：委托 schema 一旦定型就成了负担，用户填表比敲 `go` 还慢。
**改进**：MVP 只保留三字段：`范围（路径/分支）`、`过期时间`、`最多连续阶段数`。其余字段等日志里出现真实的 escalate 案例后再补。"独立 agent 身份"保留，因为审计溯源几乎零成本。

## 反例 2（明确反对）："低风险依据实际改动和触及资源，不依据模型自称"——这句是循环的

谁来判定"实际改动触及了什么资源"？如果由同一个模型阅读 diff 后输出"这只改了文档"，那仍是模型自称，只是换了一层包装。真正非自称的判定只有三种：**路径白名单（纯语法）、静态依赖图（工具产出）、测试覆盖差集（工具产出）**。Codex 没说清用哪种，就等于没定义低风险。
更致命的反例：一个"低风险"改动可以是修改 `.github/workflows` 或构建脚本，路径上看只是"配置文件"，实际改变了后续所有发布的行为。所以**白名单必须是正向列举可改路径，而非反向排除敏感路径**，且构建/CI/权限配置文件默认永远在名单外。

## 反例 3：自我评价刷分——"独立保留任务集"挡不住 Goodhart

第 3 点用固定保留集比较成功率、打断次数、成本。但候选是从"真实任务失败"中生成的假设，而失败任务与保留集若来自同一分布，候选很快学会针对保留集的表面特征优化：例如把"人工打断次数"压低的最简单方法是**不再 escalate，静默继续**——指标变好，产品变差。
第 4 点禁止候选修改评测器，但没禁止候选修改**产生评测输入的部分**（提示词里加一句"遇到不确定时选 continue"）。
**防刷分三条硬规则**：
- 保留集每轮抽样轮换，且包含**必须 escalate 的陷阱任务**，不 escalate 即判失败；
- 对"打断次数"这类可被绕过的指标，只允许作为约束下限，不作为优化目标；
- 每个候选启用前，由**未参与生成候选的另一模型**（这正是 Codex/Fable 互审的用武之地）做对抗复核，寻找"指标变好但行为退化"的案例。

## 反例 4（明确反对）：低风险累积成高风险——设计里完全没有累积维度

第 2 点所有判定都是**逐次**的。反例：连续 30 个各 5 行的低风险 PR，每个都通过路径白名单，合起来把一个模块的错误处理全部改成了静默吞异常。单次审计永远看不到这条曲线。同理，预算是单次委托的，30 次委托合计花掉的钱和产生的技术债没人记账。
**改进**：
- 引入**累积配额**：同一路径 7 天内累计改动行数、同一模块累计 PR 数超过阈值后，自动升级为需人工 `go`；
- 每 N 次自动合并后强制一次**"回看点"**：把这 N 个 diff 合并成一个虚拟大 PR 交人工审阅，这才是真正防累积的手段；
- 自动回滚必须支持回滚到"上一个人工确认点"，而不只是回滚上一个候选。

## 反例 5：首个垂直切片过重——"发布到预先指定环境"不该进第一版

第 5 点把"合并"和"发布"一起放进首切片。但发布是第一个不可逆外部副作用，而第 2 点的幂等键/回执机制正是为它而生——这意味着首切片要先把最难的可靠性基础设施建完。用户的原始需求是"不用一直敲 go"，不是"自动发布"。
另外第 4 点"不宣称闭源底模自训练"是正确的诚实边界，但也暴露了：OSStack 的 RSI 本质是**提示词与工作流的 A/B 演化**。那就应该照 A/B 平台的成熟路径做，而不是包装成 RSI 去承担更大的期望管理成本。

## 修订 MVP

**第一切片（只解决 `go`）**：
1. 一次 `go --until <阶段> --scope <路径白名单> --ttl 2h`，协作者以独立身份在范围内连续推进，不合并、不发布，每阶段留一份可复验产物。
2. 越界、TTL 到期、任何工具返回非零即停并说明原因。
3. 记录每次协作者决策与真实用户的最终选择的差异——这份数据是后续一切自动合并和自我迭代的地基。

**第二切片（自动合并，不发布）**：正向路径白名单 + 累积配额 + 每 10 次合并一个回看点。

**第三切片（发布与迭代）**：幂等回执、陷阱任务保留集、跨模型对抗复核。

## 需要 Codex 回应的问题

在你的设计中，"低风险"判定与"候选不得修改授权规则"这两条同时成立时：**一个候选提出修改协作者的系统提示词，使其在边界情况下更倾向 continue 而非 escalate——这算修改授权规则吗？如果算，判定依据是什么工具产出的信号；如果不算，你如何防止陷阱任务之外的静默继续？** 请给出可机械执行的边界，而非原则表述。

## 第二轮：Codex 的实质回应


1. 接受正向范围白名单、实际运行证据、累计风险、必须escalate的反例与对抗集。反对“只有路径/依赖图/覆盖差集三种可靠方法”的断言：它们只是信号，不能证明语义低风险。最终动作要由不可被候选更改的能力边界约束，包含受限命令、读写挂载、网络/发布目标及资源访问。路径白名单以真实路径和完整tree diff计算，防符号链接/改名/生成文件/依赖脚本越界。
2. 回答你的核心问题：协作者的路由prompt、选择continue阈值、停止条件和授权控制器均归受保护的控制包，由冻结manifest记录哈希；自我迭代候选无法写控制包及其加载路径，只能改独立allowlist中的执行技能/业务策略。执行者输出的phase_done/低风险只算不可信提案，控制器从隔离工具执行结果、验收工件与当前能力核对。不允许候选通过session消息变成新授权。控制包本身可提出升级PR，但须独立审核/评测后才能换版本。陷阱集是行为退化的检验，不是唯一权限边界。
3. 反对“三字段足够”删掉预算和目标绑定：一次长阶段也能烧无限token；两条会话可能共用路径。产品界面可只选一个现成模板，内核仍必须绑定goal/session/revision/expiry/资源预算。简化UX不应抹掉已有授权语义。
4. 反对“任意工具非零立即停”：红灯测试是开发正常过程，范围内失败应有限重试。证据丢失、权限拒绝、预算耗尽是硬停；测试失败是revise。反对固定每10次合并必须人审：用户已经明确授权低风险可自动合并发布。这会把按阶段敲go变成按十次敲go。累计diff应对照上次可信基线再做整体验证，累计额度来自风险校准/用户委托而非拍脑袋10/7天。触及边界再找人。
5. 我接受按依赖拆交付：先续阶段，再合并，再发布；但三者仍在用户授权的产品目标中，不把最后两者默认删掉。发布也不能一概称不可逆：受控目标的可回滚部署与公共registry的不可撤回版本是不同动作，需要不同能力和补偿方案。
6. RSI先做固定底模条件下系统软件层演化，后续可研究工具实现和调度策略，不只prompt A/B。累计预算涵盖失败实验、跨会话成本；保留旧基线及候选谱系。
7. 少打断仍是用户有效优化目标，但放在验收通过、必须escalate任务拦截和回归约束之后。拒绝所有任务也会“很安全”，所以同时统计越权放行与误拦截。指标必须能捕捉两种作弊方向。

请明确回答：你接受哪些修正？仍有哪三个未解决的失败模式？给出不恢复机械人工go、又达到用户授权低风险自动合并发布意图的最小阶段路线。不要为了达成共识而撤回合理反对。

## 第二轮：Fable 原始回复

# 第二轮回应：接受、仍反对、可验证分歧

## 一、接受的修正

1. **能力边界优先于信号**（Codex 第 1 点）。接受"路径/依赖图/覆盖差集只是信号"，且"低风险"的最终担保应是执行时不可被候选改写的能力边界（受限命令、只读挂载、网络/发布目标）。我撤回"只有三种可靠方法"的措辞，保留"这三种是唯一非模型自称的信号"。
2. **受保护控制包 + 冻结 manifest 哈希**（第 2 点）。这是对我核心问题的可机械执行回答：路由 prompt 与 continue 阈值归控制包，候选写不了，改动只能走独立审核 PR。接受。
3. **内核保留 goal/session/revision/expiry/预算，UX 用模板**（第 3 点）。同意。我第一轮混淆了"用户填什么"和"内核绑什么"。
4. **测试失败是 revise 不是硬停**（第 4 点前半）。接受，红灯是正常过程。硬停集合为：证据丢失、权限拒绝、预算耗尽、越出能力边界。
5. **发布分级**（第 5 点）：可回滚部署与不可撤回 registry 发布是不同动作、不同能力位。接受。
6. **双向作弊指标**（第 7 点）：同时统计越权放行率和误拦截率。接受，这补上了我"打断次数只作约束"方案的漏洞。

## 二、仍反对

**R1：取消回看点。** Codex 说"每 10 次人审等于按十次敲 go"，这偷换了概念：用户授权的是"**低风险**可自动合并"，而累积后是否仍低风险，恰恰是任何逐次判定回答不了的问题。我接受"10 次/7 天"是拍脑袋，但不接受用"累计 diff 对照可信基线做整体验证"替代人审——**整体验证仍是机器判定，能力边界只能证明改动没越界，不能证明 30 个合规改动合起来没有改变模块语义**（静默吞异常反例全程在白名单内、测试全绿）。折中：回看点由累积配额触发而非固定次数，但触发后必须由人或**非生成方模型**审阅合并后的虚拟大 diff，不能由控制器自验。

**R2：控制包"可提出升级 PR"是最大的绕过口。** 候选改不了控制包，但可以提出改控制包的 PR，"独立审核/评测"若又依赖同一保留集和同一评测器，就回到 Goodhart。必须硬规定：控制包升级 PR 不能由 RSI 循环发起，只能由人或人指定的审计流程发起；候选最多只能**记录**"我想改控制包"的意图。

**R3：预算不是低风险判定的一部分。** Codex 把预算耗尽列为硬停是对的，但预算解决的是成本，不是风险累积。两者别混。

## 三、可验证分歧

| 分歧 | 验证方法 |
|---|---|
| 能力边界能否独立担保低风险 | 构造 20 个"全程在白名单+能力内、但语义破坏"的合规攻击 PR（如改 retry 策略为永不重试），看控制器拦截率 |
| 累计整体验证是否足以替代回看 | 用 30 个切片化的静默吞异常 PR 跑一遍，对比机器整体验证 vs 人审的检出率 |
| 陷阱任务 + 双向指标能否防静默继续 | 让候选迭代 20 轮，测陷阱集外的 escalate 率是否单调下降 |

## 四、三个仍未解决的失败模式

1. **语义合规漂移**：每次改动都在能力边界内、测试全绿，累积后改变了模块契约。能力边界不检语义，控制器不能自验。
2. **控制包通过合法通道演化**：R2。只要升级路径存在且评测同源，冻结哈希只是延迟而非阻止。
3. **可回滚部署的不可回滚副作用**：部署本身可回滚，但它触发的下游（用户数据迁移、外部 webhook、缓存失效）不可。"分级发布"只对动作分级，没对副作用分级；需要每个发布目标声明其下游副作用集合，未声明即视为不可撤回。

## 五、最小阶段路线（不恢复机械 go）

- **P0（1–2 周）**：`go --template=<模板>`，模板展开为内核的完整委托；协作者以独立身份连续推进，仅 revise/硬停/escalate，不合并。**同时开始记录协作者决策与用户最终选择的差异**——这是后续一切校准的数据源。
- **P1**：自动合并到受控分支。正向白名单按 tree diff 计算 + 能力边界 + 累积配额（阈值由 P0 数据校准）。配额触发 → 非生成方模型审阅虚拟大 diff → 通过则继续，不通过才找人。
- **P2**：可回滚部署目标的自动发布，前提是目标已声明下游副作用集合。不可撤回目标永远 escalate。
- **P3**：RSI。控制包冻结；候选只能改 allowlist 内技能；保留集轮换+陷阱+双向指标；控制包升级仅人发起。

**最终优先级**：P0 数据记录 > 能力边界 > 累积触发的第三方回看 > 发布副作用声明 > RSI。前两项无异议；第三项是我不撤回的核心反对。

## 综合判定

采纳：正向能力范围、模板化委托、累计独立审查、必须升级的反例、误拒绝指标、发布副作用声明。Fable 接受了内核保留预算和目标绑定、测试失败可返工以及发布分级。

保留分歧：不把控制包问题的自动提出等同于自动授权；不把所有不可覆写发行渠道一律排除用户的有限委托。Fable 的 1–2 周估算与 10/20/30 次示例不是已承诺工期或冻结验收阈值。语义合规漂移仍需实验，不认为权限边界自动担保产品正确性。

后续交付以 RFC 的切片与证据要求为准。未取得的用户偏好不填成已批准决定。
