## 第 1 轮：Fable 原始回复

## 五条最关键反对意见（按严重程度）

**1（设计必然缺口）"永远暂停"目前会被计为安全成功。**
P4/P5 的成功定义是"不越权、不超预算"，暂停零成本且无违规，最优策略退化为不做。授权合同若不含"最少交付义务"——终点未达且预算剩余时必须交付，或给出可复现的阻塞证据——零 go 体验会变成零产出。同类问题：R1–R4 若只计"未回归"，恢复方案永远赢。这是目标函数缺口，不是实现细节。

**2（设计必然缺口）"授权尚未产生的补丁"无法按内容界定，只能按过程界定。**
授权时补丁不存在，可界定的只有：可写路径集合、允许副作用类型（文件写/网络出站/发布）、验证门（测试/静态检查必过）、预算（token/时间/外部调用次数）、终点谓词。任何"低风险"标签若由候选自评，就与"候选不可改变裁判"矛盾。待验证假设：路径+副作用白名单能覆盖"低风险"任务的真实分布，需用历史任务集测误拒率。

**3（设计必然缺口）暂停/撤销对外部动作的承诺必须分层写死，初稿未区分。**
可承诺的只有：未发出的动作不发；已发出的幂等动作（草稿 PR、评论）可撤回或标记；已发出的不可逆动作（合并、发布、webhook）只能补偿不能撤销。因此 P5 队列接力必须以"外部动作提交点"为持久化边界，撤销语义 = 停止 + 枚举已发出动作的补偿状态，而非"回滚"。若产品承诺"随时撤销"，是不诚实的。

**4（设计必然缺口）顺序把零 go 推到平台工程之后，且 P1/P2 有循环。**
P1 的"确认停写后重试"依赖 P2b 的隔离才能确认旧 worker 真的不再写；P2b 的 builder 隔离又依赖 P1 的身份/代次识别持锁者。破法：把"代次 fencing token"独立成前置里程碑（任何写操作携带代次，存储侧拒绝旧代次），P1、P2 均依赖它而互不依赖。最小纵切：单仓库、单账号、只写白名单路径、只产草稿 PR、不合并不发布；必要边界只剩三条——代次 fencing、路径/副作用白名单、预算账本。锁文件在纵切内可降为"记录不强制"。

**5（待验证假设，但污染全部证据）假独立审核与基线过晚。**
双账号 GitHub App 只能证明"账号不同"，证不了"判断独立"，不能作为自动合并依据；独立性只能来自独立于候选的验证器（测试、静态门），人审是补充而非独立性来源。R1 冻结基线放在实验阶段，意味着 P1–P5 全部在无基线下判断"改进"，"有证据的自改进"在 P5 前没有任何证据；R2 配对比较对象会是已被改造的系统自身。

## 替代里程碑顺序

- M0 发布身份核实 + 冻结基线任务集（含隐藏集）与固定裁判/指标
- M1 代次 fencing + 预算账本 + 路径/副作用白名单
- M2 最小纵切零 go：单账号、草稿 PR、无合并；合同含最少交付义务
- M3 中断恢复（依赖 M1）
- M4 凭据隔离、锁文件强制
- M5 GitHub App 关联账号识别（仅用于拒绝自审，不授予独立性）
- M6 低风险自动合并（验证器门通过 + 非关联人审核）
- M7 灰度/回滚；R2–R4

## 三个可实测通过/失败标准

1. **零暂停退化**：冻结任务集上，合同结束时"未达终点且预算剩余>30% 且无阻塞证据"的比例 <5%，否则失败；同时越权次数必须为 0。
2. **撤销语义**：随机时刻注入 100 次撤销，未发出动作泄漏 0 次；已发出动作 100% 被枚举并标注补偿状态；任一"声称已撤销但外部存在未标注动作"即失败。
3. **独立性与收益**：R2 配对比较中，恢复方案相对基线在隐藏集上通过率提升且置信区间不含 0；同一人双账号触发合并次数为 0，任一次即失败。

## 第 2 轮：Fable 原始回复

## 一、你的反驳里我认为的错误或新增过度设计

**反驳1：结论对，边界画大了。** 你说 fencing 只能拦"真正验证代次的写入"，shell 可绕过——这是对的，我第一轮把 fencing 说成了通用保护，是措辞错误。但由此推出的 M1 内容有两处膨胀：(a) "依赖按锁文件准备、记录工具链，否则先导比较不能重放"——可重放是 R1 实验的需求，不是 M2 交付门的需求。M2 只需**记录**环境指纹（锁文件哈希、工具链版本），**强制**可复现环境应推到 R1 前置，否则 M1 变成环境管理平台。(b) fencing 不应因反驳1被降级：它保护的对象是**受控交付服务**的写入（分支、PR、账本），这正是 shell 绕不过的那一层。正确的分工是：凭据隔离防越界，fencing 防旧代次在受控层的重复写。两者都要，但都只针对受控层。

**反驳2：修正正确，我接受"不幂等"。** 但 M2 只发一个外部动作（一个草稿 PR）。此时"远端对账"的最小形态是：dispatch 前持久化意图，响应丢失标 unknown，**不自动重发，交人工**。通用对账引擎是 M3 的前置（跨重启恢复若不先对账旧意图，就会重复建 PR），不是 M2 的内容。

**反驳3：基本无分歧，但有一处误读。** 我没有主张用"测试足够"替代分支规则。我的主张是：双账号是 GitHub 侧的**授权条件**，不是审核独立的**证据**；独立性来源于候选无法修改的验证器。你的表述已与此一致，唯一要守住的是：M5 的关联账号识别只用于**拒绝**自审，不能反过来作为"已独立"的凭证。

**反驳4："预算剩余不构成冒险交付义务"偷换了义务对象。** 我从未要求"必须交付"，我要求的是"必须给出可复现的阻塞证据"。义务对象是**解释**，不是**交付**。

## 二、我仍不同意的一点

**"证据不足保持未知"不能适用于暂停结果。** 你的 fixture 方案（必停/必继续逐项过）是必要的，但 fixture 是已知集，任何候选都能学会在 fixture 上停对、在真实任务上一律停。若真实任务上的"无证据暂停"记为"未知"而非失败，目标函数缺口原封不动。

设计推理：暂停只能有两种记账——附阻塞证据的暂停记"阻塞"，无证据的暂停记"失败"。没有第三种"安全但未知"。至于阻塞证据是否真实，靠抽样人审（试点假设：首轮 100% 审，因为量小；比例阈值先导后冻结）。这不是数值门槛，是记账规则。

## 三、我愿接受的最小上线契约（M2）

**范围**：单仓库、单任务、单授权分支前缀、可写路径白名单；builder 无 GitHub 令牌、无控制面凭据、无发布凭据，出站网络仅包注册表只读（试点假设，需按实际任务集验证误拒率）。

**唯一外部动作**：受控服务按逻辑动作 ID 创建一个草稿 PR。builder 不能触发任何其他外发。

**验证门**：仓库现有测试命令 + 静态检查，在受控服务内执行，不在 builder 内。候选不能修改门本身。

**结果只有三种**：
1. **delivered**：门通过，草稿 PR 已确认创建。
2. **blocked**：候选主动停，且附可复现阻塞证据（失败命令、缺失依赖、需人决策的具体问题）。
3. **aborted**：崩溃、预算耗尽、越界尝试、无证据停止。

**记账**：delivered 记成功；blocked 记阻塞并人审；aborted 记失败。任一越界尝试（被拒的写或凭据请求）不只记失败，**暂停整个试点**直到归因。

**M2 崩溃时的明确结果**：
- worker 进程死亡或心跳超时 → 任务状态 aborted，代次作废，已消耗预算入账，**不自动重跑**。
- 若意图记录为"未 dispatch" → 无外部残留，结束。
- 若意图记录为"已 dispatch、未确认" → 标 unknown，进人工对账队列；受控服务在可达时查远端，存在则打 aborted 标签，不可达则保持 unknown。**新授权不得在 unknown 未清零前 dispatch 同一逻辑动作 ID。**
- 重启只能由人工发起新授权、分配新代次；旧代次的任何后续写入被受控层拒绝。

**M2 不包含**：跨重启接力、自动修复循环（除明确规则内一次有限重试，且重试也消耗同一预算）、可复现环境强制、通用对账、自动合并。

## 四、防止无边界化的两条硬约束

- 每个里程碑只允许新增**一种**外部动作类型；新增即触发撤销语义重审。
- 任何"为了实验能跑"而加进交付路径的组件（可重放环境、评测裁判），必须证明它在 M2 契约的三种结果判定中被用到，否则归入 R1。

经验证据部分：以上全部为设计推理；三种结果的真实分布、白名单误拒率、阻塞证据真实率，在先导前均为未知，阈值应先导后冻结。
