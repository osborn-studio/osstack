canon=lambda obj:json.dumps(obj,ensure_ascii=False,sort_keys=True,separators=(',',':'))
def digest(domain,obj):return hashlib.sha256((domain+'\n'+canon(obj)).encode()).hexdigest()

    elif helper=='trialRootEffectId':prefix='trial-'
    elif helper not in ['recoverySubjectDigest','recoveryRequestInputDigest','trialConsumptionInputDigest']:raise ValueError(helper)
    expected=prefix+digest(vector['domain'],value)
    if args.check:assert vector['expected']==expected,helper
    else:vector['expected']=expected

# J11 operator recovery storage and verifier specification

Candidate source: main `ce543535be9b1ef96a8c4fb14d13ea8483444051`, schema 47. Candidate target: 48. Exact bytes and complete table lineage are in `packages/core/fixtures/operator-recovery/manifest.json`. This file and the SQL fixtures specify J12; no migration is registered and no serving database is opened by this change.

## Storage and freeze procedure

`bootstrap.sql` adds only `operator_recovery_decisions`, `operator_upgrade_journal`, their indexes and immutable-history triggers. `source-hold.sql` creates a foreign-key-valid schema-47 Attention dispatch in `dispatch_committed` with accepted message, uncertain action, delivery-unknown wait and abandoned-unknown resolution. It contains no synthetic completion. `future-storage.sql` defines separate method binding/object, active pointer, trial consumption and engineering-goal shapes for later migrations.

The manifest freezes raw SHA256 of SQL and fixture bytes; `schema_spec_digest` hashes the exact change ID, adjacent source/target numbers, those digests, the source/target schema catalog digests and sorted full expected target table list under `osstack.joint.schema-spec.v1`. It excludes future receipts/builds, avoiding a circular hash. J12 qualification additionally binds candidate commit, executable build digest and measured support profile. Schema catalog digests are raw SHA256 of joint-canonical-v1 JSON over SQLite `sqlite_master` rows `{type,name,tbl_name,sql}`, ordered by `(type,name)` and excluding SQLite internal objects whose names start with `sqlite_`. This freezes original CHECKs, indexes, views and triggers as well as tables. The schema-47 migration source and complete catalog must match the candidate base. A changed number, SQL byte, fixture or candidate requires new evidence.

48 is a candidate number, not a global reservation. The state-owner serializes `control_plane_schema`. J08/J10/J13 each supply their own `schema_spec → recovery → scoped` proof against their actual composed main. Their templates are not part of bootstrap and have no allocated schema number. File blobs are durable before transactional digest/ref insertion. Active pointers, qualification refs and consumption update under a single fenced transaction. A file rename is not a multi-object transaction.

## Recovery entry and bootstrap algorithm (J12 required)

1. Resolve the explicitly supplied recovery home; reject default/reserved or mismatched homes according to the serving/recovery policy. Authenticate the operator from the host context and verify current scope rights. Never trust operator fields supplied in a request.
2. Open through a dedicated recovery path before normal migration. Check exact version and lineage before changing pragmas/DDL. Acquire exclusive maintenance ownership and fence previous control-plane writers. Process lease expiry alone does not prove that a worker stopped.
3. Set `synchronous=FULL`; begin the owner-fenced write transaction. Recheck source version, lineage, owner generation, current operator grant and a fresh request identity inside the transaction.
4. Compare the SQL bytes to the frozen digest and a closed allowed-statement manifest. The only bootstrap effects are the listed new tables/indexes/triggers and the atomic version/lineage declaration. Reject UPDATE/DELETE/ALTER on original action, message, phase, hold, budget or worker records. Do not implement a regex-only SQL security filter; execute the pinned embedded statements.
5. Create the whole ledger and set the target version in the same transaction. On interruption, retain either source schema without any new ledger or the complete target. Never reset `user_version`. Start no worker.
6. Reopen using the matching recovery build, verify complete lineage and original rows, then allow operator recovery. The old schema-47 binary must reject 48 before migration/normal writes. Deployment must separately stop/fence an already-open old writer; a version check at open cannot fence an existing connection.

Ordinary upgrades remain blocked by unresolved holds. The bootstrap exception only adds recovery capability. For a pre-hold-table source version, use its explicitly registered compatibility rules; absence of a table is not evidence that an invocation did not start. Unsupported or mixed lineage fails closed.

## Request, proof, receipt and idempotency

J01 exports `RecoveryRequest`, `RecoveryProofEnvelope`, `RecoveryReceipt`, `RecoverySubject` and `MigrationSpec`; committed JSON shapes live in `packages/protocol/schemas/joint/joint-contract.schema.json`. Runtime input must use raw decoding plus semantic validation. Request carries request ID, subject, expected revision, requested decision, proof refs and expected schema spec. Operator, phase and generations are loaded from trusted state. A request cannot directly submit them as facts.

Within the current owner transaction, resolve `(principal, request_id)` first. Use `recoveryRequestInputDigest` under the registered `osstack.joint.recovery-request-input.v1` domain over schema version, authenticated principal/scope/tenant and the entire parsed request. Trial consumption uses its separate registered constructor/domain; root IDs use `trialRootEffectId`. Identical input returns the existing receipt only after current authentication/scope checks. Different input returns idempotency conflict. The recovery revision is 0 when this subject has no ledger entry; otherwise it is `MAX(prior_revision)+1` from this subject’s immutable ledger. It is distinct from the session/message/binding revision. Compare it to `if_revision` inside the write transaction; appending a row advances it exactly once even for preserve_unknown. Re-read and compare the original subject facts, live owner and binding/source generations in that same transaction; ledger revision alone cannot fence a source change. The local-home ledger rejects broker subjects; J17 owns the broker-side ledger and cannot reuse a home owner generation. Receipt proofs name their immutable record refs; preserve_unknown has no proof, and each resolving decision has exactly one matching typed proof. The ledger's unique `(subject_digest, prior_revision)` prevents concurrent different requests from deciding the same revision. A replay does not insert a second row. A retry after preserve_unknown uses a new request ID and current revision. A terminal decision seals this subject chain; later contradictory decisions require a new protocol version, not a new revision. SQL insertion guards reject skipped revisions and replacement even when SQLite recursive triggers are OFF.

Load proofs by immutable host refs. Recompute raw evidence digests and verify producer authorization, subject, candidate/build/schema/profile and timestamps. A matching SHA256 is not producer authentication. Broker proof also binds broker ID, lease, broker schema and broker owner generation. Home ownership never substitutes for broker evidence. Receipt records actual trusted state, not the client's desired state. Receipt insertion and any required original-subject hold/accounting CAS commit atomically in FULL mode. A denied/conflicting request changes nothing.

## Verifier and post-state matrix

| Trusted state | Decision | Additional required proof | Persisted consequence |
|---|---|---|---|
| Any supported subject | preserve_unknown | Current authority, target and revision | Increment recovery revision, append receipt; preserve original phase/hold/resources/reserved budget/wait; upgrade blocked |
| Reserved, resolution=none | proven_not_started | Dispatcher transaction confirms never committed, stop intent, exact cancellation CAS | Original action permanently cancelled before dispatch; release only provably unexecuted reservation; wait remains unfulfilled; no resend |
| Committed or broker unknown | proven_stopped | Independent exact invocation containment/termination record | Append resolved_stopped; retain original immutable phase/hold history; release concurrency only; unknown finance stays reserved; wait remains unfulfilled; no resend |
| Committed home subject | applied_observed | Existing exact completed turn + applied message, or exact Graph completion receipt | Project the existing completion; preserve provenance; do not manufacture success from exit 0 or an operator note |
| Legacy unknown | preserve_unknown only | Current authority and known legacy target | Never convert absence of evidence into stopped/not-started |
| Abandoned resolution on reserved | preserve_unknown only | Current authority | Do not revive a terminal disposition or dispatch again |

Other state/decision pairs fail without mutation. New effect subjects require binding generation and profile; legacy Attention/broker subjects can explicitly carry null identities. Subject digest includes the discriminant and all typed keys. The receipt proof and effect/broker identity must agree. Self-reported roles do not establish independence.

`proven_stopped` is an accounting resolution, not completion. A compatible upgrade requires every relevant hold accounted for, no active dispatcher, intact reserved unknown finance and an explicit maintenance journal transition. `operator_upgrade_journal` records fenced → verified → installed_inactive (or failed) with revisions/evidence. SQL enforces append-only revision order and the listed state transitions; the host still authenticates evidence and fences the live owner. Installation never resumes dispatch automatically. A failed upgrade retains the recovery build and obligations; downgrade is unsupported.

## J12 acceptance obligations

The J11 tests execute SQL in isolated in-memory databases. They check exact digests/lineage, preservation of all original rows, valid foreign keys, rollback at injected transaction boundaries, old migration-runner refusal, immutable history and permit uniqueness. These are specification checks, not process-crash qualification.

Before J12 can pass, add file-backed WAL/FULL subprocess kill tests before/during/after DDL and commit; old-owner and already-open old-writer fencing; missing/mixed lineage; wrong migration number/DDL/build/profile; malicious original-table mutations; duplicate and conflicting requests; stale subject revision; trusted-proof forgery and subject mismatch; accounting and wait assertions for every matrix cell; original-message non-replay; broker orphan proof on the exact broker tuple when enabled. Re-run against the exact composed candidate. Independent oracle authorship and trusted provider measurements remain separate gates.

The narrow local-home gate applies only with broker disabled. It does not satisfy Firstmate's full home+broker recovery gate. No later migration may reuse the bootstrap test result as proof of its own recoverability.
