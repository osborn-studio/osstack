**结论：先做 B，立刻接 A 的内置 CLI 子集，C 只做准入关闭这一小片并行推进。G25 确实在证明比原验收更多的东西，应按“宿主实例内、重启即失败关闭”的边界收口。**

## 为什么 B 第一

当前真实链路是这样的：内置适配器没有 confirmStopped，包装器在 broker 第 538 行走不到 original 分支，第 541 行对 adapter 类型拿到的 commandPending 是 undefined，于是第 557 行必然抛出“external stop unconfirmed”。也就是说，真实 CLI 现在会先启动、产生效果，再在完成后被判为未确认，这是最坏的顺序：效果已发生，结果被丢弃，还要进入对账。B 把这次拒绝提前到预留和启动之前，不新增任何未知效果。它是几十行的改动，能立刻让状态诚实，并且不改变任何测试中的有限适配器行为。

B 的验收：

- 执行注册为 adapter 且适配器缺少 confirmStopped 时，在 reservation 和 agent 启动前以明确错误码拒绝，不写 intent，不建 worktree。
- 已存在 run 的读取、取消、对账不受影响。
- 第 541 行对 adapter 类型改为显式返回“无可信停止收据”，不再靠 undefined 兜底。

## A 才是可用性的真正补丁

A 应限定为“本宿主实例、适配器自己 spawn 的本地子进程”。三个内置适配器都是 CLI 子进程，可以复用 runShellCommand 已有的进程组终止证明：以独立进程组启动，close 之后对 pgid 做探测，ESRCH 才记录 stopped:true，evidence 写入 pgid、退出码、探测时间。done 事件、iterator 关闭、AbortSignal 触发都不算证据。

A 的验收：

- 探针输出中三个内置适配器 hasStopConfirmation 为 true，且 evidence 非空并引用观测到的进程组。
- 取消路径下若 TERM 和 KILL 宽限后仍有后代存活，返回 stopped:false，broker 保持失败关闭。
- 第 555 行的固定一秒竞速改为按执行类型的有界等待，与第 549 行的宽限口径一致。延长上界是给观测留时间，不是放松证据标准。
- 若某个适配器改用 SDK 而拿不到 pgid，它继续被 B 拒绝，并在文档中列为未支持，而不是伪造收据。

内置后端真正可用还缺四件事，A 之后逐项补：适配器必须在 abort 时真正杀进程组而非仅发出 cancelled；真实 CLI 的 usage 事件要符合第 496 到 512 行的严格校验，否则整次运行会因格式被判失败；runtimeIdentity 需要返回实际二进制指纹；Loop 和权限层需要用与 broker 相同的执行注册路径，而不是绕过它。

## G25 是否过度证明

是。第 681 到 683 行是原始验收，对应 F01 到 F12 的核心承诺：不形成非法成功、未知即对账、不重放未知副作用、不宣称物理恰好一次。第 685 和 687 行把范围扩展到了 daemon 未观察到 worker 退出时的持久 PID、PGID 恢复、PID 重用和锁残留，这是无人值守恢复研究，不是内部编排试点的前提。

诚实的收口是：G25 在“宿主实例内”验收，daemon 重启后 run 进入未知并失败关闭，禁止自动接管，取消和读取仍可用，resume 明确拒绝。这不削弱安全，因为“绝不释放未知效果”的性质完整保留，牺牲的只是可用性中的自动恢复。第 685 和 687 行的内容移入独立阶段，不阻塞 G26 到 G29。

削弱安全的做法要划清界线，一律不做：从 done 或退出码推断停止；超时后视为已停；租约到期推断可接管；第 291 和 334 行的占位 receiptRef 继续冒充执行器证据。

## 四个有限切片

1. **B 准入门禁。** 上述验收，不触碰 delivery 和 reconciler。
2. **A 内置子进程收据。** 三个 CLI 适配器实现 confirmStopped，broker 等待上界按类型有界，探针转绿。
3. **A 交付层收据替换。** cancel 和 takeover 的 verifyQuiescence 改为引用本实例 broker 记录的真实停止收据；不同实例或重启后一律抛出失败关闭。验收：同实例观测到退出才允许接管，重启后 cancel 和 status 可用，resume 带明确错误码。
4. **C 窄片。** 仅做准入开关：关闭后 graph.start 拒绝，graph.cancel 和状态读取对现存 run 继续工作。这不依赖 G25 关闭，试点回滚必需，其余 G26 兼容项等第三片完成后再做。

第一和第二片完成后，G25 才能被称为内部 CLI 后端在宿主实例内验收；第三片完成后再改文档状态。以上均为改动方案与验收口径，未运行任何测试。
